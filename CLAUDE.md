# Project Specification: 2D Idle RPG (Unity 6)

## 1. Project Overview
- **Genre:** 2D Idle RPG (Medieval Fantasy)
- **Target Platform:** Mobile (Android / iOS)
- **Engine/Lang:** Unity 6 / C#
- **Key Mechanics:** Auto-combat, Monster Spawning, Equipment & Growth, Stage Escalation, Story-driven Rank System, Climax War Battles.

## 2. Core Game Systems

### A. Stage & Combat Mechanics
- **Stage Progression:** Chapter-based structure (e.g., 1-1 ~ 1-40, 2-1 ~ 2-40).
- **Combat Loop:**
  - Monsters spawn off-screen and move toward the Player.
  - Player attacks with equipped weapons.
  - On contact with player -> Player HP decreases.
  - Progression Loop: Auto-Combat -> Gold/Equipment Drop -> Enhance Equipment -> Stat Growth -> Stage Clear -> Unlock Rank/Content.

### B. Rank & Progression System
- Player progresses from "시골 소년" to "병사", "십인 대장", etc.
- Unlocks occur at stage milestones (e.g., Clearing 4-40 -> Rank Upgrade -> Short Dialogue Cutscene -> Unlocks New System).
- System unlocks are gated by **Rank**, NOT Player Level.

### C. War & Soldier Systems
- **Soldier System:** Unlocked at 'Decurion'. Spawns small auxiliary troops that fight alongside the player (does not alter the core idle RPG genre).
- **War System:** Triggered at chapter climaxes (e.g., Stage X-40). Features larger monster/soldier scale and visual effects without changing genre mechanics.

### D. Growth Systems (Decoupled Subsystems)
- Equipment, Skills, Pets, Relics, Collections, Achievements, Enhancements, Promotions.
- Every growth subsystem must be independent and decoupled.

## 3. Architecture & Technical Rules

### A. Programming Guidelines
- **Design Pattern:** Object-Oriented Programming (OOP), SOLID, Composition over Inheritance.
- **Data Architecture:** Data-driven via ScriptableObjects (SO).
- **Communication:** Event-driven architecture (Observer/Action based). Cross-system communication goes through `Core.EventBus` — domain systems must never reference each other directly.
- **Performance:** Avoid `Update()` abuse, strict Object Pooling, Addressables-ready design.
- **Code Style:** XML Documentation comments, zero magic numbers, interface-driven.

### C. Core Foundation (implemented)
`Assets/02. Script/Core/` provides the base every other system builds on:
- `IManager` — lifecycle contract (`Initialize`/`Shutdown`) for stateful managers.
- `IService` — marker interface for stateless functionality providers.
- `ITickable` — `Tick(float deltaTime)` contract; register with `GameTicker` instead of writing a per-object `Update()`.
- `ServiceLocator` — type-keyed instance registry (`Register<T>`/`Get<T>`/`TryGet<T>`/`Unregister<T>`). Replaces scattered static singletons.
- `EventBus` — typed pub/sub (`Subscribe<T>`/`Unsubscribe<T>`/`Publish<T>`) for decoupled cross-system communication.
- `GameTicker` — the one `MonoBehaviour` allowed to own an `Update()`; ticks all registered `ITickable`s, with safe register/unregister during iteration.
- `GameBootstrapper` — scene entry point (composition root). `Awake()` creates `ServiceLocator`/`EventBus`, registers `EventBus`, `GameTicker`, and `PoolManager` into the locator, exposes `static Services`/`static Events` as the single intentional global access point.

Domain systems (Combat, Stage, War, Equipment, ...) depend on `Core`; `Core` never depends on them. Domain systems talk to each other only via `EventBus`, never by direct reference.

### D. Object Pooling (implemented)
`Assets/02. Script/Core/Pooling/` + `Assets/02. Script/Managers/PoolManager.cs`:
- `IPoolable` — optional `OnSpawned()`/`OnDespawned()` hooks for pooled components.
- `PooledInstance` — internal tag component recording a spawned instance's source prefab, so callers can `Release(instance)` without remembering which pool it came from.
- `ObjectPool<T>` — generic `Stack<T>`-based pool; create/get/release/destroy are all caller-supplied callbacks, capacity/max size are constructor params (no magic numbers).
- `PoolManager` (`IManager`, `IService`) — keeps one `ObjectPool<GameObject>` per registered prefab. `RegisterPool(prefab, defaultCapacity, maxSize)`, `Get(prefab, position, rotation)`, `Release(instance)`. Registered into `GameBootstrapper.Services` at startup.
- Any system that repeatedly spawns/destroys GameObjects (monsters, projectiles, damage numbers, soldiers, VFX) must go through `PoolManager` instead of `Instantiate`/`Destroy` directly.

### E. Character Foundation (implemented)
`Assets/02. Script/Character/` — the shared component set Player and Monster are both composed from (no inheritance hierarchy):
- `CharacterStatsSO` — data asset (`MaxHealth`/`AttackPower`/`MoveSpeed`/`AttackInterval`), read-only, never mutated at runtime.
- `RuntimeStats` — plain C# copy of a `CharacterStatsSO`'s values with settable properties, so buffs/equipment can modify it later without touching the source asset.
- `CharacterStatsProvider` — holds the `CharacterStatsSO` reference and lazily builds/exposes `RuntimeStats` via `Stats` (lazy so it doesn't depend on component `Awake()` order).
- `Health` (`IPoolable`) — `TakeDamage`/`Heal`, clamps to `[0, MaxHealth]`, publishes `CharacterHealthChangedEvent` on change and `CharacterDiedEvent` on death via `GameBootstrapper.Events`. `OnSpawned()` resets current health and `IsDead` for pooled reuse.
- `CharacterMover` (`ITickable`) — moves toward a `Target` transform at `Stats.MoveSpeed`; registers with `GameTicker` in `OnEnable`. Doesn't know about "Player" — the target is assigned by whichever system spawns it (Stage/Monster spawner, later).
- `Character/Events/CharacterHealthChangedEvent.cs`, `CharacterDiedEvent.cs` — `readonly struct` events other systems (Stage, Combat, UI) subscribe to; `Health` never references those systems directly.
- `Health.Revive()` — public API that resets `IsDead`/heals to max (same logic as `OnSpawned()`, extracted so non-pooled characters can use it too). `OnSpawned()` now just calls `Revive()`.
- `PlayerReviveOnStageChanged` (MonoBehaviour, Player only) — subscribes `Stage.Events.StageChangedEvent`, calls `Revive()` on every stage change (advance, repeat, or death-fallback). Character doesn't know Stage exists as a system; it just reacts to Stage's public event, same direction as `StatEnhancementReceiver` reacting to `Enhancement`.
- `HealthBarUI` (MonoBehaviour) — world-space health bar; hidden until first damage (`Current < Max`), shown/updated via `CharacterHealthChangedEvent`, `fillAmount` tweens smoothly (`ITickable`, `GameTicker`) instead of snapping so fast deaths are still visible. Nested as a child prefab (`Assets/04. Prefab/HealthBar.prefab`) inside `Monster.prefab`/`Soldier.prefab`/`Soldier_Ranged.prefab`. **Gotcha:** the fill `Image`'s `Source Image` must be non-null and `Type` must be `Filled` (enum value `3`, not `1` — `Simple=0, Sliced=1, Tiled=2, Filled=3`) or `fillAmount` is silently ignored and the bar always renders full.

Note: `CharacterStatsSO`/`RuntimeStats` also carry `AttackRange` (added for Combat).

### F. Combat (implemented)
`Assets/02. Script/Combat/` — 2D physics-based auto-combat, built only on `Health`/`RuntimeStats`/`GameTicker`; never references Stage/Rank/Loot:
- `Attacker` (`ITickable`) — range-scan attacker. Accumulates `deltaTime`; every `Stats.AttackInterval`, runs `Physics2D.OverlapCircleAll(position, Stats.AttackRange, targetLayerMask)`, picks the nearest live `Health`, calls `TakeDamage(Stats.AttackPower)`. Used by Player to auto-attack Monsters.
- `ContactAttacker` (`ITickable`) — trigger-based attacker. Tracks the `Health` currently overlapping via `OnTriggerEnter2D`/`OnTriggerExit2D` (2D triggers — this is a 2D mobile game, no 3D physics), attacks it every `Stats.AttackInterval` while in contact. Used by Monsters to damage the Player on contact.
- Neither component publishes its own events or knows about factions by name — target filtering is purely via `LayerMask` set per-prefab in the Inspector (Player prefab targets the Monster layer, Monster prefab targets the Player layer), so adding Soldier/War later needs no Combat code changes.
- Damage application and death/health events remain owned by `Character.Health` — Combat only decides *who* and *when* to hit.
- `EnemyTracker` (`ITickable`, requires `CharacterStatsProvider`+`CharacterMover`) — periodically (`retargetInterval`) scans `detectionRange` for the nearest live, on-screen `Health` and sets it as the `CharacterMover.Target` (with `StoppingDistance = AttackRange`), so the character walks up and `Attacker` takes over once in range. Player and Soldier both use this instead of a fixed target — nobody stands still except Monsters walking straight at whatever `MonsterTargetSelector` picks (below).
- `ITargetFilter` — optional hook a component can implement (`GetComponent<ITargetFilter>()` in `EnemyTracker.Awake`) to bias which candidate is preferred without changing `EnemyTracker` itself. `Soldier.SoldierEnemyFilter` implements it so soldiers spread out across different monsters instead of piling onto the same one (see Soldier section). If no candidate is preferred, `EnemyTracker` falls back to plain nearest.
- `PlayerTargetTracker` (`IManager`/`IService`) — single-slot record of whichever `Health` the Player's `EnemyTracker` currently has targeted.
- `PlayerTargetMarker` (`ITargetFilter`, Player only) — always returns `true` for `IsPreferred` (doesn't change Player's own targeting), just mirrors `EnemyTracker`'s final pick into `PlayerTargetTracker` via `OnTargetAcquired`.
- `MonsterTargetSelector` (`ITickable`, Monster only) — replaces the old "always walk at the Player" behavior. Every `retargetInterval`, re-evaluates `CharacterMover.Target` by priority: (1) if `PlayerTargetTracker.CurrentTarget == 나` → Player; (2) else if `SoldierTargetRegistry.TryGetClaimant(나)` finds a Soldier currently targeting this monster → that Soldier; (3) else → Player (fallback). `MonsterSpawner` injects the Player `Transform` via `Initialize()` right after spawn instead of setting `CharacterMover.Target` directly.

### G. Stage (implemented)
`Assets/02. Script/Stage/` — runs a single stage (e.g. "1-1") and detects clear; knows nothing about Rank/UI, and only touches `Equipment` for the drop-table data type (see Loot section):
- `StageSO` — data asset: `Chapter`, `StageNumber`, `SpawnEntries` (`MonsterSpawnEntry[]`), `EquipmentDrops` (`Equipment.EquipmentDropEntry[]` — the stage's equipment drop table, see Loot section; empty by default, e.g. chapters 1–5 have none by design, drops start at 6-1).
- `MonsterSpawnEntry` (`[Serializable]`, not a SO) — one spawn wave: `MonsterPrefab`, `Count`, `SpawnInterval`.
- `MonsterSpawner` (`ITickable`) — walks `SpawnEntries` in order, spawns via `PoolManager.Get`, and calls `StageProgressTracker.RegisterSpawned` for each instance. Monsters always spawn off-screen opposite the player: it picks a top or bottom spawn point (`topSpawnPoints`/`bottomSpawnPoints`, both Inspector-assigned `Transform[]`) based on whether the player is currently near the top of the viewport (`playerNearTopViewportThreshold`). Instead of setting `CharacterMover.Target` directly, it calls `MonsterTargetSelector.Initialize(playerTransform)` on the spawned instance (see Combat section) so the monster's real target gets decided by the priority system.
- `StageProgressTracker` — tracks exactly the monsters it was told about via `RegisterSpawned` (a `HashSet<GameObject>`, not tag/string based) against `CharacterDiedEvent`; when the registered count all die, publishes `StageClearedEvent` and unsubscribes itself (`Dispose`). `ReleaseRemaining(PoolManager)` force-releases any still-alive monsters without loot/events — used when a stage is abandoned mid-fight (death fallback) rather than cleared.
- `Stage/Events/StageClearedEvent.cs` — `readonly struct` carrying the cleared `StageSO`; consumed by `StageProgression` (see Stage Progression section).
- `StageCatalogSO` — ordered `StageSO[]` array defining stage sequence; `Find(chapter, stageNumber)`, `GetNext(current)`, plus index-based `IndexOf(stage)`/`GetAt(index)` used by `StageProgression`'s breakthrough/repeat math.
- `StageController` (MonoBehaviour, composition root for one stage) — loads `SaveData` once (`LoadSave()`), resolves the initial stage from it (`ResolveInitialStage`), and constructs `StageProgression` with the saved current + highest-cleared stages and a `[SerializeField] maxRegressionDistance` (default 20). `LoadStage(stageSO)` calls `PoolManager.EnsurePool` per monster prefab (idempotent — see below), builds `StageProgressTracker` + `MonsterSpawner`, registers the spawner with `GameTicker`, publishes `StageChangedEvent`. `EndCurrentStage()` now also calls `StageProgressTracker.ReleaseRemaining` before disposing, so switching stages (including a death-triggered fallback) never leaves stray monsters from the abandoned attempt.
- **`PoolManager.EnsurePool(prefab, defaultCapacity, maxSize)`** (added to `Managers/PoolManager.cs`) — registers a pool only if one doesn't already exist for that prefab; needed because multiple stages reuse the same monster prefabs and `RegisterPool` throws on duplicate registration.

See "Stage Progression: Breakthrough & Repeat" section for how `StageController.LoadStage` gets called across stage clears/deaths.

### H. Attack Behaviors: Melee / Ranged (implemented)
`Assets/02. Script/Combat/` — pluggable "what happens on hit" strategies for `Attacker`, swapped by composition (attach the desired behavior component, no subclassing):
- `IAttackBehavior` — `Execute(origin, target, attackPower)`. `Attacker.Awake()` caches `GetComponent<IAttackBehavior>()` and calls it instead of applying damage directly; if none is attached, the attack silently no-ops.
- `WeaponSwing` (`ITickable`) — attached to a "weapon socket" child transform (e.g. `Player/WeaponAnchor`). `Play()` rotates the socket 0→`swingAngle`→0 over `swingDuration` via a sine curve, ticking only while actively swinging. This anchor is where the future Equipment system will parent the equipped weapon's visual — swinging the socket swings whatever is attached to it, without Combat needing to know about Equipment.
- `MeleeAttackBehavior` — applies damage immediately (hit detection stays in `Attacker`'s range scan) and calls `WeaponSwing.Play()` for the visual. The swing is purely cosmetic and does not gate the hit.
- `Projectile` (`ITickable`) — spawned by `RangedAttackBehavior`, homes toward a captured `Health` target each tick, applies damage and self-releases to the pool on arrival (`hitDistance`) or if the target dies/vanishes first (fake-null-safe).
- `RangedAttackBehavior` — spawns/launches a `Projectile` from `PoolManager` instead of dealing damage directly; damage lands only when the projectile arrives.
- Both `Character/Monster` test prefabs demonstrate this: Player currently has `MeleeAttackBehavior` wired to `WeaponAnchor`'s `WeaponSwing`; `RangedAttackBehavior` + `Assets/04. Prefab/Projectile.prefab` were verified working the same way (swap the attached behavior component to switch).

**Known gotcha — Script Execution Order:** Unity processes `Awake`→`OnEnable` per-GameObject in scene order, not as two separate global passes. Any component that reads `GameBootstrapper.Services`/`Events` in `OnEnable` (a one-shot check) can silently and permanently fail to acquire it if that GameObject initializes before `GameBootstrapper`'s GameObject does (this actually happened with `RangedAttackBehavior` failing to get `PoolManager`). Fix applied: `GameBootstrapper`'s script execution order is set to `-1000` (stored in `Core/GameBootstrapper.cs.meta`, committed) so its `Awake()` always runs first. Keep this in mind if new components read `GameBootstrapper.Services`/`Events` in `OnEnable`/`Awake`.

### I. Loot & Currency (implemented)
`Assets/02. Script/Loot/` — turns monster death into gold/equipment drops; knows Character (via `CharacterDiedEvent`), `Stage` (via `StageChangedEvent` + `StageCatalogSO`, for the current equipment drop table), and the `Equipment` data type:
- `MonsterLootSO` — data asset, **gold only**: `MinGold`/`MaxGold`/`DropChance`. Equipment is no longer per-monster — it moved to `StageSO.EquipmentDrops` (see Stage section) because drop tables are designed per stage (e.g. nothing drops before 6-1), not per monster species.
- `Equipment.EquipmentDropEntry` (`[Serializable]`, not a SO, lives in the `Equipment` namespace/folder even though `Loot` also uses it) — one drop table row: `EquipmentSO Equipment`, `DropChance`.
- `MonsterLootProvider` (MonoBehaviour) — attached to monster prefabs, holds the `MonsterLootSO` reference so `LootDropper` can identify "this dead GameObject was a monster with loot" without any tag/name check.
- `LootDropper` (plain C# class, constructed once in `GameBootstrapper` with a `StageCatalogSO`, not per-stage) — subscribes `CharacterDiedEvent` for drops and `StageChangedEvent` to track the current `StageSO` (resolved via `catalog.Find(chapter, stageNumber)`). On a monster's death: gold rolls against that monster's own `MonsterLootSO`, equipment rolls against the *current stage's* `EquipmentDrops` — both independently, both via `ItemDroppedEvent`/`GoldEarnedEvent`.
- `LootRoller` (static) — pure probability-rolling logic shared by `LootDropper` (real-time) and `OfflineProgressService` (simulated), so both roll with identical odds: `RollGold(MonsterLootSO)`, `RollEquipment(EquipmentDropEntry[])`.
- `CurrencyService` (`IManager`, `IService`) — subscribes `GoldEarnedEvent`, accumulates `CurrentGold`, publishes `GoldChangedEvent` on any change. Also exposes `TrySpendGold(amount)` (used by `Enhancement`) which fails without side effects if the balance is insufficient.
- `Loot/Events/GoldEarnedEvent.cs`, `GoldChangedEvent.cs`, `ItemDroppedEvent.cs` — the three event types other systems subscribe to.

### J. Equipment (implemented)
`Assets/02. Script/Equipment/` — item data model plus the fusion/enhancement growth loop. Equip *state* (which owned line is worn) lives in `Inventory` instead (see Inventory section) since it's about ownership, not item definitions.

**Data model**
- `EquipmentType` — `enum { Weapon, Gloves, Armor, Helmet, Shoes }` (5 gear slots).
- `EquipmentSO` — `ItemName`, `EquipmentType` (slot), `Grade` (`EquipmentGradeSO`, which rung of the grade ladder this specific slot+grade item is), `Icon` (added alongside section AI's Content Editor tool — not yet drawn by any existing UI, just the field + a place to fill it in for now).
- `EquipmentGradeSO` — one rung of the grade ladder (e.g. "커먼1"): `DisplayName`, `TintColor`. Deliberately has no separate "main grade" (Common/Rare/...) + "sub-tier" fields — the grade's position is purely its index in `EquipmentGradeCatalogSO`, so grades are entirely content-driven (add/reorder SO assets, no code/enum changes needed to extend the ladder).
- `EquipmentGradeCatalogSO` — ordered `EquipmentGradeSO[]` (currently 30: 커먼1–5, 언커먼1–5, 레어1–5, 슈퍼레어1–5, 에픽1–5, 레전더리1–5). Same shape as `StageCatalogSO`: `IndexOf`/`GetAt`/`GetNext`.
- `EquipmentCatalogSO` — flat `EquipmentSO[]` of every item definition (currently 150 = 5 slots × 30 grades); `FindBySlotAndGrade(slot, grade)` is how fusion finds "the next tier of this same slot." `IndexOf(item)`/`GetAt(index)` (same shape as the other catalogs) let `SaveService` identify an item by a plain int instead of an asset reference for PlayerPrefs storage (see Save section).

**Growth loop**
- `EquipmentFusionService` (`IManager`/`IService`) — `TryFuse(definition)` consumes 5 copies of the same line (via `InventoryService.TryConsume`) and grants 1 copy of `equipmentCatalog.FindBySlotAndGrade(definition.EquipmentType, gradeCatalog.GetNext(definition.Grade))` by re-publishing `ItemDroppedEvent` (reuses the normal acquisition pipeline — fusion output isn't special-cased in `InventoryService`). Fails harmlessly if already max grade or the next-tier item doesn't exist in the catalog yet (content gap).
- `EnhancementStoneService` (`IManager`/`IService`) — a second currency, same shape as `CurrencyService`/Gold (`AddStones`/`TrySpendStones`, publishes `EnhancementStoneChangedEvent`). Nothing grants stones yet — reserved for a future "강화석 던전" (enhancement stone dungeon); the spend side is built now so that system just needs to call `AddStones` later, no rework.
- `EquipmentEnhancementConfigSO` — one shared data asset (not per-grade/per-slot): `DuplicatesRequiredPerLevel`, `StoneCostBase`, `StoneCostIncreasePerLevel`, `StatBonusPerLevel`, `MaxLevel`.
- `EquipmentEnhancementService` (`IManager`/`IService`) — `TryEnhance(definition)` consumes `DuplicatesRequiredPerLevel` copies (keeping at least 1 — the one being enhanced isn't itself consumed) plus a scaling stone cost, then calls `InventoryService.AddEnhancementLevel`. `StatBonusPerLevel` is stored but not yet *applied* to the player — that lands whenever the equip system starts granting stats on wear.

### K. Inventory (implemented)
`Assets/02. Script/Inventory/` — holds owned equipment by line (not by individual copy) and tracks what's equipped; knows nothing about `Loot` except the event types it subscribes to:
- `OwnedEquipment` (plain class, not a SO — runtime owned state) — `Definition` (`EquipmentSO`), `Count` (stack size, used as fusion/enhancement material and for UI "×N"), `EnhancementLevel`. One `OwnedEquipment` per distinct `EquipmentSO`; duplicates increment `Count` rather than creating separate entries, and `EnhancementLevel` is shared by the whole stack (there's no per-copy enhancement — enhancing "spends" other copies of the same line as material to level up the one line).
- `InventoryService` (`IManager`, `IService`) — internally a `Dictionary<EquipmentSO, OwnedEquipment>`, exposed read-only as `Items`. Subscribes `ItemDroppedEvent` (increments existing line's `Count` or creates a new line). `TryGet(definition, out owned)`, `TryConsume(definition, amount)` (fails without side effects if short; removes the line entirely if it hits 0), `AddEnhancementLevel(definition, levels)` — all publish `InventoryChangedEvent(changed, totalDistinctItems)` on success so UI can refresh. `ExportSnapshot(catalog)`/`RestoreSnapshot(snapshot, catalog)` (de)serialize the whole dictionary to/from `OwnedEquipmentSnapshot[]` (catalog index + count + enhancement level) for `SaveService`; restoring does not publish `InventoryChangedEvent` (it's seeding, not a gameplay change).
- `EquippedGearService` (`IManager`, `IService`) — `Dictionary<EquipmentType, OwnedEquipment>` of what's worn per slot. `Equip(owned)` just records the reference and publishes `EquipmentEquippedEvent(slot)` — it does **not** consume `Count`; equipping doesn't remove the item from the stack, it just points at one of the copies as "currently worn." `ExportSnapshot(catalog)`/`RestoreSnapshot(snapshot, catalog, inventory)` mirror `InventoryService`'s for `SaveService`, keyed by `EquipmentType` + catalog index; restore looks the definition up in the (already-restored) `InventoryService` rather than creating its own `OwnedEquipment`.
- `Inventory/Events/InventoryChangedEvent.cs` (`OwnedEquipment Changed`, `int TotalDistinctItems`), `EquipmentEquippedEvent.cs` (`EquipmentType Slot`, no payload — subscribers re-query `EquippedGearService` for details).

### L. Enhancement (implemented)
`Assets/02. Script/Enhancement/` — spends gold to raise the player's base stats; deliberately does not know "Player" exists:
- `EnhancementStatType` — `enum { AttackPower, MaxHealth }`.
- `EnhancementConfigSO` — per-stat data asset: `StatType`, `BaseCost`, `CostIncreasePerLevel`, `ValuePerLevel`, `MaxLevel`. Cost for the next level is `BaseCost + CostIncreasePerLevel * currentLevel` — fully data-driven, no magic numbers in code.
- `EnhancementService` (`IManager`, `IService`) — constructed with `EventBus`, `CurrencyService`, and the full `EnhancementConfigSO[]` (assigned on `GameBootstrapper` in the Inspector). `TryEnhance(statType)` computes the next cost, calls `CurrencyService.TrySpendGold`, and on success increments the internal level and publishes `StatEnhancedEvent` (stat type + `ValuePerLevel` to apply + new level). Never touches any `RuntimeStats` itself.
- `Enhancement/Events/StatEnhancedEvent.cs` — the event `Character.StatEnhancementReceiver` subscribes to.
- `Character/StatEnhancementReceiver.cs` (MonoBehaviour, attached to the Player) — subscribes `StatEnhancedEvent`, adds `ValuePerLevel` to its own `CharacterStatsProvider.Stats.AttackPower`/`MaxHealth` depending on `StatType`. This is how "Enhancement doesn't know Player" and "Player's stats still get buffed" coexist — the receiver lives on the Character/Player side, not the Enhancement side.

### M. UI Shell (implemented)
`Assets/02. Script/UI/` — mobile-portrait presentation layer; every component here subscribes only to the events of the one domain it displays, never to each other:
- `Canvas`'s `CanvasScaler` is set to `ScaleWithScreenSize`, reference resolution 1080x1920 (portrait).
- `BottomMenuUI` — generic tab-bar controller: an inspector-assigned `(Button, GameObject panel)[]` array. Clicking a tab's button opens its panel (closing whichever was open); clicking the already-open tab's button closes it. Has zero knowledge of what any panel contains. The 장비 tab's entry is `EquippedSlotBar`, not a dedicated list panel (see `EquippedSlotBarUI` below) — `EquipmentPanel`/`EquipmentPanelUI` are left in the scene, unwired and inactive, in case a full-list view is wanted again later.
- `GoldDisplayUI` — subscribes `GoldChangedEvent`; reads `CurrencyService.CurrentGold` once on `OnEnable` for the initial value (since the event only fires on change, not on load).
- **Gotcha (legacy `Text` silently renders nothing):** if a `Text`'s `RectTransform` height is shorter than what its `fontSize` needs for one line (`preferredHeight`), `Vertical Overflow = Truncate` drops the *entire* line's vertices — the text is fully populated and the component looks correctly configured, but `vertexCount` is 0 and nothing draws. This hit `GoldText` (box height 60 vs. `fontSize` 72 needing ~80) and looked exactly like "the element went off-screen" from a resolution change; it hadn't — check `preferredHeight` vs. box height (or just set `Vertical Overflow = Overflow`) before suspecting layout/anchors.
- `StageInfoUI` — subscribes `Stage.Events.StageChangedEvent` + `Stage.Events.StageProgressChangedEvent`; shows "스테이지 N-M" + "남은 몬스터: X/Y". `Stage.StageProgressTracker` publishes `StageProgressChangedEvent(remaining, total)` once at construction (remaining = total) and again on every `CharacterDiedEvent` kill it registers, so remaining-count UI doesn't need to know about spawn waves at all.
- `EquipmentRowUI` — one card row shared by every place that lists owned equipment (`EquipmentSlotPopupUI`, `EquipmentPanelUI`): serialized refs to its background `Image`, label `Text`, and three `Button`s (row/fuse/enhance), wired directly to `EquippedGearService.Equip`/`EquipmentFusionService.TryFuse`/`EquipmentEnhancementService.TryEnhance` in `Initialize(owned, isEquipped, backgroundColor, onEquipped)`. `EquipmentRowUI.ComputeGradeBackground(cardBaseColor, grade, blend)` is a shared `static` helper (`Color.Lerp` toward `EquipmentGradeSO.TintColor`) so every list uses the same grade-tint formula.
- `EquipmentPanelUI` — subscribes `InventoryChangedEvent` + `EquipmentEquippedEvent`; instantiates one `EquipmentRowUI` per owned line, sorted by slot then grade (`EquipmentGradeCatalogSO.IndexOf`), across *all* slots (not filtered like the popup).
- `StatPanelUI` — subscribes `StatEnhancedEvent`; shows each stat's current level and next cost via `EnhancementService`, and wires its two buttons to `EnhancementService.TryEnhance`.

### O. Save & Persistence (implemented)
`Assets/02. Script/Save/` — the only system that touches `PlayerPrefs`; every other system reads/writes save state purely by publishing/subscribing events, never by calling `SaveService` directly except to `Load()` an initial snapshot at startup:
- `SaveData` (`readonly struct`) — `Gold`, `EnhancementStones`, `Chapter`/`StageNumber` (current/resume stage), `HighestClearedChapter`/`HighestClearedStageNumber` (best-ever record, see Stage Progression section), `LastActiveUnixTime`, `AttackPowerLevel`/`MaxHealthLevel` (stat enhancement levels), `InventoryJson` (owned equipment + equipped slots, see below).
- `SaveService` (`IManager`/`IService`) — subscribes `GoldChangedEvent`, `Equipment.Events.EnhancementStoneChangedEvent`, `Stage.Events.StageChangedEvent`, `Stage.Events.HighestStageClearedEvent`, `Enhancement.Events.StatEnhancedEvent`, `Inventory.Events.InventoryChangedEvent`, `Inventory.Events.EquipmentEquippedEvent`; any one of them updates its internal fields and immediately writes the *entire* `SaveData` to `PlayerPrefs` (not just the changed field — simplest way to guarantee nothing drifts out of sync). `Load()` returns sane defaults (`0` for gold/stones/highest-cleared/enhancement levels, `1` for current chapter/stage, `""` for `InventoryJson`) when there's no prior save.
- **Gotcha (seed before subscribe):** `SaveService.Initialize()` must call `Load()` and copy every field into its own internal state *before* subscribing to any event. Its internal fields otherwise start at C# defaults and only get populated reactively by their own first event — so if a *different* tracked event fires first and triggers `Save()`, it writes those never-yet-populated fields back as defaults and **overwrites real saved data with zeroes**. This actually happened: `EnhancementService.RestoreLevel()` (below) published `StatEnhancedEvent` before `OfflineProgressService` had published a fresh `StageChangedEvent`/`HighestStageClearedEvent`, and when the offline-progress elapsed-time budget was `<= 0` (e.g. rapid Editor stop/play within the same second) it skipped its own corrective publish — permanently resetting stage/highest-cleared progress to defaults. Fixed by seeding from `Load()` first; keep this in mind before adding any new tracked event.
- `Stage.Events.HighestStageClearedEvent` — separate from `StageChangedEvent` on purpose: it only fires when a stage becomes a **new** best-ever record, whereas `StageChangedEvent` fires on every stage load (advance, repeat, or death fallback). Keeping them separate is what lets "current position" and "best-ever position" diverge and both still persist correctly.
- **Stat enhancement levels** — `EnhancementService.RestoreLevel(statType, level)` sets the level directly (no gold spent) and republishes `StatEnhancedEvent` with the *cumulative* bonus (`ValuePerLevel * level`) so `Character.StatEnhancementReceiver` applies it in one shot. Called from `GameBootstrapper.Start()` (after every object's `OnEnable`, same timing reason as `OfflineProgressService.CalculateAndApply()` — `StatEnhancementReceiver` must already be subscribed or it misses the event).
- **Inventory/equipped snapshot** — a variable-length collection can't be flat `SaveData` fields, so it's serialized as one JSON blob (`JsonUtility`) keyed by `EquipmentCatalogSO` index rather than by `EquipmentSO` reference (PlayerPrefs can't hold asset references). `EquipmentCatalogSO.IndexOf`/`GetAt` added to match the other index-based catalogs. `InventoryService.ExportSnapshot`/`RestoreSnapshot` and `EquippedGearService.ExportSnapshot`/`RestoreSnapshot` do the actual (de)serialization; neither publishes events when restoring (it's seeding, not gameplay). `SaveService` takes `InventoryService`/`EquippedGearService`/`EquipmentCatalogSO` as constructor dependencies — the same *composed direct dependency* shape as `EnhancementService` depending on `CurrencyService` — because rebuilding a full snapshot on every change can't be done from event payloads alone (`InventoryChangedEvent`/`EquipmentEquippedEvent` only say "something changed", not the full state). `GameBootstrapper.Awake()` constructs `InventoryService`/`EquippedGearService` *before* `SaveService` so they're available to inject, then calls `saveService.RestoreInventory(save)` right after the initial `Load()` (no `OnEnable`-timing concern here, since `EquipmentPanelUI`/`EquippedSlotBarUI`/`EquipmentSlotPopupUI` all re-query current state on their own `OnEnable`/`Open()` rather than relying on catching a one-shot event).

### P. Offline Progress (implemented)
`Assets/02. Script/Offline/` — approximates what would have happened while the app was closed; explicitly does **not** simulate player death or stage failure:
- `OfflineProgressService` — `CalculateAndApply()` runs from `GameBootstrapper.Start()` (after other objects' `OnEnable`/event subscriptions, so `OfflineProgressCalculatedEvent` isn't missed by the popup UI). Budget = `min(elapsed since LastActiveUnixTime, maxOfflineHours)`. Simulation now starts from **`HighestCleared`**, not the saved current/resume stage — offline time represents best-case play with no death risk, so it shouldn't be held back by a temporary death-fallback the player was sitting in when they left. If it reaches the last stage in the catalog, it keeps repeating that stage for the rest of the budget instead of stopping (mirrors the real-time repeat behavior). Uses `LootRoller` for identical drop odds to real combat.
- At the end, publishes `StageChangedEvent` (new resume point) and, if the record advanced, `HighestStageClearedEvent` — so `StageController.Start()`'s `SaveService.Load()` (which runs right after) picks up the post-offline state, and the player returns to a breakthrough frontier rather than wherever they'd fallen back to before going offline.

### Q. Stage Progression: Breakthrough & Repeat (implemented)
`Stage/StageProgression.cs` — the policy layer above `StageController`/`StageCatalogSO` implementing: normally advance through new stages ("돌파"); once there's nothing left to advance into (or the player died attempting new ground), fall back to repeating a stage ("반복"); repeat-clearing climbs back up one stage at a time until breakthrough naturally resumes at whichever stage was originally failed. Death always regresses, but never past `highest − maxRegressionDistance`.
- State is exactly two catalog **indices** (not `(chapter, stageNumber)` pairs — indices make "next"/"one back"/"cap distance" trivial arithmetic via `StageCatalogSO.IndexOf`/`GetAt`): `_currentIndex` (where you're playing) and `_highestClearedIndex` (your record, never regresses). **There is no separate persisted "mode" field** — Breakthrough vs. Repeat is a pure function of comparing the two (`current == highest + 1` → breakthrough/new ground; `current <= highest` → repeating already-cleared ground) — so a saved mode can never drift out of sync with the positions.
- On `StageClearedEvent`: if `current > highest` (new ground), `highest` advances to `current` (publishes `HighestStageClearedEvent`), then `current` moves to the next stage if one exists, else stays put (repeat the last stage forever). If `current <= highest` (repeat-clearing known ground), `current` just steps forward by exactly one — repeated clears climb back toward `highest + 1` one at a time, and once `current` reaches `highest + 1` and clears it, that's a new record and breakthrough resumes automatically at the stage the player originally died on.
- On `CharacterDiedEvent` (filtered to the Player via a `Transform` reference, the same filtering pattern `StageProgressTracker` already uses for monsters): regardless of current mode, `current` steps back exactly one stage, clamped to `max(current − 1, highest − maxRegressionDistance, 0)`. `highest` never regresses on death.
- `StageController` passes `playerTransform`, `maxRegressionDistance` (`[SerializeField]`, default 20), and the initial current/highest `StageSO`s (resolved from `SaveData` at `Start()`) into `StageProgression`'s constructor.

### S. Equipment Stats on Wear (implemented)
`Assets/02. Script/Equipment/` + `Assets/02. Script/Character/` — equipped gear now actually contributes stats instead of being purely cosmetic:

- `Character.EquipmentStatReceiver` (Player only) — subscribes `EquipmentStatsChangedEvent`. Unlike enhancement (monotonic, safe to `+=`), equipping can *decrease* a stat (unequip/swap), so this receiver tracks its own previously-applied total per stat and applies only the delta to `RuntimeStats`.

Fixed: `EquippedGearService` now also subscribes `InventoryChangedEvent`; `InventoryService.TryConsume` publishes the event with the same object's `Count` already at 0 right before removing the line, so `evt.Changed.Count <= 0` on the currently-equipped instance is the exact signal to auto-unequip that slot.
- Save: no dedicated save state — equipment stats are *derived* every time from `InventoryService`/`EquippedGearService`'s own persisted state (see Save section), recomputed via `EquipmentStatService.RecomputeAndPublish()` called once from `GameBootstrapper.Start()` after `RestoreInventory()` (which itself doesn't publish events).
- Content: `EquipmentStatConfig.asset` currently has 5 placeholder entries (Weapon→AttackPower, other 4 slots→MaxHealth) — balance numbers, not final.

### W. Soldier Behavior: Off-Screen Return Priority & Ranged Kiting (implemented)
`Assets/02. Script/Combat/CameraVisibility.cs` + `Assets/02. Script/Soldier/SoldierBehaviorController.cs` — soldiers now prioritize getting back on-screen over any combat logic, and ranged soldiers kite instead of tanking hits at melee range:
- `CameraVisibility.IsOnScreen(camera, worldPosition, viewportMargin = 0f)` — static helper extracted from `EnemyTracker`'s original on-screen check, so target-candidate filtering and a soldier's own off-screen check share one viewport-margin-aware formula.
- `SoldierBehaviorController.Evaluate()` checks `CameraVisibility.IsOnScreen` on its *own* position first, before consulting its `BehaviorProfileSO` rules at all — if off-screen, it skips straight to `ReturnToScreen()` (disables `EnemyTracker`, points `CharacterMover.Target` at a viewport-clamped position) regardless of engage/hold/retreat mode.
- **Gotcha:** the return target must be a fresh, *unparented* scratch `Transform` (`_returnAnchor`, created once in `Awake()`, repositioned every call). An earlier attempt parented it to the soldier itself — since a child's world position tracks its parent, the anchor receded at exactly the rate the soldier walked toward it, so the soldier ran in a straight line forever. Sending it to the deployment slot's own spawn point (the original idea) doesn't work either: those sit below the camera's visible area by design (an off-screen staging line), so "return to spawn point" would just send it to *another* off-screen point forever.
- `Combat.Attacker.AttackPerformed` (`event Action`) — fires right after `_attackBehavior.Execute(...)`. A same-GameObject notification, not `EventBus` (Soldier already composes Combat components directly), that `SoldierBehaviorController` subscribes to for ranged-kiting timing.
- Ranged kiting (only when `RangedAttackBehavior` is present on the same soldier) replaces `EnemyTracker` entirely for that unit while `Engage`: on `AttackPerformed`, starts a `postAttackLockDuration` (default 0.5s) root (`CharacterMover.Target = null`). Once the lock expires, if the nearest on-screen enemy is within `AttackRange`, it retreats — tries 5 candidate directions (straight away from the enemy, then that vector rotated ±45°/±90°) at `kiteStepDistance`, keeping only ones that stay inside the viewport (`kiteScreenMargin`) and picking whichever maximizes distance from the enemy. If every candidate would leave the screen (cornered), it holds position instead of forcing itself off-screen, since that would just re-trigger the off-screen-return priority above.

### X. Monster Targeting Simplified to Nearest-Ally, Real Attack Range, Visual Tiering (implemented — supersedes the `MonsterTargetSelector` description in section F)

### Y. Rank Gating Fixes: Startup Promotion Replay & Locked Soldier Tab (implemented — supersedes part of section U)
- **Gotcha fixed:** `RankService` used to sit at its constructor-default rank (index 0) until `GameBootstrapper.Start()` called `RestoreLevel`. ### AC. Enhancement System Expansion: New Stats & Critical Hits (implemented)
`Assets/02. Script/Enhancement/` + `Assets/02. Script/Character/` + `Assets/02. Script/Combat/Attacker.cs`:
- `EnhancementStatType` gained `AttackSpeed`, `MoveSpeed`, `CriticalChance`, `CriticalDamage` (supersedes the two-value enum shown in section L). `CharacterStatsSO`/`RuntimeStats` gained matching `CriticalChance` (default `0`) and `CriticalDamageMultiplier` (default `0.5` — a critical hit deals `AttackPower * (1 + CriticalDamageMultiplier)`, so the default is "crits deal 150%").
- `Combat.Attacker` rolls `Random.value < Stats.CriticalChance` on every attack and scales damage accordingly before calling `IAttackBehavior.Execute`. This applies to whatever shares the component — Player, Soldier, and Monster alike — but monsters never crit in practice since their base `CriticalChance` is `0`.
- `Character.RuntimeStatApplier` now takes the owning character's *base* `CharacterStatsSO` alongside its `RuntimeStats`, because `AttackSpeed`/`MoveSpeed` are designed as "N% of the character's own base value per level" rather than a flat delta (e.g. `stats.MoveSpeed += baseStats.MoveSpeed * delta`) — `CriticalChance`/`CriticalDamage` stay flat additive (percentage-point) since they have no meaningful "base" to scale from. Both `StatEnhancementReceiver` and `EquipmentStatReceiver` (which share this mapping table) pass `CharacterStatsProvider.BaseStats` into the call now.
- `EnhancementConfigSO.CostIncreasePerLevel` (linear, `int`) was replaced with `CostMultiplier` (compound, `float`) — next cost is `BaseCost * CostMultiplier ^ level`, computed in `double` and saturated at `int.MaxValue` rather than cast straight to `int`. **Gotcha this fixed:** the naive `int` cast overflowed (wrapped negative) around level 47 at a 1.5x multiplier, and `CurrencyService.TrySpendGold` then read the negative cost as "affordable," making enhancement free (and net gold-*positive*, since spending a negative amount is adding). Current tuned values: `AttackPower`/`MaxHealth`/`AttackSpeed`/`MoveSpeed` at 1.05x–1.1x (`AttackPower`/`MaxHealth` 1.05x, `AttackSpeed`/`MoveSpeed` 1.1x), `CriticalChance`/`CriticalDamage` at 2.1x, all with `MaxLevel = 2000` (previously 50) — chosen so the compound curve stays affordable across a meaningfully large number of levels instead of most of the level range being purely decorative, since monster HP scaling (section X derived from section R) grows *linearly* with stage index while a much steeper compound rate does not correspond to that at all.
- `AttackSpeed`/`MoveSpeed`: 1%/level, capped at level 20 (±20% off base). `CriticalChance`: 0.1%/level to level 500. `CriticalDamage`: 0.5%/level to level 300 (i.e. the crit bonus fraction, not total multiplier — see above).
- `UI.StatDisplayNames.FormatValue(statType, value)` — new formatting helper so the four percentage-based stats render as `"N%"` in `StatRowUI` instead of a raw decimal (`0.01` read as meaningless before this).
- `Save.SaveData`/`SaveService` gained one level field per new stat, following the exact same per-stat-field pattern as `AttackPowerLevel`/`MaxHealthLevel` (no generic collection — six named int fields, consistent with existing style rather than a new serialization scheme).

### AD. Offline Progress: Difficulty-Accurate & Repeat-Only (implemented — supersedes section P)
`Assets/02. Script/Offline/OfflineProgressService.cs`:
- **Gotcha fixed:** the offline combat simulation computed monster health from each monster's flat `CharacterStatsSO.MaxHealth`, completely ignoring `StageDifficultyConfigSO`'s per-stage-index multiplier that real combat applies via `StageMonsterScaler` (up to ~49x by the final stage). The simulation was effectively always fighting stage-1-strength monsters, so a long-enough offline window could blow through most of the 320-stage catalog in one sitting — including stages the player could never actually clear live. Fixed by computing `_difficultyConfig.GetMultiplier(_catalog.IndexOf(stage))` and folding it into the simulated monster's health exactly like `StageMonsterScaler` does.
- Even with health scaling fixed, the simulation still advanced into new, unproven stages every time it "cleared" one. Redesigned to be repeat-only: it now simulates the player's *highest-cleared* stage on repeat for the entire time budget and never advances the record or resume position past it, always resuming there afterward regardless of whatever death-regressed position (see `StageProgression`, section Q) was current when the player left. `HighestStageClearedEvent` is no longer published from here at all, since the record never changes.
- `Offline.Events.OfflineProgressCalculatedEvent.StagesCleared` renamed to `TimesCleared`, reflecting that it now counts repeat-clears of one stage rather than newly-conquered stages.

Same "recompute fully from BaseStats every spawn, never accumulate across pool reuse" shape as `Character.StageMonsterScaler.ApplyScale`. - `SkillSO` gained `VfxFollowCaster`(bool)/`VfxHeightOffset`(float) — same sparse opt-in idiom as the shake fields above. `SpawnAndPlay` gained an optional `Transform followTarget` param: when given, the spawned instance is `SetParent(followTarget, worldPositionStays: true)` right after spawn, so it tracks the caster purely through Unity's transform hierarchy — no per-frame follow code anywhere. `PoolManager.Release`'s existing `ReturnToRoot` already reparents back to the pool root on every release regardless of who parented it in between, so no extra cleanup was needed.
- `Skill.Effects.SelfBuffSkillEffect.Execute` computes `origin.position + Vector3.up * definition.VfxHeightOffset` as the spawn position and passes `origin` itself as `followTarget` when `VfxFollowCaster` is set — `origin` is the caster's own `SkillSlot` transform (a Player child sitting at local `(0,0,0)`, i.e. exactly the Player's position), so this reuses the same "above-head" height (`0.7`) `HealthBar` already sits at.
- `SkillVfx_SelfBuff.prefab` had its `ParticleSystem`/`ParticleSystemRenderer`/`SkillEffectVfx` components replaced in place with `SpriteRenderer`/`Animator`(→ user-authored `DamageUp.controller`)/`SkillEffectAnimationVfx`, keeping the **same root GameObject fileID** so `Skill_BattleCry.asset`'s existing `vfxPrefab` reference needed no edit. `Skill_BattleCry.asset`: `vfxFollowCaster=1`, `vfxHeightOffset=0.7`.
- **Gotcha fixed (invisible despite correct spawn):** the new effect and the Player sprite sat at the same position with the same default `sortingOrder` (0), so the (opaque, same-size) Player sprite fully occluded it every time. Fixed by setting the effect's `SpriteRenderer.sortingOrder = 2` (above `WeaponVisual`'s `1` from section AP, above the body's `0`) directly on the prefab.
- Verified in Play Mode: forcing a cast shows the sprite advancing through all animation frames and cleanly deactivating (pooled) after exactly one clip-length with no looping; moving the Player mid-effect moves the effect by the identical delta the same frame (pure transform-parenting follow, no lag).

### BG. Equipment Possession Effect: Owned-Regardless-of-Equip Stat Bonus (implemented)
`Assets/02. Script/Equipment/EquipmentPossessionConfigSO.cs` + `EquipmentPossessionService.cs` + `Assets/02. Script/Character/PossessionStatApplier.cs` + `EquipmentPossessionStatReceiver.cs` — a second, independent passive-bonus system alongside section S's "equip-to-get-stats" (`EquipmentStatConfigSO`/`EquipmentStatService`), which only counts the 5 currently-*equipped* items. This one grants a stat bonus from merely *owning* a line, regardless of equip state, summed across every owned line:
- `EquipmentPossessionConfigSO` reuses `EquipmentStatConfigSO.SlotStatEntry` for the slot→stat mapping (무기→공격력, 장갑→공격속도, 갑옷→체력, 투구→크리티컬데미지, 신발→이동속도), same as the equip-effect config. Per-grade scaling is deliberately **not** `SlotStatEntry.PerGradeIndex` (that field is present but unused here) — the user specified growth in terms of the 6 **main-grade categories** (커먼/언커먼/레어/슈퍼레어/에픽/레전더리), not the 30 individual sub-rungs, so `mainGradeMultipliers` (`[1, 5, 10, 20, 50, 100]`) + `subGradesPerMainGrade` (`5`) implement a step function via `GetMainGradeTier(gradeIndex) = gradeIndex / subGradesPerMainGrade` — flat within a main grade's 5 sub-rungs, jumping only at the boundary. This is a deliberate, scoped exception to section J's "grade has no main-grade field, purely index-driven" rule — it doesn't touch `EquipmentGradeSO` itself, just this one config's own derived grouping.
- Enhancement-level scaling also diverges by main-grade tier rather than using a single global rate: `PossessionEnhancementTier { MainGradeTierThreshold, PercentPerLevel, MaxLevel }` — `GetEnhancementTier(mainGradeTier)` picks the entry with the largest `MainGradeTierThreshold <= mainGradeTier`. Tuned values: tiers 0–3 (커먼~슈퍼레어) get `+1%`/강화 레벨 capped at 강화 100; tiers 4–5 (에픽~레전더리) get `+10%`/강화 레벨 capped at 강화 20. This intentionally does **not** reuse `EquipmentEnhancementConfigSO.StatBonusPerLevel` (the equip-effect system's single flat rate) — `EquipmentPossessionService`'s constructor dropped that dependency entirely once this landed.
- `EquipmentPossessionService` (`IManager`/`IService`) — subscribes `Inventory.Events.InventoryChangedEvent`; `RecomputeAndPublish()` iterates **`InventoryService.Items`** (all owned lines, not `EquippedGearService`), and for each line sums `entry.BaseValue × GetMainGradeMultiplier(gradeIndex) × (1 + tier.PercentPerLevel × min(line.EnhancementLevel, tier.MaxLevel))` per stat type across every line touching that stat — same "publish only what changed vs. last time" shape as `EquipmentStatService`. Owning multiple *copies* of the same line (`OwnedEquipment.Count`) does **not** multiply the bonus (each distinct line counts once); owning multiple *distinct* lines of the same slot (different grades) sums all of them (user's explicit choice: "보유 중인 라인 전체를 합산").
- `Character.PossessionStatApplier` — a table deliberately **separate** from the pre-existing `Character.RuntimeStatApplier`, because this feature's semantics for AttackPower/MaxHealth are "% of the character's own base stat" (unlike Enhancement/`RuntimeStatApplier`'s flat-additive convention for those two stats); AttackSpeed/MoveSpeed are base-relative in both tables so the logic matches; CriticalDamage stays flat-additive-percentage-points, matching Enhancement's own established convention for that stat (section AC).
- `Character.EquipmentPossessionStatReceiver` (Player only) — subscribes `Equipment.Events.EquipmentPossessionStatsChangedEvent`, same "track previously-applied cumulative total, apply only the delta" shape as `EquipmentStatReceiver`.
- `EquipmentDetailPopupUI` — the existing 착용 옵션 미리보기 아래에 a `[보유 효과]` section was added to the same `optionsText` block (no new scene UI needed — the existing text box had spare room), listing each stat this specific line contributes as a percentage via `EquipmentPossessionService.CalculatePreview(definition, enhancementLevel)` (mirrors `EquipmentStatService.CalculatePreview`'s shape).
- No dedicated save state — like section S, this is entirely derived from `InventoryService`'s own persisted owned-lines state; `GameBootstrapper.Start()` calls `_equipmentPossessionService?.RecomputeAndPublish()` once after `RestoreInventory()`, same spot/reason as `EquipmentStatService`'s equivalent call.
- Content: `EquipmentPossessionConfig.asset` — Common1 baseline (무기 1%/장갑 0.05%/갑옷 1%/투구 0.1%/신발 0.05%), `PerGradeIndex = 0` for all 5 entries (superseded by `mainGradeMultipliers`, left at 0 as a harmless unused placeholder rather than removed, since the field is shared with `EquipmentStatConfigSO`).
- Verified in Play Mode via reflection: owning 1 Common1 weapon line applied exactly `baseAttack × 1%`; a 2nd copy of the same line added nothing further; a 2nd *distinct* weapon line (different grade) summed on top correctly; enhancing a line scaled the bonus per the tiered formula; grade multipliers matched `1/5/10/20/50/100%` exactly at 커먼1/언커먼1/레어1/슈퍼레어1/에픽1/레전더리1 and stayed flat across sub-rungs within the same main grade; SuperRare capped its enhancement contribution at 강화 100 (20%→40%), Epic capped at 강화 20 (50%→150%).

### BH. Gold Dungeon: Chapter-Relative Monster Reference + Player-Progress-Based Stage Cap (implemented — supersedes section BE)
`Assets/02. Script/Dungeon/GoldDungeonConfigSO.cs` + `GoldDungeonSessionController.cs` + `Assets/02. Script/Rank/RankService.cs` + `Assets/02. Script/Stage/StageCatalogSO.cs` + `Assets/02. Script/UI/StageStepperUI.cs`/`GoldDungeonEntryUI.cs` — section BE's `storyMultiplier(fixed climaxStage) × extraStrengthMultiplier × stageNumber` formula let the "단계" stepper scale gold reward linearly and unboundedly (the stepper's `maxStage` defaulted to `999`) while monster HP had no matching per-단계 growth — a max-stage exploit (farm 999단계 for `goldPerKillPerStage × 999` gold against monsters no stronger than whatever a single fixed reference stage gave). Replaced with two independent fixes:
- **Reference stage now varies per 단계, not fixed:** `GoldDungeonConfigSO.CalculateMonsterStatMultiplier(stageNumber)` interprets 단계 N as "챕터 N의 -20 스테이지" monster HP (`ResolveReferenceStage` → `stageCatalog.Find(N, 20)`, falling back to `stageCatalog.Find(stageCatalog.GetMaxChapter(), 20)` if that chapter doesn't exist in the catalog — purely a defensive null-guard, not the primary bound anymore). The old `climaxStage` field (single fixed reference) was removed entirely. `extraStrengthMultiplier` (existing field, `1` → **`1.2`**) is the only remaining "story-relative bias" knob, now multiplying that resolved stage's own difficulty index instead of a flat `× stageNumber` term.
- **The 단계 upper bound is the player's own progress, not catalog content:** first implemented as "clamp to whatever chapters exist in `stageCatalog`" (`StageCatalogSO.GetMaxChapter()`, new generic helper — counts the highest `StageSO.Chapter` present), then corrected per explicit user feedback ("존재하는 스테이지가 아니라 플레이어 본인이 클리어한 스테이지 기준으로") to clamp to **`RankService.HighestClearedChapter`** instead (new public getter — reuses the same `_highestClearedIndex` `RankService` already tracks for rank-eligibility, just exposes the cleared stage's `.Chapter`). `GoldDungeonConfigSO` stayed a pure data asset with no runtime-service access (unchanged architectural rule) — the player-progress clamp lives in `GoldDungeonSessionController.MaxStageNumber` (a `MonoBehaviour`, reads `GameBootstrapper.Services.Get<RankService>()`) instead of on the config.
- `GoldDungeonSessionController.Enter(stageNumber)` immediately normalizes `_stageNumber = Mathf.Clamp(stageNumber, 1, MaxStageNumber)` before *any* downstream use — both `CalculateMonsterStatMultiplier(_stageNumber)` (HP) and `GoldPerKillPerStage × _stageNumber` (gold reward) always read the same already-clamped field, so the two can never diverge regardless of what raw value the UI passed in. This is the actual exploit fix; the UI-side cap below is a second, defense-in-depth layer, not the only one.
- `StageStepperUI.SetMaxStage(max)` (new) — lets a stepper's `maxStage` be overridden at runtime instead of only the static Inspector default (`999`). `GoldDungeonEntryUI.OnEnable()` calls `stepper.SetMaxStage(session.MaxStageNumber)` every time the popup opens (relies on Unity's "all `Awake()`s in an activation finish before any `OnEnable()`s" ordering guarantee so `StageStepperUI.Awake()`'s `minStage` init has already run) — so the player can no longer even dial past their own cleared-chapter count in the first place.
- Verified in Play Mode: `RankService.SeedHighestCleared(1, 40)` → `MaxStageNumber = 1`; `SeedHighestCleared(2, 40)` → `MaxStageNumber = 2`; `Enter(999)` with the latter seed still normalized `_stageNumber` to `2`, matching the player's actual progress rather than the trimmed catalog's own max (which happened to also be 2, but for the unrelated reason of section BD's content cut — the two bounds are independent and this test isolated the progress-based one).

## 4. Execution Workflow (Strict Rule)
Do NOT write full implementation code at once. Follow this iterative approval process:

1. Requirements Analysis
2. Implementation Plan
3. Class Diagram / UML Outline
4. System Architecture Explanation
5. Target Folder/File Path Mapping

- Conversation with the user, and code comments (including XML doc comments), must be in Korean.
