### HB. PracticeStageController Re-Introduced the Spawn-Before-Commit Antipattern (GitHub 이슈 #20 추가 범위)
`Stage/PracticeStageController.cs` — 이슈 #20(커밋 `70a04c2`)이 이미 고친 "스폰 성공을 확인하기 전에 오버레이/전투 상태부터 커밋"하는 안티패턴이, 그 수정 **이후** section GK에서 새로 추가된 연습 스테이지 기능에 그대로 재발했다는 게 같은 이슈의 추가 코멘트(2026-08-26)로 제보됐다. 원래 6개 오버레이 컨트롤러(Gold/Stone/Skill/Boss 던전, 병사 구출 던전, 랭크 승급전)는 여전히 정상임을 재확인했다 — `TrySpawnMonsters()`/`TrySpawnBoss(out instance)`가 스폰 성공을 먼저 확인한 뒤에만 `_isActive`/`_isFighting`을 켜는 패턴이 그대로 살아있다.

### HC. Gacha Pull Batching Pushed to the Event Source; GC-Allocation-Ratio Performance Regression Test (GitHub 이슈 #21 나머지 완료 조건)
`Soldier/SoldierRosterService.cs` + `Gacha/GachaService.cs`/`SkillGachaService.cs` + `Editor/RegressionChecks.cs` — section GQ가 이미 고친 건 `SkillGachaTableSO.Entries` 캐싱과 `SaveService`의 저장 재직렬화 디바운스(다운스트림 소비 비용)였다. 이슈 #21을 재점검하며 남아있던 두 완료 조건("배치당 도메인 변경 이벤트 횟수가 명시적으로 제한됨", "저사양 모바일 기준 CPU·GC 예산이 정의되고 측정됨")을 이번에 마저 채웠다.
- **이벤트 소스 자체를 배치화(다운스트림 디바운스에만 기대지 않음):** `SaveService`의 더티 플래그 디바운스는 `SoldierRosterChangedEvent`가 300번 발행돼도 실제 재직렬화는 1번만 하도록 막아주지만, 이벤트 자체는 여전히 300번 발행되고 있었다 — `Core.EventBus.Publish`가 호출마다 `GetInvocationList()`로 구독자 델리게이트 배열을 새로 할당하는 구조(section DV)라, 지금 당장은 무해해도 나중에 evt마다 무거운 일을 하는 구독자(업적 시스템 등, 이슈가 명시적으로 경고한 시나리오)가 추가되면 같은 증폭이 재발할 수 있는 자리였다.
- **`SoldierRosterService.AddSoldiersBatch(IReadOnlyList<SoldierSO>)`(신규)** — N개를 로스터에 순차 등록하되 `SoldierRosterChangedEvent`는 배치 끝에 딱 1번만 발행한다. 유일한 호출부였던 `Gacha.GachaService.TryPullOne`이 더 이상 `AddSoldier`를 직접 안 부르고, `Pull()`이 루프에서 뽑힌 `SoldierSO` 정의만 모아뒀다가 루프가 끝난 뒤 `AddSoldiersBatch`를 한 번 호출하는 구조로 바뀌었다(확률 판정/재화 소모는 여전히 시도마다 개별적으로 일어난다 - 로스터 반영 단계만 배치로 묶었다). 기존 `AddSoldier`(단일 추가)는 그대로 남겨뒀다(다른 호출부가 없어 굳이 없앨 이유가 없음).
- **`Gacha.SkillGachaService`는 새 API 없이 기존 `SkillService.AddCopy(definition, amount)`의 amount 인자만 활용** — 병사와 달리 스킬은 "보유 개수"라는 집계값이라(개별 인스턴스가 아님) `AddCopiesBatch` 같은 새 메서드가 필요 없었다. `Pull()` 루프에서 `TryPullOne`이 더 이상 `AddCopy`를 직접 안 부르고 뽑힌 `SkillSO`만 반환, 루프 종료 후 `GrantByDefinition`(신규 private 메서드)이 결과를 `Dictionary<SkillSO,int>`로 정의별 집계해 서로 다른 스킬 종류 수만큼만 `AddCopy`를 호출한다 - 300연이어도 스킬 카탈로그가 9종이면 이벤트는 최대 9번.
- **성능 회귀 검사는 절대 ms/바이트 임계값이 아니라 아이템당 GC 할당량의 "비율"로 판정한다(완료 조건 "CPU·GC 예산이 정의되고 측정됨"):** 하드웨어/CI 러너 성능에 좌우되는 절대 시간과 달리 `GC.GetAllocatedBytesForCurrentThread()`는 같은 코드 경로에서 항상 같은 바이트 수를 반환해 타이머 노이즈가 없다 — 절대 임계값을 잡았다가 flaky해질 위험(이슈 #11 조사 때 자동 UI 레이캐스트 검사를 포기한 것과 같은 이유)을 피했다. `CheckGachaServicePull300DoesNotScaleSuperlinearly`가 30개 배치를 먼저 돌려 로스터를 채운 뒤 그 상태에서 300개 배치를 이어서 돌리고(이슈가 실제로 재현한 "기존 로스터가 클수록 다음 배치 비용이 커지는" 순서 그대로), 아이템당 할당량이 3배 이상 벌어지면 초선형 회귀로 판정한다. 절대 시간은 하드웨어 차이를 감안한 관대한 안전망(3초)으로만 별도 확인한다.
- `RegressionChecks.cs`에 검사 4개 추가(62/62 통과): 배치 API가 이벤트를 정확히 1회만 발행하는지(병사 로스터), `GachaService.Pull`이 실제로 그 배치 API를 거쳐가는지, GC 할당량 비율 성능 검사, 스킬 쪽 정의별 집계가 정확히 동작하는지(단일 스킬 카탈로그로 50연을 강제해 이벤트가 정확히 1번만 뜨는지 확인). 기존 58개 검사(300연 부분성공 토스트 등 `Pull()`을 실제로 호출하는 검사 다수 포함)도 리팩터링 후 전부 그대로 통과해 동작 회귀가 없음을 확인했다.
- Unity Editor에서 `execute_code`로 실제 300연 배치를 직접 실행해 소요시간이 서브밀리초(0.057ms) 수준임을 교차 확인했다 - 이슈가 원래 보고한 "600개 순차 추가 82ms"와 대조적이다(다만 `GC.GetAllocatedBytesForCurrentThread()`가 이 실행 경로에서 0을 반환한 것은 `execute_code`의 CodeDom 컴파일 환경 특성으로 보이며, 신뢰할 수 있는 수치는 `RegressionChecks`가 Unity 정식 컴파일러로 돌린 결과다).
- **완료 조건 중 여전히 남은 것:** "1/10/30/300회 결과 분포와 기존 저장 호환성 유지"는 이번 리팩터링이 확률 테이블/저장 포맷을 전혀 안 건드려 자연히 유지되지만 이번 세션에서 4개 카운트 전부를 명시적으로 검증하는 별도 테스트는 추가하지 않았다("50연 강제" 형태로 이미 일부 커버). "결과 이벤트에는 요청 수, 실제 수, 결과 목록을 포함해 UI·업적·저장이 같은 배치를 공유"는 `SoldierPulledEvent`/`SkillPulledEvent`가 이미 배치 결과 목록을 담고 있어(section AA) 사실상 충족돼 있다고 판단했다.

- **수정:** `sortingOrder`를 `-90`으로 고정했다 — 배경(-100)보다는 항상 위, 캐릭터의 실질 최저값(-80)을 포함한 그 외 모든 오브젝트(캐릭터/HealthBar/DamageNumber 등, 전부 -80 이상)보다는 항상 아래를 유지하는 값이다. 예고 표시는 바닥 장식(위치가 어디든 원근에 따라 다른 오브젝트를 가리거나 가려질 이유가 없다)이라, 캐릭터처럼 Y 위치에 따라 매 틱 동적으로 재계산할 필요 없이 고정값 하나로 항상 충분하다 — `YSortRenderer`를 붙이지 않고 정적 sortingOrder만 바꾸는 쪽을 택했다.
- 클래스 doc 주석에 이 sortingOrder 제약(배경보다 위, 나머지보다 아래)과 근거 수치를 기록해뒀다 — 프리팹 값이라 코드 자체에 상수로 강제할 수 없는 값이라, 다음에 이 프리팹을 만지는 사람이 실수로 되돌리지 않도록 하는 문서화.
- 이 컴포넌트를 재사용하는 소비처(`WarStructure`의 점령 범위, `MeteorSkillEffect`의 포탄 낙하 예고, `SiegeMortarAttackBehavior`의 공성 박격포 착탄 예고)가 프리팹 하나를 공유하므로 이 수정 한 곳으로 전부 함께 고쳐진다.
- 컴파일 0 errors, `RegressionChecks` 149/149 통과, `execute_code`로 실제 프리팹의 `sortingOrder=-90`을 재확인.
