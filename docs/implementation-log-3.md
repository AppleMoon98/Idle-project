### AP. Monster Weapon Swing Visual
`Assets/04. Prefab/Monster.prefab` + `Monster_Elite.prefab` + `Monster_Boss.prefab` — monsters use the same `Attacker`+`MeleeAttackBehavior` composition as Player/Soldier, which needs a `WeaponAnchor`(→`WeaponSwing`+weapon sprite child) for `MeleeAttackBehavior.weaponSwing` to reference. All three monster tiers have this child structure (`WeaponAnchor` at local `(0.6,0,0)` with `WeaponSwing`, default `swingAngle=90`/`swingDuration=0.2`; child `WeaponVisual` at local `(0.5,0,0)` with a `SpriteRenderer` reusing `Assets/01. Sprite/WeaponSprite.png`, `sortingOrder=1`), wired to each prefab's `MeleeAttackBehavior.weaponSwing`. `Monster_Elite`/`Monster_Boss`'s 1.2x/1.5x root `localScale` (section X) scales the weapon anchor along with the body automatically since it's a plain child — unlike `HealthBar`, no counter-scaling needed here.
- **Gotcha:** `GameTicker.Unregister` called *during* iteration only queues into `_pendingRemove` and applies it after the current frame's loop finishes (safe to unregister mid-iteration — see section C). If a character dies mid-swing, `WeaponSwing.OnDisable()` → `FinishSwing()` resets rotation to rest and calls `Unregister`, but since that call lands *during* the frame's iteration, the same still-in-`_tickables` `WeaponSwing` can receive one more `Tick()` before removal actually applies — without a guard this recomputes from the stale `_elapsed` and overwrites the just-reset rotation with a mid-swing angle, frozen on an inactive GameObject with no `OnEnable` to re-fix it on next pool reuse. `WeaponSwing.Tick()` guards with `if (!_isSwinging) return;` at the top; `FinishSwing()` sets `_isSwinging = false` before the stale tick would land, closing the gap without touching `GameTicker`'s shared deferred-removal design. Any `ITickable` whose `Tick()` reads state that `OnDisable`/`FinishSwing`-style cleanup just reset needs the same guard.

### AQ. Skill Loadout System: 6 Equip Slots, Active/Passive Tabs, Cooldown HUD (supersedes the "fixed 3-slot loadout" note in section AH; folds in later visual/interaction fixes from sections AR/AV)
`Assets/02. Script/Skill/` + `Assets/02. Script/UI/` — leveling (permanent, gold+stones) and equipping (free, freely swappable, 6 slots) are fully separate concepts, mirroring Equipment's own "보유 vs 장착" split.
- `Skill.SkillEffectType` (enum: `AreaDamage`/`SingleTargetStrike`/`SelfBuff`) + `SkillSO.EffectType` — lets a generic cast slot resolve *which* of several effect strategies to run for whatever skill happens to be equipped there.
- `Skill.SkillLoadoutService` (`IManager`/`IService`) — 6 slots (`SlotCount`), each holding a `SkillSO` or nothing. `TryEquip(slotIndex, definition)` fails if `SkillService.GetLevel(definition) < 1`; if `definition` is already equipped in a *different* slot, that slot is auto-vacated first (same "auto-vacate old slot" shape as `SoldierDeploymentService.TryAssign`, section Z). `Unequip(slotIndex)`, `FindEquippedSlot(definition)`. Publishes `Skill.Events.SkillLoadoutChangedEvent`. Starts with all 6 slots empty (no auto-populate from old saves/defaults).
- `Skill.SkillSlot` — holds only `slotIndex` and asks `SkillLoadoutService.GetEquipped(slotIndex)` fresh every tick; an empty slot does nothing. Each of the 6 cast-slot GameObjects (`Player/SkillCastSlot_0`‥`5`) carries all three `ISkillEffect` components simultaneously (`AreaDamageSkillEffect`/`SingleTargetStrikeSkillEffect`/`SelfBuffSkillEffect`), cached in `Awake()` into a `Dictionary<SkillEffectType, ISkillEffect>`; the equipped `SkillSO.EffectType` picks which one runs — same "enum → implementation table" shape as `Character.RuntimeStatApplier`. Exposes `CooldownProgress01` (0~1) for the HUD.
  - **Gotcha:** every effect component on a shared multi-effect slot GameObject needs its own `targetLayerMask`(/`range` for SingleTargetStrike) configured — a component that's only ever *inactive* in the Inspector because its skill wasn't originally assigned there still defaults to `LayerMask = 0` ("Nothing") once equipping makes it live, silently matching zero targets.
- **Inline slot-style picker (final interaction model):** tapping an equip slot **selects** it (`SkillSlotBarUI.SelectedSlotIndex`, shown via a `SelectedHighlight` child Image). Below the slot bar, `UI.SkillGridUI` renders every `SkillCatalogSO` entry as an icon grid (`GridLayoutGroup`, 140×140 cells, standard `ScrollRect → Viewport(RectMask2D) → Content` pattern from section AB) via `UI.SkillGridCellUI` cells — tapping a cell's icon *or* its level badge opens `UI.SkillDetailPopupUI`. The popup shows `levelText`(`"Lv. N / Max"`), `statsText` (per-`EffectType` spec, live magnitude/range/duration), `materialText` (gold/stone cost vs. owned, insufficient side in `<color=#ff6b6b>`, live-refreshing on `GoldChangedEvent`/`EnhancementStoneChangedEvent`) and a **장착(Equip)** button that reads `SkillSlotBarUI.SelectedSlotIndex` and calls `SkillLoadoutService.TryEquip` (disabled when the skill is level 0 or no slot is selected).
- `Canvas/PanelRoot/SkillPanel` has a `SubTabBar` (액티브/패시브, `BottomMenuUI` with `selectFirstTabByDefault=true`/`allowToggleClose=false` — same fix as section AN) toggling between an `ActiveTabContent` container (wraps `SkillSlotBar`+`SkillGridUI` together so the passive tab actually hides both) and a scriptless `PassiveTabContent` ("패시브 스킬 - 준비 중") placeholder — passives have no system yet.
- `UI.SkillCooldownHudUI` — a persistent row of 6 icon+radial-cooldown-overlay slots (`Canvas/SkillCooldownHud`, above `BottomMenu`, outside any tab panel so it's always visible, Canvas's first sibling so every popup draws in front of it). Icons refresh on `SkillLoadoutChangedEvent`; the cooldown overlay (`Image`, `Type=Filled`/`FillMethod=Radial360`, black @ 0.75 alpha) redraws every tick from `1 - SkillSlot.CooldownProgress01` via direct `[SerializeField] SkillSlot[] casterSlots` references — same "read live gameplay state every frame" shape as `HealthBarUI`.
- `UI.EquippedSlotBarUI` (Equipment domain) holds a `skillCooldownHud` reference and toggles it in its own `OnEnable`/`OnDisable` — the 장비 tab's slot bar and this HUD occupy overlapping screen space, so the HUD hides for exactly as long as the equipment UI is open.
- Save: `SaveData.SkillLoadoutJson` (array of `{SlotIndex, CatalogIndex}`, empty slots omitted) — a JSON blob like `InventoryJson`/equipment snapshots rather than flat int fields.
- **UI construction gotchas worth remembering:** Unity UI children always draw on top of their parent's own graphic — a selection-border Image needs a hollow center (`Image.Type = Sliced`, `fillCenter = false`, Unity's built-in `UI/Skin/Background.psd`) or it fully occludes whatever icon sits on the same GameObject; and a single Image field shouldn't double as both "empty-state background" and "content icon" if the content sprite's aspect ratio doesn't match the slot (use separate child Images, and set `Preserve Aspect = true` consistently across every surface reusing the same non-square placeholder sprite).

### AS. Skill Cast VFX (Particle System) + Skill Spec Data Ownership Moved to SkillSO (supersedes section AH's per-slot radius/range/duration/vfx ownership)
`Skill/SkillEffectVfx.cs` — a single reusable playback component (`IPoolable`) shared by all three skill effect types via three different prefabs (`Assets/04. Prefab/SkillVfx_AreaDamage/SkillVfx_SingleStrike/SkillVfx_SelfBuff.prefab`, same "one class, many prefabs" pattern as `Combat.Projectile`). `Play()` starts the `ParticleSystem`; `main.stopAction = ParticleSystemStopAction.Callback` (forced in `Awake()` regardless of prefab authoring) drives `OnParticleSystemStopped()` → auto-`PoolManager.Release`, no manual timer needed. Prefabs are built with Unity's built-in `Default-Particle.mat` (no new art), color-matched to each skill's `IconTint`.
- **Architecture change:** `radius`/`range`/`duration`/`vfxPrefab` originally lived on the *slot's* effect components (`AreaDamageSkillEffect`/`SingleTargetStrikeSkillEffect`/`SelfBuffSkillEffect`), which was wrong — since any of the 6 slots can have any skill equipped (section AQ), a slot-owned value is shared by whatever skill happens to sit there, so two different skills of the same `EffectType` could never have different range/radius/duration/visual. These moved to `SkillSO` (`AreaRadius`/`StrikeRange`/`BuffDuration`/`VfxPrefab` — a skill only ever uses the one field matching its own `EffectType`, others sit unused, same "sparse/unused-field-is-fine" idiom as `RankSO.RequiredStage == null`). `ISkillEffect.Execute` signature changed from `(Transform origin, float magnitude)` to `(Transform origin, SkillSO definition, float magnitude)` so effects can read them. `targetLayerMask` (always "Monster") and VFX pool capacity/max size stay on the slot components — those really are per-slot-instance, not per-skill-identity. VFX pool registration moved from `OnEnable` (fixed prefab) to inside `Execute()` (`EnsurePool` is idempotent, safe to call every cast) since the prefab now varies with whatever's equipped.
- **Balance change:** `SingleTargetStrikeSkillEffect`'s range default was `8` — larger than the distance from the player to the monster spawn points (~5.8 units, measured via camera orthographic size 8 vs. `SpawnPoint_Bottom_*` positions), so 강타 could hit monsters that had just spawned off-screen, looking like it "fired for no reason." Retuned to `2.5`, matching melee `AttackRange`.
- **Damage scales with player power (deliberate):** `AreaDamageSkillEffect`/`SingleTargetStrikeSkillEffect` deal `(caster's current RuntimeStats.AttackPower + magnitude)` instead of `magnitude` alone (cached via `GetComponentInParent<CharacterStatsProvider>()`, same pattern `SelfBuffSkillEffect` uses) — a flat skill number alone would fall behind auto-attack damage as the player's attack power grows from enhancement/equipment, removing any reason to use skills. `SelfBuffSkillEffect` is unaffected (it's a buff, not damage).

### AT. Equipment Bulk Enhance/Fuse: 전체 강화 / 전체 합성
`Equipment/EquipmentEnhancementService.TryEnhanceAll(slot)` / `Equipment/EquipmentFusionService.TryFuseAll(slot)` — next to `EquipmentSlotPopupUI`'s existing `CloseButton` (two buttons to its left). Both sort the slot's owned lines ascending by grade (`EquipmentGradeCatalogSO.IndexOf`) and drive the existing single-step `TryEnhance`/`TryFuse` to exhaustion per line before moving to the next — `TryEnhanceAll` needed `EquipmentEnhancementService` to gain an `EquipmentGradeCatalogSO` constructor dependency (`GameBootstrapper` already holds that field). `TryFuseAll` re-scans and repeats the whole ascending pass until a full pass makes zero progress, so fusion output that lands on a *higher* grade line (possibly newly created via `ItemDroppedEvent`, which mutates `InventoryService.Items` — a single static snapshot would miss it) cascades upward automatically in the same click.

### AU. Skill Auto-Cast On/Off Toggle (implemented)

### AW. Bug Fixes: Cross-Stat Unlock Refresh, Skill Panel Passive-Tab Leak
- **`StatRowUI` unlock overlay didn't clear in real time:** `OnStatEnhanced` only called `Refresh()` when `evt.StatType == _statType` (its own stat) — a row locked behind *another* stat's level (section AN, e.g. `AttackSpeed` requiring `AttackPower` Lv.100) never re-checked `IsUnlocked` when that *other* stat leveled up, so the lock overlay stayed stuck until the row was touched some other way (impossible while its buttons are non-interactable). Fixed with `EnhancementService.HasUnlockRequirement(statType)` (new passthrough) + `StatRowUI.OnStatEnhanced` also refreshing when `evt.StatType == service.GetRequiredStatType(_statType)` (guarded by `HasUnlockRequirement`, since `GetRequiredStatType` returns a meaningless default enum value for rows with no requirement at all).
- **`SkillPanel`'s 패시브 tab didn't hide the active skill grid:** `SubTabBar`'s `BottomMenuUI.panels` array was `[SkillSlotBar, PassiveTabContent]` — `SkillGrid` was never included, so it stayed visible regardless of which sub-tab was selected. Fixed by wrapping `SkillSlotBar` + `SkillGrid` in a new `ActiveTabContent` container (full-stretch, zero-offset match to `SkillPanel`'s own rect so existing child anchored-positions needed no adjustment when reparented — same recipe as the pre-existing `PassiveTabContent`) and pointing `panels[0]` at that container instead of `SkillSlotBar` directly.

### AY. Rank System: Manual War-Battle Promotion (supersedes section U's automatic "clear the required stage → auto-promote" behavior)
Clearing `RankSO.RequiredStage` no longer promotes automatically. `RankService` now tracks eligibility only:
- `RankService.SeedHighestCleared(chapter, stageNumber)` (replaces the old `CatchUpFromHighestStage`, called from the same `GameBootstrapper.Start()` spot) and its `HighestStageClearedEvent` subscription both just cache `_highestClearedIndex` — no side effects, no promotion.
- `GetNextRank()` always returns `RankCatalogSO.GetNext(current)` — **exactly one step**, never more, regardless of how far stage progress has outrun the catalog. `IsNextRankAvailable()` is true only when that one next rank's `RequiredStage` is satisfied *and* it has a `BossPrefab` assigned (content gate). `PromoteToNext()` advances exactly one step and publishes `RankChangedEvent(isRestore:false)` (unchanged consumer: `RankUpPopupUI`). **This is deliberate and load-bearing:** a player who stage-skips far ahead while still low-ranked must still fight and win every intermediate rank's promotion battle one at a time — there is no code path that lets `HighestCleared` satisfy more than the immediate next rank in one shot.
- `UI.RankUpAvailableTextUI` — a clickable gold text directly under `StageInfoText` on the main HUD, shown only while `IsNextRankAvailable()`. **Gotcha:** a component must not live on the *same* GameObject it calls `SetActive(false)` on to hide itself — that also fires that GameObject's own `OnDisable()`, unsubscribing the very event handlers needed to detect "conditions changed, should reappear," permanently stranding it hidden. Fix: put the script on an always-active parent and the toggled Text+Button on a child (`Content`) — the same `popupRoot`-as-child shape every other popup in this project uses. General trap for any component whose own visibility toggle also needs to keep listening for what should un-toggle it.
- `Rank.RankPromotionBattleController` — line-for-line the same shape as `Dungeon.StoneDungeonSessionController` (`Enter`/`Retry`/`ExitToOriginalStage`, spawns `targetRank.BossPrefab` via `PoolManager`, `CharacterDiedEvent` decides win/loss), reusing `StageController.PauseForOverlay()`/`ResumeAfterOverlay()` so the promotion battle never touches `StageSO`/`StageProgression`/`SaveService` — identical "self-contained overlay" pattern as the gold/stone dungeons, just triggered by rank eligibility instead of a dungeon-entry popup. On boss death, calls `RankService.PromoteToNext()` directly (no event indirection needed — same GameObject knows exactly what it was fighting for) then resumes the paused stage. On player death, publishes `Rank.Events.RankPromotionAttemptFailedEvent`; `UI.RankPromotionFailurePopupUI` (a `StoneDungeonFailurePopupUI` clone, same retry/exit button wiring) shows a "승급 실패" choice — retry revives the player and respawns the boss without ending the session, exit resumes the original stage with rank unchanged.
- `RankSO` gained `BossPrefab` (nullable — no boss assigned means the promotion is content-incomplete and `IsNextRankAvailable` stays false forever, same "empty = not ready" idiom as `Skill_*`'s `VfxPrefab`). `Rank_1_병사`/`Rank_2_십인대장` both currently point at `Monster_Boss.prefab` (no dedicated boss art/patterns yet, same placeholder-reuse convention as everywhere else in this project).

- Scene wiring built by duplicating the existing Soldier-뽑기 category panel and Stone-던전 popup/HUD/failure-popup/session GameObjects (preserves exact visual styling), then swapping each duplicate's domain-specific component (`StoneDungeonEntryUI` → `SkillDungeonEntryUI`, etc.) and repointing the handful of fields that don't auto-remap on duplicate — external cross-hierarchy references (e.g. `SimplePopupUI.openButton` pointing at the *original* row's button, `session` pointing at the *original* `StoneDungeonSession`) don't get remapped by Unity's duplicate (only references *within* the duplicated subtree do), so those need explicit re-wiring after every duplicate. Added as a 3rd "스킬 뽑기" category tab in `GachaPopupUI`'s existing `CategoryTabBar` (`UI.BottomMenuUI`) and a 3rd "스킬 던전" row in `DungeonPopup`.
- **Gotcha (array-of-component-reference properties via UnityMCP `manage_components.set_property`):** setting an array field of a `Component` type (e.g. `SimplePopupUI[] popupsToClose`, `Button[] pullButtons`) with plain instance-ID integers (`[123, 456]`) silently resolves every element to `null` — each element must be wrapped as `{"instanceID": 123}`. Array fields of primitives (`int[]`) or a single `Component` field both accept a plain value directly; only *arrays of object/component references* need the wrapped form. Worth remembering for any future scene wiring done through UnityMCP rather than the Editor UI.
- **Gotcha (UnityMCP GameObject `duplicate` corrupts stretch-anchor RectTransforms):** every full-stretch (`anchorMin≠anchorMax`) RectTransform produced by this MCP server's `manage_gameobject` duplicate action comes out with `anchoredPosition`/`sizeDelta` shifted by roughly half the parent's size instead of staying `(0,0)` — collapsing the copy's rect to zero width/height, so the entire duplicated subtree renders nothing despite being logically active. Children under an active `HorizontalLayoutGroup`/`VerticalLayoutGroup` self-heal on the next layout pass; children with no layout group (popup roots, category panels) stay broken until fixed by hand. Root cause is in the MCP tool, not this project's code — fix is a one-off script (walk the duplicate's transform tree in parallel with the original's, copy `anchorMin`/`anchorMax`/`pivot`/`anchoredPosition`/`sizeDelta` wherever they differ) run once **in Edit Mode** right after every `duplicate` call on a UI object; Play Mode edits don't persist, so fixing it mid-Play-session and exiting silently reverts the fix.

### BA. Skill Camera Shake + On/Off Setting (implemented)
`Assets/02. Script/Services/CameraShakeService.cs` + `Assets/02. Script/Skill/` + `Assets/02. Script/UI/CameraShakeToggleUI.cs` — lets a skill optionally shake the screen on cast, and lets the player turn that off entirely from Settings.
- `SkillSO` gained `ShakeCamera`(bool, default false)/`ShakeDuration`/`ShakeMagnitude` — same sparse "only the skills that opt in use these" idiom as `AreaRadius`/`StrikeRange`/`BuffDuration` (section AS). `Skill.Events.SkillCameraShakeRequestedEvent` (new) carries `Duration`/`Magnitude`.
- `Skill.SkillSlot.Tick()` publishes that event right after `effect.Execute(...)` when `definition.ShakeCamera` is true. `SkillSlot` never learns Camera/Services exist — same producer-doesn't-know-consumer direction as `Character.StatEnhancementReceiver` reacting to `Enhancement`'s events.

Script/UI/` — direct PlayerPrefs read/write in a self-contained `MonoBehaviour`, no service/event round-trip, since it's a pure client-side preference) **except** it reads the key from `CameraShakeService.DisabledPlayerPrefsKey` instead of a serialized Inspector string, specifically because — unlike the Sound toggles, which nothing reads yet — this key is actually consumed by a real service, so a shared `const` avoids the two sides drifting on a typo'd literal.

- Content: `Skill_BattleCry.asset` (전투의 함성) has `shakeCamera=1`, `shakeDuration=1`, `shakeMagnitude=0.25` — every other skill defaults to off, unaffected.

### BB. Skill Cast VFX: Animator/Sprite-Sheet Effects + Caster-Follow (extends section AS)
`Assets/02. Script/Skill/SkillEffectAnimationVfx.cs` — section AS's `SkillEffectVfx` was hard-coded to `ParticleSystem`; this adds a second, parallel playback component for Animator/sprite-sheet-driven effects (e.g. a hand-authored `.anim`+`.controller` pair over a sprite sheet, as opposed to a `ParticleSystem` graph), and teaches skills to keep a cast effect glued to (and above) the caster instead of leaving it stuck at the cast position.
- `Skill.SkillEffectAnimationVfx` (`IPoolable`, `ITickable`, new) — mirrors `Combat.DamageNumber`'s "self-contained pooled component, ticks its own timer, self-releases" shape rather than `SkillEffectVfx`'s particle-stop-callback shape, since `Animator` has no built-in "finished playing" event. `Play()` calls `_animator.Play(0, 0, 0f)` and reads `GetCurrentAnimatorStateInfo(0).length` as the auto-release countdown — this means the effect always plays for exactly one clip-length regardless of whether the authored clip's own Loop Time is on, so a looping clip still reads as "plays once" to the player.

### BG. Equipment Possession Effect: Owned-Regardless-of-Equip Stat Bonus
`Assets/02. Script/Equipment/EquipmentPossessionConfigSO.cs` + `EquipmentPossessionService.cs` + `Assets/02. Script/Character/PossessionStatApplier.cs` + `EquipmentPossessionStatReceiver.cs` — a second, independent passive-bonus system alongside section S's "equip-to-get-stats" (`EquipmentStatConfigSO`/`EquipmentStatService`), which only counts the 5 currently-*equipped* items. This one grants a stat bonus from merely *owning* a line, regardless of equip state, summed across every owned line:
- `EquipmentPossessionConfigSO` reuses `EquipmentStatConfigSO.SlotStatEntry` for the slot→stat mapping (무기→공격력, 장갑→공격속도, 갑옷→체력, 투구→크리티컬데미지, 신발→이동속도), same as the equip-effect config. Per-grade scaling is deliberately **not** `SlotStatEntry.PerGradeIndex` (that field is present but unused here) — the user specified growth in terms of the 6 **main-grade categories** (커먼/언커먼/레어/슈퍼레어/에픽/레전더리), not the 30 individual sub-rungs, so `mainGradeMultipliers` (`[1, 5, 10, 20, 50, 100]`) + `subGradesPerMainGrade` (`5`) implement a step function via `GetMainGradeTier(gradeIndex) = gradeIndex / subGradesPerMainGrade` — flat within a main grade's 5 sub-rungs, jumping only at the boundary. This is a deliberate, scoped exception to section J's "grade has no main-grade field, purely index-driven" rule — it doesn't touch `EquipmentGradeSO` itself, just this one config's own derived grouping.
- Enhancement-level scaling also diverges by main-grade tier rather than using a single global rate: `PossessionEnhancementTier { MainGradeTierThreshold, PercentPerLevel, MaxLevel }` — `GetEnhancementTier(mainGradeTier)` picks the entry with the largest `MainGradeTierThreshold <= mainGradeTier`. Tuned values: tiers 0–3 (커먼~슈퍼레어) get `+1%`/강화 레벨 capped at 강화 100; tiers 4–5 (에픽~레전더리) get `+10%`/강화 레벨 capped at 강화 20. This intentionally does **not** reuse `EquipmentEnhancementConfigSO.StatBonusPerLevel` (the equip-effect system's single flat rate) — `EquipmentPossessionService`'s constructor dropped that dependency entirely once this landed.
- `EquipmentPossessionService` (`IManager`/`IService`) — subscribes `Inventory.Events.InventoryChangedEvent`; `RecomputeAndPublish()` iterates **`InventoryService.Items`** (all owned lines, not `EquippedGearService`), and for each line sums `entry.BaseValue × GetMainGradeMultiplier(gradeIndex) × (1 + tier.PercentPerLevel × min(line.EnhancementLevel, tier.MaxLevel))` per stat type across every line touching that stat — same "publish only what changed vs. last time" shape as `EquipmentStatService`. Owning multiple *copies* of the same line (`OwnedEquipment.Count`) does **not** multiply the bonus (each distinct line counts once); owning multiple *distinct* lines of the same slot (different grades) sums all of them (user's explicit choice: "보유 중인 라인 전체를 합산").
- `Character.PossessionStatApplier` — a table deliberately **separate** from the pre-existing `Character.RuntimeStatApplier`, because this feature's semantics for AttackPower/MaxHealth are "% of the character's own base stat" (unlike Enhancement/`RuntimeStatApplier`'s flat-additive convention for those two stats); AttackSpeed/MoveSpeed are base-relative in both tables so the logic matches; CriticalDamage stays flat-additive-percentage-points, matching Enhancement's own established convention for that stat (section AC).
- `Character.EquipmentPossessionStatReceiver` (Player only) — subscribes `Equipment.Events.EquipmentPossessionStatsChangedEvent`, same "track previously-applied cumulative total, apply only the delta" shape as `EquipmentStatReceiver`.
- `EquipmentDetailPopupUI` — the existing 착용 옵션 미리보기 아래에 a `[보유 효과]` section was added to the same `optionsText` block (no new scene UI needed — the existing text box had spare room), listing each stat this specific line contributes as a percentage via `EquipmentPossessionService.CalculatePreview(definition, enhancementLevel)` (mirrors `EquipmentStatService.CalculatePreview`'s shape).
- No dedicated save state — like section S, this is entirely derived from `InventoryService`'s own persisted owned-lines state; `GameBootstrapper.Start()` calls `_equipmentPossessionService?.RecomputeAndPublish()` once after `RestoreInventory()`, same spot/reason as `EquipmentStatService`'s equivalent call.
- Content: `EquipmentPossessionConfig.asset` — Common1 baseline (무기 1%/장갑 0.05%/갑옷 1%/투구 0.1%/신발 0.05%), `PerGradeIndex = 0` for all 5 entries (superseded by `mainGradeMultipliers`, left at 0 as a harmless unused placeholder rather than removed, since the field is shared with `EquipmentStatConfigSO`).

### BN. Camera Zoom Slider: Mid-Left Vertical Scroll for Battlefield Visibility
`Assets/02. Script/UI/CameraZoomSliderUI.cs` — a persistent vertical slider at the screen's mid-left that directly controls `Camera.main.orthographicSize` (the project's Orthographic 2D camera, otherwise fixed at `8`).
- **Direct-apply component, not a `IManager`/`IService`+event pair:** unlike `Services.CameraShakeService` (section BA), which exists because *multiple* systems trigger shake and a separate settings toggle also gates it, camera zoom has exactly one producer (this slider) and one consumer (`Camera.main.orthographicSize`) — no other system needs to trigger or query zoom level. Following `UI.SoundVolumeSliderUI`'s simpler "slider directly applies the value and saves to `PlayerPrefs` immediately, no service/event round-trip" shape instead, since that's the established pattern for this exact kind of single-consumer personal-preference control (and `CameraZoomSliderUI` had to be a *new* component regardless — `SoundVolumeSliderUI` lives inside `SettingsPopup`, only visible when that popup is open, whereas this needed to be always on-screen).
- `Slider.direction = BottomToTop` (value `0` = bottom = "−", value `1` = top = "+"), and `orthographicSize = Lerp(wideOrthographicSize(16), narrowOrthographicSize(6), slider.value)` — deliberately *inverted* (low slider value → large `orthographicSize` → wide view; high value → small `orthographicSize` → narrow view), matching the user's explicit direction spec exactly. Both size bounds are `[SerializeField]`s (defaults `16`/`6`, chosen so the existing `8` sits at `0.8` on the slider) rather than hardcoded, since the right amount of "how much wider can you zoom out" is a balance/feel question meant to be tuned in the Inspector, not a fixed number — flagged in the plan as needing playtesting, particularly because monster spawn points and other "on/off-screen" logic elsewhere in the project (`CameraVisibility.IsOnScreen`, `DungeonSpawnUtility.RandomOnScreenPosition`, etc.) all query `Camera.main` live rather than hardcoding a size, so they should track a changed `orthographicSize` automatically, but a large enough zoom-out could still surface spawn points visually that were designed to stay off-screen — worth an eye during playtesting.
- `OnEnable` computes the slider's default position via `Mathf.InverseLerp(wide, narrow, currentOrthographicSize)` — so a fresh install with no saved `PlayerPrefs` value starts the slider exactly where the current `8` default sits (`0.8`), not snapped to an endpoint — then loads any saved value over that default and applies both to the slider (`SetValueWithoutNotify`, avoiding a redundant self-triggered `onValueChanged` call) and the camera directly.
- Scene: `Canvas/CameraZoomControl` (mid-left: `anchorMin/Max (0,0.5)`, `pivot (0,0.5)`, `anchoredPosition (30,0)`, `sizeDelta (80,600)`) contains a hand-built vertical `Slider` (`ZoomSlider`, no existing vertical slider in this project to copy — `SoundVolumeSliderUI`'s is horizontal) plus "+"/"−" `Text` labels above/below, mirroring Unity's default Slider template onto the vertical axis: `Background`/`Fill Area→Fill` inset to a thin centered band (`anchorMin/Max x: 0.35–0.65`), `Handle Slide Area→Handle` spanning the full width inset top/bottom by the handle radius. `Fill`'s `anchorMin/Max = (0,0)–(1,0)` (point-anchored on the fill axis, full-stretched on the cross axis) is what `Slider.cs` itself repositions every value change by moving `anchorMax.y`.
- **Gotcha:** setting a stretched (`anchorMin ≠ anchorMax`) child's `offsetMin`/`offsetMax` and a point-anchored (`anchorMin == anchorMax` on an axis) child's `sizeDelta` in the *same* property-set call risks the two representations (offset-pair vs. size+position) fighting over which wins depending on evaluation order, collapsing the rect. Set a point-anchored axis using only `anchorMin`/`anchorMax`/`pivot`/`sizeDelta`/`anchoredPosition`, never mixing in `offsetMin`/`offsetMax` for that axis.

### BO. Character Physical Separation: No-Overlap Foundation for Player/Soldier/Monster (prerequisite for the 7-unit-type system below)
`Assets/02. Script/Character/CharacterSeparation.cs` — phase 0 of a larger planned feature (7 monster unit types — Infantry/Archer/Cavalry/Knight/Spearman/MountedArcher/Siege — each with unique combat mechanics, later applied to player soldiers too). Every later mechanic (charge collisions, knockback, a shield physically blocking what's behind it) depends on characters occupying distinct space instead of freely overlapping.
- **Why characters overlap despite having colliders:** `Character.CharacterMover.Tick` moves every character via direct `transform.position = Vector3.MoveTowards(...)`, completely bypassing Unity's 2D physics engine. Every character (`Player`, `Soldier`/`Soldier_Ranged`, all `Monster*` tiers) has a `CircleCollider2D` *and* a `Rigidbody2D`, but every `Rigidbody2D` is `Kinematic` — Kinematic bodies are never pushed by physics collision response no matter how their colliders overlap, so the existing colliders/rigidbodies are only load-bearing for `Physics2D.OverlapCircleAll`-based *detection* (targeting scans, hit detection) elsewhere in this project, never for physical collision response.
- **Deliberately did not migrate movement onto Rigidbody2D/Dynamic bodies** to get "free" physics-based collision response — that would require rewriting `CharacterMover` and every system that reads/writes `CharacterMover.Target`/`transform.position` directly (`EnemyTracker`, `MonsterTargetSelector`, `RallyMoveReceiver`, `SoldierBehaviorController`'s kiting, `PlayerManualMover`, offline/online — dozens of already-working call sites) around Rigidbody2D's `FixedUpdate`-timed physics step instead of this project's `GameTicker`/`ITickable` `Update`-timed step, a much larger and riskier rewrite for a project with no physics-driven movement anywhere today. Instead, `CharacterSeparation` is a **fully independent, additive `ITickable`** — it doesn't touch `CharacterMover` at all, doesn't know about targets/AI, and just nudges `transform.position` by a small correction each tick if it's overlapping another `CharacterSeparation`-bearing character, layered on top of whatever `CharacterMover` (or anything else) already did to the position that frame.
- `CharacterSeparation.BodyRadius` (public) reads `CircleCollider2D.radius × transform.lossyScale.x` once in `OnEnable` (re-read on every pool reuse, matching the established "recompute on every `OnEnable`, pooling-safe" idiom from `Soldier.SoldierStatReceiver`/`Character.StageMonsterScaler`) — reuses the collider each prefab already has instead of introducing a second, potentially-inconsistent "body size" number, and automatically picks up `Monster_Elite`/`Monster_Boss`'s 1.2×/1.5× visual scale (section X) without any special-casing.
- No layer filtering at all — `Physics2D.OverlapCircleAll(position, bodyRadius × 2)` queries every layer, and any hit is treated as "another character to separate from" purely by checking `TryGetComponent<CharacterSeparation>()`, regardless of which side it's on (Player/Soldier share the `Player` layer, Monster tiers use `Monster`) — matches the explicit ask ("병사와 플레이어, 적들에게" — soldiers, player, and enemies all mutually block each other) without needing per-prefab layer mask configuration that could be misconfigured.
- Attached to `Player` (scene GameObject) and all 7 character prefabs — `Monster`/`Monster_Elite`/`Monster_Boss`/`Monster_GoldDungeon`/`WarBoss`/`Boss_TrainingDummy`/`Soldier`/`Soldier_Ranged` — via `manage_prefabs(modify_contents, components_to_add)`. `Boss_TrainingDummy` included even though section BF removed its `CharacterMover`/targeting (it never moves) — it should still physically block others from walking through it, and `CharacterSeparation` has no dependency on `CharacterMover` so this works with zero extra wiring.
- **Gotcha (Edit Mode testing only, not a runtime concern):** Unity's 2D physics broadphase only syncs a `Collider2D`'s world position with its `Transform` during an actual physics step (`FixedUpdate`, continuous in Play Mode) — in Edit Mode, setting `transform.position` directly does *not* update what `Physics2D.OverlapCircleAll` sees until `Physics2D.SyncTransforms()` is called. Real gameplay runs a physics step every frame regardless, so this only matters for scripted Edit-Mode tests that move colliders and immediately query overlaps.
- Unit types themselves (`RangedKiter`, `CavalryCharge`+knockback, `DamageReduction` stat, shield-formation for Spearman, orbit-kite for MountedArcher, `SplashAttackBehavior` for Siege) and AI-generated sprites are out of scope for this step — see sections BP onward.

### BP. Unit Type Phase 1: Archer + Mounted Archer (ranged kiting/orbiting)
`Assets/02. Script/Combat/IMonsterMovementInitializer.cs`/`KiteRetreatCalculator.cs`/`RangedKiter.cs`/`OrbitKiter.cs` + `MonsterTargetSelector.cs`/`Stage/MonsterSpawner.cs` — the first two of the seven planned unit types (section BO's roadmap). Both reuse the existing `RangedAttackBehavior`/`Projectile` for actually shooting (no new attack code) — their "unique mechanic" is entirely about *where they stand*, not how they deal damage.
- **`Combat.IMonsterMovementInitializer`** (new interface, `void Initialize(Transform playerTransform)`) — `MonsterTargetSelector` now implements it (trivial, zero logic change) alongside `RangedKiter`/`OrbitKiter`, and `MonsterSpawner.SpawnOne` was generalized from a concrete `TryGetComponent<MonsterTargetSelector>` lookup to `TryGetComponent<IMonsterMovementInitializer>` — since exactly one of these three ever sits on a given monster prefab (mutually exclusive movement drivers), the spawner no longer needs to know which concrete type it is. This is what let the two new prefabs work without touching `MonsterSpawner`'s per-type logic further.
- **`Combat.KiteRetreatCalculator`** (new static class) — the "try 5 candidate angles (0/±45/±90°) opposite the threat, keep the one that stays on-screen and maximizes distance from the threat" math was *extracted* from `Soldier.SoldierBehaviorController.TryFindKiteRetreatPoint` (section W) into a pure, reusable function, rather than copy-pasted — `SoldierBehaviorController` itself was **not** refactored to call it yet (out of scope, don't touch working code without being asked), but now both the existing Soldier kiting and this new Monster kiting share one proven algorithm, which matters once unit types get applied to soldiers later (the explicit long-term goal stated at the start of this whole feature).
- **`Combat.RangedKiter`** (Archer) — replaces `MonsterTargetSelector` entirely on this prefab (not layered alongside it). Every retarget: if the nearest threat is farther than `kiteTriggerDistance`(2), approach it with `StoppingDistance = AttackRange` (identical shape to `MonsterTargetSelector`'s own approach logic); if closer, call `KiteRetreatCalculator` and flee to the returned point, or hold position (`Target = null`) if cornered (no on-screen retreat candidate) — same "hold rather than force off-screen" fallback `SoldierBehaviorController` already established.
- **`Combat.OrbitKiter`** (Mounted Archer) — the "말은 180도로 급선회할 수 없다" requirement: instead of retreating directly away, it continuously parametrically orbits the threat — `orbitAngleDegrees` accumulates by `orbitAngularSpeedDegrees × Δt` every retarget, and the chase target is always `threatPosition + orbitRadius × (cos, sin)(angle)`, a point that itself keeps moving. No explicit "flee" logic exists at all — a fast-enough `MoveSpeed` (this unit type's whole design point per the user) is what makes the chased point actually trace a circle rather than the unit just slowly drifting toward wherever the point currently is. Start angle is randomized per-spawn (`Random.Range(0,360)` in `OnEnable`) so multiple mounted archers don't all orbit in lockstep.
- Content: `MonsterStats_Archer.asset`(HP 25/ATK 7/Range 6/Speed 1.3/Interval 1.2) and `MonsterStats_MountedArcher.asset`(HP 30/ATK 7/Range 5.5/Speed 2.5/Interval 1.2) — placeholder pacing numbers, same spirit as every other stat asset in this project (section V/AL), meant for later tuning. `Monster_Archer.prefab`/`Monster_MountedArcher.prefab` built by duplicating `Monster.prefab` (inherits `CharacterSeparation` from section BO automatically) via `manage_prefabs(duplicate)`, then swapping `MeleeAttackBehavior`+`MonsterTargetSelector` → `RangedAttackBehavior`+`RangedKiter`/`OrbitKiter` and rewiring `baseStats`/`projectilePrefab`(`Projectile.prefab`)/`allyLayerMask`(`Player` layer, bit `256`, read from the original `Monster.prefab`'s `MonsterTargetSelector` to match exactly). Sprites (still the shared placeholder body/weapon art) and stage spawn-table wiring are both explicitly **not** done this session — per this project's established "mechanism now, content later" convention (section BC's `MonsterVisualSetSO` is the precedent), these two prefabs exist and work but nothing in the actual stage catalog spawns them yet.
- **Gotcha:** any test involving `CameraVisibility.IsOnScreen` (e.g. `KiteRetreatCalculator`) must position test objects within `Camera.main`'s actual view — "on-screen" is relative to the real camera transform/orthographic size, unlike pure `Physics2D` overlap tests which are camera-independent.

### BQ. Unit Type Phase 2: Cavalry Charge with Speed-Dependent Handling + Generic Knockback
`Assets/02. Script/Combat/CavalryCharge.cs`/`Character/KnockbackReceiver.cs` — the third planned unit type. Unlike Archer/MountedArcher (section BP, pure repositioning on top of the existing `RangedAttackBehavior`), Cavalry needed new impact/damage logic: retreat → straight charge → knockback, with steering still possible mid-charge (if the target dodges) but handling that degrades the faster the charge is going.
- **State machine** (`Positioning` ↔ `Charging`, replaces `MonsterTargetSelector` entirely, same "one movement-driving component per monster" convention as section BP): in `Positioning`, reuses `KiteRetreatCalculator`(section BP) to back away until `chargeStartDistance`(5) is reached, then locks in the threat's *current* position as the initial charge direction and switches to `Charging`. During `Charging`, `CharacterMover` is bypassed entirely (`_mover.Target = null`) — the component drives `transform.position` directly every tick for precise control over acceleration and steering, something `CharacterMover`'s simple `MoveTowards` couldn't express.
- **Acceleration:** `_chargeSpeed` grows by `chargeAcceleration`(4/s) every tick, capped at `maxChargeSpeed`(9), starting from `chargeStartSpeed`(3).
- **Speed-dependent steering:** every tick, the ideal direction to the threat's *live* (possibly moved) position is computed, and `_chargeDirection` is rotated toward it via `Vector3.RotateTowards` — but the maximum rotation allowed this tick is `turnRateDegreesPerSecond = max(minTurnRateDegreesPerSecond(20), baseTurnRateDegreesPerSecond(180) − turnRatePenaltyPerSpeed(25) × (currentSpeed − chargeStartSpeed))`. At the charge's starting speed this is a full 180°/s (nearly instant lock-on); by `maxChargeSpeed` it's down to 30°/s — never dropping below the 20°/s floor.
- **Impact:** each `Charging` tick also runs `Physics2D.OverlapCircleAll(position, bodyRadius + hitCheckReach, allyLayerMask)` (`bodyRadius` read from `CharacterSeparation.BodyRadius`, section BO — same body-size source as the no-overlap system, no second number introduced) — every live `Health` caught is dealt `Stats.AttackPower + (currentSpeed − chargeStartSpeed) × bonusDamagePerSpeed` via a **direct `Health.TakeDamage` call**, bypassing the normal `Attacker`/`IAttackBehavior` cadence entirely (same reasoning as `War.Boss.WarBossPatternRunner`'s AoE, section AG: this is a special one-off impact, not a periodic attack). A hit ends the charge immediately (back to `Positioning`); no hit within `maxChargeDuration`(3s) also ends it (overrun case, prevents an infinite off-screen chase). Regular melee (`Attacker`+`MeleeAttackBehavior`, kept on this prefab unlike Archer/MountedArcher) still functions independently the whole time, for the case where something is adjacent without an active charge.
- **`Character.KnockbackReceiver`** (new, generic — attached to `Player`, `Soldier`, `Soldier_Ranged`, and `Monster_Cavalry` itself for symmetry/future-proofing, *not* the other monster tiers yet since nothing currently targets them with an effect like this) — `ApplyKnockback(direction, distance, duration)` disables the target's own movement-driving components (`componentsToSuspend`, copied field-for-field from each prefab's existing `RallyMoveReceiver` config — `[SoldierBehaviorController, EnemyTracker]` for Soldiers, `[EnemyTracker]` for Player, `[CavalryCharge]` for Cavalry itself) plus `CharacterMover` itself, then moves `transform.position` directly at `distance/duration` units/sec for `duration` seconds — deliberately **not** using `CharacterMover`'s own `Stats.MoveSpeed` (a knockback should feel like a fixed external impact, not scale with how fast the *victim* normally walks). Same "revert cleanly when done, don't leave suspended forever" shape as `RallyMoveReceiver`/`RangedKiter`.
- Content: `MonsterStats_Cavalry.asset`(HP 45/ATK 9/Range 2.5/Speed 2.2/Interval 1) and `Monster_Cavalry.prefab` (duplicated from `Monster.prefab`, `MonsterTargetSelector` → `CavalryCharge`, `MeleeAttackBehavior`/`Attacker` kept as-is). Same "mechanism now, stage spawn tables later" scope as section BP.
- **Gotcha (Edit Mode test-harness debris, not a code bug):** orphaned `GameObject`s left behind by earlier interrupted/failed `execute_code` test attempts (from this or an unrelated earlier session) can sit in the scene indefinitely and get picked up by a broad `LayerMask`/`OverlapCircleAll` scan in a *later* unrelated test, causing confusing failures (e.g. a `Health` component whose fields were never reflection-populated because the test that created it threw before its own cleanup ran). Always enumerate `FindObjectsByType<GameObject>` and destroy stray `Test*`/`Debug*`-named objects before trusting a scan-based test result, and wrap test code in `try/finally` so aborted attempts can't leave debris behind. Separately: constructing a "match every layer" `LayerMask` via `new LayerMask()` + reflection on `m_Bits` silently produces an empty mask (mutating a boxed copy of a value type) — use the direct implicit conversion `LayerMask mask = ~0;` instead.

### BR. Unit Type Phase 3: Knight Flat Damage Reduction
`Assets/02. Script/Character/CharacterStatsSO.cs`/`RuntimeStats.cs`/`Health.cs` — the fourth planned unit type; no new behavior component, simpler than Cavalry.
- **Design choice:** damage reduction is a **flat per-hit reduction** ("방어력 수치 자체보다는 피해를 일정량 감소해서 받는 방향"), not a percentage/defense-stat multiplier. `CharacterStatsSO`/`RuntimeStats` gained `DamageReduction` (shared stat, default `0`, same "sparse opt-in, zero effect on everything else" idiom as `EnhancementConfigSO.HasUnlockRequirement`/`SkillSO.ShakeCamera`).
- `Character.Health.TakeDamage` now computes `mitigatedAmount = Mathf.Max(0, amount - Stats.DamageReduction)` before applying it — a hit smaller than the reduction is fully negated (no health change, no `DamageAppliedEvent`, treated identically to the pre-existing `amount <= 0f` no-op case) rather than ever dealing negative/healing damage. This is the **only other touchpoint into the shared `Health` class** besides `CriticalChance`/`CriticalDamageMultiplier` (section AC) — it applies to Player and Soldiers too the moment either ever gets a non-zero `DamageReduction`, which is exactly the stated long-term goal (apply unit types to soldiers later) rather than an accident of scope.
- Also per explicit request: Knight's `MoveSpeed`(1.2) is slightly *below* Infantry's(1.5) — the "heavy armor is slower" half of the tradeoff.
- Content: `MonsterStats_Knight.asset`(HP 50/ATK 8/Range 2.5/Speed 1.2/Interval 1/**DamageReduction 3**) and `Monster_Knight.prefab` — duplicated from `Monster.prefab` with **zero component changes**, only `CharacterStatsProvider.baseStats` repointed. Unlike every other unit type phase so far (Archer/MountedArcher/Cavalry all swapped out `MonsterTargetSelector` and/or the attack behavior), Knight keeps the exact same `MonsterTargetSelector`+`Attacker`+`MeleeAttackBehavior` composition as plain Infantry — its entire identity lives in the stats asset.
### BS. Unit Type Phase 4: Spearman + Shield-Bearer Formation
`Assets/02. Script/Character/ShieldGuard.cs` + `Health.cs` + `Assets/02. Script/Combat/FormationFollower.cs` — the fifth planned unit type, and the first to introduce a genuine two-unit relationship (a Shield-Bearer that soaks hits, and a Spearman that hides behind it) rather than a single self-contained monster.
- **`Character.ShieldGuard`** (attached to `Monster_ShieldBearer.prefab` only) — a second, independent HP pool (`maxShieldHealth`, default 25) that `Health.TakeDamage` checks for and delegates to first. `AbsorbDamage(amount)` absorbs up to its remaining shield HP and returns the unabsorbed overflow, which `Health.TakeDamage` applies to the shield-bearer's *own* body. The shield protects only its own wearer — it never forwards damage to any other unit (shield-bearer and spearman are separate entities that don't share damage). No damage-source filtering exists (melee, ranged, charge impact — anything routed through `Health.TakeDamage` is absorbed identically).
- **`Character.Health.TakeDamage`** has a `_shieldGuard` field (`GetComponent<ShieldGuard>()` in `Awake`, `null` for every character type except Shield-Bearer — same "optional sibling component, absent everywhere else" shape `CavalryCharge`/`KnockbackReceiver` established). Order: `DamageReduction` flat mitigation (section BR) first, then `ShieldGuard` absorption if present and still up, then whatever's left lands on the unit's own health — each stage can fully negate the hit (return early, no event) if it reaches 0.
- **`Combat.FormationFollower`** (Spearman's movement driver, replaces `MonsterTargetSelector` entirely) — `SetLeader(Transform)` assigns which Shield-Bearer to hide behind (no automatic pairing/formation-spawn system exists — see section BU for that). Every retarget, if a leader is assigned: finds the nearest threat *from the leader's position* (not the spearman's own), then sets its follow-anchor to `leaderPosition + normalize(leaderPosition − threatPosition) × followDistance(1.5)` — directly behind the leader, opposite the threat, so the leader's body stays between the spearman and whatever it's fighting. Protection here is purely positional — a fast unit can still flank around the leader and reach the spearman directly. If no leader is assigned, falls back to approaching the threat directly like a plain monster.
- **Range math (deliberate, not incidental):** `MonsterStats_Spearman.asset`'s `AttackRange = 4` was chosen as `ShieldBearer's AttackRange(2.5) + followDistance(1.5)` — exactly far enough that, standing at the follow anchor, the spear still reaches past the shield-bearer to the same threat the shield-bearer itself is fighting. The Spearman's own `Attacker`/`MeleeAttackBehavior` needed no changes for this — it already independently scans its own `AttackRange` every attack interval, same as any other melee unit; `FormationFollower` only decides *where the Spearman stands*, never who it attacks.
- Content: `MonsterStats_ShieldBearer.asset`(HP 40/ATK 8/Range 2.5/Speed 1.0/Interval 1/DamageReduction 0) and `MonsterStats_Spearman.asset`(HP 35/ATK 10/Range 4/Speed 1.3/Interval 1.1/DamageReduction 0). `Monster_ShieldBearer.prefab` (duplicated from `Monster.prefab`, kept the normal `MonsterTargetSelector`+`Attacker`+`MeleeAttackBehavior` Infantry composition, added `ShieldGuard`) and `Monster_Spearman.prefab` (duplicated from `Monster.prefab`, `MonsterTargetSelector` → `FormationFollower`, `allyLayerMask` wired to the `Player` layer bit `256`).

### BT. Unit Type Phase 5: Siege Splash Attack (completes the 7-unit-type roadmap from section BO)
`Assets/02. Script/Combat/SplashAttackBehavior.cs` — the sixth and final planned unit type. Unlike Spearman/Shield-Bearer (section BS, a two-unit relationship) or Cavalry (section BQ, a state machine), Siege needed only a new *attack strategy* — its slowness is expressed purely via stat values (`moveSpeed`/`attackInterval`) on the existing `MonsterTargetSelector`+`Attacker` composition; this component only decides how splash damage spreads once an attack lands.
- **`Combat.SplashAttackBehavior`** (new, `IAttackBehavior`, mirrors `MeleeAttackBehavior`'s shape) — `Execute(origin, target, damage, isCritical)`는 먼저 정타 대상에게 `damage`를 그대로 적용한 뒤(`Attacker`가 이미 계산해 넘긴, 치명타 배율까지 반영된 최종값 — section AK의 관례 그대로), `target.transform.position`을 중심으로 `splashRadius`(2.5) 안의 다른 대상들에게 `damage × splashDamageMultiplier`(0.5)만큼 추가 피해를 준다. `Physics2D.OverlapCircleAll` + `TryGetComponent<Health>` 스캔은 `Skill.Effects.AreaDamageSkillEffect`(section AS)가 이미 쓰던 것과 정확히 같은 패턴을 재사용했다. 정타 대상 자신은 `hitHealth != target` 체크로 스플래시 스캔에서 제외되어(같은 공격에 이중으로 맞지 않도록) 오직 *주변의 다른* 대상만 스플래시를 받는다. 마지막으로 기존 `weaponSwing`도 재생 — Melee와 동일하게 시각 효과는 순수 코스메틱이며 판정을 막지 않는다.
- **레이어 마스크는 별도 필드:** `Attacker.targetLayerMask`는 `private`이라 재사용할 수 없으므로(프로젝트 관례상 각 컴포넌트가 자기 몫의 `LayerMask` 필드를 따로 갖는 것과 동일 — `RangedKiter`/`OrbitKiter`의 `allyLayerMask`도 같은 이유로 별도 필드다), `splashLayerMask`를 새 필드로 두고 `Monster_Siege.prefab`에서 `Attacker.targetLayerMask`와 같은 값(`Player` 레이어, 비트 `256`)으로 맞춰 배치했다.
- Content: `MonsterStats_Siege.asset`(HP 75/ATK 16/Range 3/Speed **0.6**/Interval **1.8**/**DamageReduction 4**) — "매우 느린 속도 + 일정 피해감소 + 높은 체력 + 강력한 데미지"라는 요청을 그대로 수치화한 것(플레인 Infantry의 `MoveSpeed`(1.5) 대비 40%, `AttackInterval`(1)의 1.8배로 느리게, `MaxHealth`(40) 대비 거의 2배, `AttackPower`(8)의 2배). `Monster_Siege.prefab`은 `Monster.prefab`을 복제해 `MeleeAttackBehavior` → `SplashAttackBehavior`로 교체하고 `MonsterTargetSelector`/`Attacker`/`CharacterSeparation`(section BO) 등 나머지 구성은 그대로 유지했다 — 이동/타게팅 방식 자체는 평범한 보병과 동일하고, 오직 "느림 + 광역 강타"만 다르다.

### BU. Formation Tactics: Shield Wall with Dynamic Casualty Rebalancing
`Assets/02. Script/Stage/Tactics/` + `TacticType.cs`/`TacticSpawnEntry.cs` + `StageSO.cs`/`MonsterSpawner.cs`/`StageController.cs` + `Combat/GuardPositioner.cs` — the first "전술(병법)" system, wiring `FormationFollower.SetLeader` (section BS) to real spawn-time pairing. `MonsterSpawnEntry`(프리팹 1종 × N마리, section G)와는 별개의 새 스폰 개념 — 리더/추종자 두 프리팹을 쌍으로 묶어 스폰하고, 이후 생존 상태에 따라 스스로 재배정하는 "대형(Formation)"을 도입했다.
- **확장 포인트:** `Stage.TacticType`(enum, 현재 `ShieldWall` 하나) + `Stage.Tactics.ITacticSpawnStrategy`(리더/추종자 인스턴스 목록을 받아 `ITacticFormationGroup`을 만든다) + `Stage.Tactics.ITacticFormationGroup`(`IDisposable`, 생성 시점에 스스로 `CharacterDiedEvent`를 구독해 재배정하는 자기완결형 객체) — `Skill.SkillEffectType`→`ISkillEffect`(section AH)와 같은 "enum이 전략 구현체를 가리키는" 디스패치 관례. `MonsterSpawner`는 `Dictionary<TacticType, ITacticSpawnStrategy>` 하나로 전략을 찾을 뿐, 새 전술이 추가돼도 스폰 루프 자체는 손댈 필요가 없다.
- **`Stage.TacticSpawnEntry`**(`[Serializable]`, `MonsterSpawnEntry`와 같은 급의 평범한 데이터 행) — `Type`/`LeaderPrefab`/`FollowerPrefab`/`PairCount`/`SpawnInterval`(+ `AlternateFollowerPrefab`/`AlternateFollowerChance`, 아래). `StageSO`에 `SpawnEntries`와 나란히 `TacticEntries` 배열로 추가.
- **`MonsterSpawner` 웨이브 순서:** 스테이지 입장 시 **전술 웨이브(대형)를 먼저** 처리하고, 그게 끝난 뒤 일반 웨이브(엘리트/보스 포함)로 넘어간다 — 대형이 즉시 갖춰지도록. 대형이 아직 살아 움직이는 동안엔(스폰만 끝났어도 완전히 전멸하기 전까지는) 다음 웨이브로 넘어가지 않는다(`ITacticFormationGroup.IsCleared`/`MonsterSpawner.AllFormationGroupsCleared()`) — 엘리트/보스가 아직 살아있는 대형과 같은 전장에서 뒤섞이는 것을 막는다. 실제 인스턴스 생성 로직(`_pool.Get` → `StageMonsterScaler.ApplyScale` → `IMonsterMovementInitializer.Initialize` → `MonsterVisualRandomizer.ApplyVisualSet` → `_tracker.RegisterSpawned`)은 `SpawnInstance(prefab, visualSet)`로 추출해 일반 웨이브와 전술 쌍 스폰 양쪽에서 재사용.
- **대형 스폰 좌표:** 리더/추종자를 스폰 지점 배열을 순환 재사용하는 대신, 전술 엔트리가 시작될 때(사이드 상/하단 한 번만 고정) 리더 줄/추종자 줄의 좌표를 미리 통째로 계산한다(`MonsterSpawner.PrepareFormationLayout`) — 앵커를 중심으로 `unitSpacing`(기본 1.5) 간격의 한 줄에 리더를, 그보다 `rowSpacing`(기본 2)만큼 더 화면 밖(플레이어 반대 방향)으로 물러난 평행한 줄에 추종자를 배치한다. 이렇게 해야 다수의 쌍이 몇 안 되는 스폰 지점에 몰려 뭉치지 않는다. `SpawnInstance`는 `Vector3? explicitPosition`을 받아(일반 웨이브는 `null`, 기존 스폰 지점 순환 그대로) 이 좌표를 직접 받는다. `unitSpacing`/`rowSpacing`은 `StageController`의 `[SerializeField]`(매직 넘버 금지 원칙).
- **`Stage.Tactics.ShieldWallFormationGroup`** — 생성 시점에 방패병/창병 리스트를 받아 `Rebalance()`를 한 번 돌리고(이상적 1:1 배치), 이후 `CharacterDiedEvent`를 받을 때마다 죽은 유닛을 자기 리스트에서 제거하고 `Rebalance()`를 통째로 재실행한다(부분 diff 없이 매번 생존자만으로 처음부터 다시 계산 — `StageMonsterScaler.ApplyScale`과 같은 "매번 깨끗하게 재계산" 관례). 규칙: 방패병 수(S)와 창병 수(P) 중 작은 쪽만큼 1:1 페어를 만들고 —
  - `S > P`: 남는 방패병은 순환 배정(`(i-pairCount) % P`)으로 기존 페어의 창병 중 하나를 **위치상으로만** 추가 보호 — `MonsterTargetSelector`를 끄고 `GuardPositioner`(아래)를 켜서 그 창병과 가장 가까운 위협을 잇는 선 위에 자리 잡게 한다(데미지는 공유하지 않는다 — 방패병과 창병은 서로 다른 개체이므로, 방패가 깨지면 넘친 피해는 방패병 자기 몸에만 적용된다). `P == 0`이면(창병 전멸) 남는 방패병은 전부 평범한 동작(`MonsterTargetSelector` 켬, `GuardPositioner` 끔)으로 복귀.
  - `P > S`: 남는 창병은 `FormationFollower.SetLeader(null)` — `FormationFollower`의 "리더 없음 ⇒ 직접 접근(혼자 싸움)" 대체 동작이 그대로 적용된다.
  - 양쪽 리스트가 모두 비면(전멸) `Dispose()`로 스스로 구독을 해제한다.
- **`Character.ShieldGuard`** — `AbsorbDamage`는 오직 자기 자신(호출한 `Health.TakeDamage`)에게만 overflow를 반환하며, 다른 유닛에게 피해를 전달하는 코드는 없다. 창병의 "보호"는 순전히 위치 메커니즘(`Combat.FormationFollower`가 방패병 뒤에 서기, `Combat.GuardPositioner`가 여분 방패병을 위협-창병 사이에 끼워 넣기)에서만 나온다 — 빠른 유닛이 우회해 창병을 직접 노리거나, 창병이 먼저 표적이 되는 것도 자연스러운 결과로 허용된다.
- **`Combat.GuardPositioner`**(`FormationFollower`의 반대 버전) — `FormationFollower`가 "보호 대상 뒤(위협 반대쪽)"에 숨는다면, 이건 "보호 대상과 가장 가까운 위협을 잇는 선 위, 보호 대상 쪽에서 `guardDistance`만큼 떨어진 지점"에 선다 — 위협이 오는 길목에 실제로 끼어든다. 스폰 시점엔 이 유닛이 "여분"이 될지 알 수 없으므로 `IMonsterMovementInitializer`는 구현하지 않는다 — `MonsterTargetSelector`와 같은 GameObject에 있는 채로 `TryGetComponent<IMonsterMovementInitializer>`가 모호해지는 걸 피하기 위해서다. 평소엔 `enabled=false`로 비활성 상태로 두고, `ShieldWallFormationGroup.Rebalance()`가 여분 방패병에게만 명시적으로 켠다.
- **창병 자리에 궁병이 대신 들어가는 경우:** `TacticSpawnEntry.AlternateFollowerPrefab`/`AlternateFollowerChance`(0~1) — `MonsterSpawner.SpawnPair`가 2열 자리를 스폰할 때마다 `Random.value < AlternateFollowerChance`를 굴려 `FollowerPrefab`(창병) 대신 `AlternateFollowerPrefab`을 쓸지 결정한다. 궁병도 방패 뒤에 숨을 수 있도록 `Monster_Archer.prefab`에 `Combat.FormationFollower`를 추가했다(평소엔 `enabled=false`, 기존 `RangedKiter`가 기본 이동 방식) — `MonsterSpawner.ConfigureAsFormationFollower(instance)`가 2열로 스폰된 인스턴스마다 `RangedKiter`를 끄고 `FormationFollower`를 켜고 `Initialize(playerTarget)`을 직접 호출한다(창병에겐 `RangedKiter`가 없으므로 이 메서드는 no-op으로 안전하게 통과).
  - **모호성 문제:** 궁병이 `RangedKiter`와 `FormationFollower`를 동시에 갖게 되면서, 둘 다 `IMonsterMovementInitializer`를 구현하면 `MonsterSpawner.SpawnInstance`의 범용 `TryGetComponent<IMonsterMovementInitializer>` 자동 초기화가 어느 쪽을 찾을지 불확실해진다(`GuardPositioner`를 이 인터페이스에서 제외한 것과 같은 함정). `Combat.FormationFollower`는 `IMonsterMovementInitializer`를 구현하지 않고(공개 `Initialize` 메서드는 유지), 대신 `MonsterSpawner.SpawnPair`가 대형 편입 시점에 명시적으로 직접 호출한다 — 창병도 이제 이 명시적 경로로만 초기화된다.
- **누수 방지:** `ShieldWallFormationGroup`은 생성 즉시 `EventBus`를 구독하는데, 스테이지가 대형이 다 죽기 전에 강제로 끝나면(플레이어 사망/스테이지 전환) 남은 대형원들은 `StageProgressTracker.ReleaseRemaining`으로 **죽지 않고** 풀에 강제 반환되므로(section G) `CharacterDiedEvent`가 안 뜨고, 그룹의 구독이 영원히 안 풀리는 누수가 생긴다. `MonsterSpawner`가 자신이 만든 `ITacticFormationGroup`들을 리스트로 들고 있다가 `Dispose()`에서 전부 강제 해제하고, `StageController.EndCurrentStage()`가 `_spawner.Dispose()`를 호출한다(`_tracker.Dispose()`를 이미 호출하던 바로 옆).
- **풀 등록 함정:** `StageController.LoadStage`는 `stage.SpawnEntries`뿐 아니라 `stage.TacticEntries`의 `LeaderPrefab`/`FollowerPrefab`/`AlternateFollowerPrefab`도 전부 `PoolManager.EnsurePool`해야 한다 — 빠뜨리면 `PoolManager.Get`이 등록되지 않은 프리팹에 `InvalidOperationException`을 던진다.

### BW. Shield Wall Formation Content: Total-Count Sizing, Archer Substitution
`Assets/03. SO/Stages/Stage_*_33~40.asset`(16개) — `s=33~40` 방패벽 태그 스테이지의 실제 콘텐츠 값.
