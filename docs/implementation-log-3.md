### AP. Monster Weapon Swing Visual (implemented — fills a gap left by section X)
`Assets/04. Prefab/Monster.prefab` + `Monster_Elite.prefab` + `Monster_Boss.prefab` — pure prefab content, no new code. Section X gave monsters the same `Attacker`+`MeleeAttackBehavior` composition Player/Soldier use, but never gave them the `WeaponAnchor`(→`WeaponSwing`+weapon sprite child) that `MeleeAttackBehavior.weaponSwing` points at — so the reference was always null and `Execute()`'s `if (weaponSwing != null) weaponSwing.Play();` silently no-opped on every monster attack. Fixed by adding the exact same child structure Player/Soldier already have (`WeaponAnchor` at local `(0.6,0,0)` with `WeaponSwing`, default `swingAngle=90`/`swingDuration=0.2`; child `WeaponVisual` at local `(0.5,0,0)` with a `SpriteRenderer` reusing `Assets/01. Sprite/WeaponSprite.png`, `sortingOrder=1`) to all three monster tiers, and wiring each prefab's `MeleeAttackBehavior.weaponSwing` to it. `Monster_Elite`/`Monster_Boss`'s 1.2x/1.5x root `localScale` (section X) scales the weapon anchor along with the body automatically since it's a plain child — unlike `HealthBar`, no counter-scaling needed here. Verified in Play Mode: `weaponSwing` field non-null on every spawned monster; manually ticking a monster's `WeaponSwing` confirmed the same sine-eased rotation (peaks at 90° at the swing's midpoint, resets and unregisters from `GameTicker` on finish) Player/Soldier already use.
- **Gotcha fixed (found via this section's own testing):** `GameTicker.Unregister` called *during* iteration only queues into `_pendingRemove` and applies it after the current frame's loop finishes (by design, so it's safe to unregister mid-iteration — see section C). If a character dies mid-swing, `WeaponSwing.OnDisable()` → `FinishSwing()` correctly resets rotation to rest and calls `Unregister`, but since that call lands *during* the very frame's iteration, the same still-in-`_tickables` `WeaponSwing` can receive one more `Tick()` before `ApplyPendingChanges()` actually removes it — and `Tick()` had no guard, so it recomputed from the stale (never-reset) `_elapsed` and silently overwrote the just-reset rotation with a mid-swing angle, frozen forever on a GameObject that's already inactive (no `OnEnable` exists to re-fix it on the next pool reuse) — exactly the "died mid-swing → respawns with the weapon facing wrong" bug reported for monsters after this section shipped. Fixed with a one-line guard, `if (!_isSwinging) return;`, at the top of `WeaponSwing.Tick()`; `FinishSwing()` already sets `_isSwinging = false` before the stale tick would land, so the guard closes the gap without touching `GameTicker`'s (intentionally-shared) deferred-removal design. Reproduced and verified via direct `ITickable.Tick()` calls bracketing a real `Health.TakeDamage` death, both before the fix (rotation snapped back to a stale angle after death) and after (stayed at rest).

### AQ. Skill Loadout System: 6 Equip Slots, Active/Passive Tabs, Cooldown HUD (implemented — supersedes the "fixed 3-slot loadout" note in section AH)
`Assets/02. Script/Skill/` + `Assets/02. Script/UI/` — replaces the old "3 skills, always active once leveled" design with a proper equip system: leveling (permanent, gold+stones) and equipping (free, freely swappable, 6 slots) are now fully separate concepts, mirroring Equipment's own "보유 vs 장착" split.
- `Skill.SkillEffectType` (new enum: `AreaDamage`/`SingleTargetStrike`/`SelfBuff`) + `SkillSO.EffectType` (new field) — lets a generic cast slot resolve *which* of several effect strategies to run for whatever skill happens to be equipped there, instead of a skill being permanently bound to one fixed GameObject+component pair.
- `Skill.SkillLoadoutService` (new, `IManager`/`IService`) — 6 slots (`SlotCount`), each holding a `SkillSO` or nothing. `TryEquip(slotIndex, definition)` fails if `SkillService.GetLevel(definition) < 1`; if `definition` is already equipped in a *different* slot, that slot is auto-vacated first (prevents duplicate equips, same "auto-vacate old slot" shape as `SoldierDeploymentService.TryAssign`, section Z). `Unequip(slotIndex)`, `FindEquippedSlot(definition)`. Publishes `Skill.Events.SkillLoadoutChangedEvent`. Starts with **all 6 slots empty** by design (no auto-populate from old saves/defaults).
- `Skill.SkillSlot` (rewritten) — no longer holds a fixed `SkillSO`; holds only `slotIndex` and asks `SkillLoadoutService.GetEquipped(slotIndex)` fresh every tick. An empty slot does nothing. Each of the 6 cast-slot GameObjects (`Player/SkillCastSlot_0`‥`5` — the original 3 fixed skill children repurposed + 3 new ones, all renamed off their old skill-specific names) carries **all three** `ISkillEffect` components simultaneously (`AreaDamageSkillEffect`/`SingleTargetStrikeSkillEffect`/`SelfBuffSkillEffect`), cached in `Awake()` into a `Dictionary<SkillEffectType, ISkillEffect>`; the equipped `SkillSO.EffectType` picks which one runs — same "enum → implementation table" shape as `Character.RuntimeStatApplier`. Gained a public `CooldownProgress01` (0~1) for the HUD to read.
  - **Gotcha fixed (found via this section's own testing):** `AreaDamageSkillEffect`/`SingleTargetStrikeSkillEffect` have a `targetLayerMask` (and `SingleTargetStrikeSkillEffect` a `range`) that must point at the Monster layer to hit anything. The *original* 3 GameObjects only ever had **one** of the three effect components each (whichever their one fixed skill used), so that one component was correctly configured in the Inspector — but the other two components freshly `AddComponent`'d onto every slot (to support arbitrary equipping) came in with Unity's default `LayerMask = 0` ("Nothing"), silently matching zero targets. Equipping 강타 (SingleTargetStrike) into a slot that originally held a different skill cast every 6s and hit nothing. Fixed by copying the one properly-authored reference value for each effect type (`radius=3`/`mask=512` for AreaDamage, `range=8`/`mask=512` for SingleTargetStrike, `duration=5` for SelfBuff) onto all 6 slots' corresponding components, so every slot behaves identically regardless of which skill ends up equipped there.
- UI (initial pass, then reworked — see the next bullet): `UI.SkillSlotBarUI` shows the 6 **equip slots** (not skills) in one row (shrunk to 140×140, spacing 15, to fit six across — was 200×200/spacing 40 for three).
- **Reworked into an inline slot-style picker (supersedes the popup this section originally shipped with):** tapping an equip slot no longer opens a popup — it just **selects** that slot (`SkillSlotBarUI.SelectedSlotIndex`, shown via a `SelectedHighlight` child Image toggled per slot, gold border). The empty area below the slot bar (`SkillPanel`'s previously-unused middle/bottom) now permanently hosts `UI.SkillGridUI` — every `SkillCatalogSO` entry rendered as an icon grid (`UnityEngine.UI.GridLayoutGroup`, 140×140 cells, inside the standard `ScrollRect → Viewport(RectMask2D) → Content` scrollable-list pattern from section AB) via `UI.SkillGridCellUI` cells. Each cell splits two tap targets the same way `EquipmentRowUI` separates its name button from its equip button: tapping the **icon** equips that skill into `SkillSlotBarUI.SelectedSlotIndex` (a pull, not a push — `SkillGridUI` holds a direct reference to `SkillSlotBarUI` and just reads whatever's currently selected at click time); tapping the small **level badge** in the corner opens the *existing* `UI.SkillDetailPopupUI` for leveling up. `UI.SkillPickerPopupUI`/`UI.SkillPickerRowUI` and `SkillPickerRow.prefab` were deleted entirely — no popup remains in this flow.
- `Canvas/PanelRoot/SkillPanel` gained a `SubTabBar` (액티브/패시브, `BottomMenuUI` with `selectFirstTabByDefault=true`/`allowToggleClose=false` — the same fix from this section's neighbor in AN applied here too) toggling between the (repositioned to the top of the panel, directly under the sub-tab bar) `SkillSlotBar`+`SkillGridUI` and a scriptless `PassiveTabContent` ("패시브 스킬 - 준비 중") placeholder — passives have no system yet, this is purely a reserved slot in the layout per the request.
- `UI.SkillCooldownHudUI` (new) — a persistent row of 6 icon+radial-cooldown-overlay slots (`Canvas/SkillCooldownHud`, positioned directly above `BottomMenu`, **not** inside any tab panel so it's always visible during play, and set as Canvas's **first** sibling so every other popup/panel draws in front of it). Icons refresh only on `SkillLoadoutChangedEvent`; the cooldown overlay (`Image`, `Type=Filled`/`FillMethod=Radial360`, black @ 0.75 alpha) is redrawn every tick from `1 - SkillSlot.CooldownProgress01` (full cover right after casting, drains away as the skill comes off cooldown) via direct `[SerializeField] SkillSlot[] casterSlots` references to `Player`'s 6 cast slots — same "read live gameplay state every frame, judgment lives elsewhere" shape as `HealthBarUI`.
- `UI.EquippedSlotBarUI` (Equipment domain) gained a `skillCooldownHud` reference and `SetActive(false)`/`(true)`s it in its own `OnEnable`/`OnDisable` — the 장비 tab's slot bar and this HUD occupy overlapping screen space, so the HUD hides for exactly as long as the equipment UI is open. A cross-domain UI reference (Equipment component directly toggling a Skill element) but treated as pure screen-layout coordination, same category as `EquippedSlotBarUI` already managing its own child popups' lifecycles.
- Save: one new `SaveData.SkillLoadoutJson` field (array of `{SlotIndex, CatalogIndex}`, empty slots omitted) — a JSON blob like `InventoryJson`/equipment snapshots rather than 6 more flat int fields, since `SaveData`'s constructor was already flagged as growing large (section AM) and this is inherently a small array, not independent scalars.
- Verified in Play Mode end-to-end: equip/duplicate-auto-swap/level-gate-rejection all correct; a slot with an equipped skill actually deals the right (level-scaled) damage to the nearest live target after the LayerMask gotcha fix, an empty slot does nothing; cooldown HUD overlay measured exactly at 1.0 right after cast, 0.5 at half the cooldown, back to 1.0 on the next auto-cast; 액티브/패시브 sub-tab defaults open and doesn't toggle-close; opening/closing the Equipment slot bar correctly hides/restores the cooldown HUD; `PlayerPrefs.Save.SkillLoadoutJson` persists the exact equipped slots. Inline grid rework re-verified separately: selecting a different equip slot moves the highlight and re-targets which slot the grid's icon-tap equips into; tapping a grid cell's level badge opens the level-up popup independently of equipping; screenshot-confirmed layout (sub-tab → slot bar → grid → cooldown HUD, all visible and non-overlapping).

### AR. Skill UI Polish: Slot Border, Icon Aspect Ratio, Fixed Background (implemented — supersedes visual details from section AQ)
- **Gotcha fixed (border covered the whole slot instead of framing it):** `SkillSlotBarUI`'s `SelectedHighlight` child was a plain `Image` with `sprite = null` (solid color fill) sized 8px bigger than the slot on each side, intended to peek out as a border ring. Since children always draw on top of their parent's own graphic in Unity UI (the slot's `Icon` used to live on the *root* GameObject), the solid highlight fully covered the icon whenever a slot was selected instead of framing it. Fixed by assigning Unity's built-in 9-slice sprite (`AssetDatabase.GetBuiltinExtraResource<Sprite>("UI/Skin/Background.psd")`, border 10px) with `Image.Type = Sliced` and `fillCenter = false` — the hollow center lets whatever's drawn earlier (the icon) show through regardless of draw order, so no reparenting was needed.
- **Gotcha fixed (background disappeared once a skill was equipped):** `SkillSlotBarUI`'s `Icon` field pointed at the slot root's *own* `Image`, which doubled as both "empty-slot gray background" (`sprite=null`, gray fill) and "equipped icon" (`sprite=definition.Icon`). Since `WeaponSprite.png` (the placeholder icon, see below) is non-square, setting the sprite only painted a thin sliver, leaving the rest of the slot transparent and making the slot boundary hard to read. Fixed by adding a dedicated `Icon` *child* Image (inset 8px, matching `SkillGridCellUI`'s existing background/icon split) and rewiring `SkillSlotBarUI.slots[*].Icon` to it; the root's own `Image` is now a permanently-fixed gray background never touched by script.
- **Gotcha fixed (Preserve Aspect inconsistency made icons look "square" in one place, "stretched" in another):** the reused `WeaponSprite.png` is actually 16×64 (a tall thin sword), not square. `SkillSlotBarUI`'s icon had `Preserve Aspect = false` (stretched to fill, visually reads as blob-square) while `SkillCooldownHudUI`/`SkillGridCellUI` already had it `true` (correctly thin/tall). Unified all three to `Preserve Aspect = true` so every skill-icon surface shows the same (currently placeholder, pending real square icon art) true aspect ratio.

### AS. Skill Cast VFX (Particle System) + Skill Spec Data Ownership Moved to SkillSO (implemented — supersedes section AH's per-slot radius/range/duration/vfx ownership)
`Skill/SkillEffectVfx.cs` — a single reusable playback component (`IPoolable`) shared by all three skill effect types via three different prefabs (`Assets/04. Prefab/SkillVfx_AreaDamage/SkillVfx_SingleStrike/SkillVfx_SelfBuff.prefab`, same "one class, many prefabs" pattern as `Combat.Projectile`). `Play()` starts the `ParticleSystem`; `main.stopAction = ParticleSystemStopAction.Callback` (forced in `Awake()` regardless of prefab authoring) drives `OnParticleSystemStopped()` → auto-`PoolManager.Release`, no manual timer needed. Prefabs are built with Unity's built-in `Default-Particle.mat` (no new art), color-matched to each skill's `IconTint`.
- **Architecture change:** `radius`/`range`/`duration`/`vfxPrefab` originally lived on the *slot's* effect components (`AreaDamageSkillEffect`/`SingleTargetStrikeSkillEffect`/`SelfBuffSkillEffect`), which was wrong — since any of the 6 slots can have any skill equipped (section AQ), a slot-owned value is shared by whatever skill happens to sit there, so two different skills of the same `EffectType` could never have different range/radius/duration/visual. These moved to `SkillSO` (`AreaRadius`/`StrikeRange`/`BuffDuration`/`VfxPrefab` — a skill only ever uses the one field matching its own `EffectType`, others sit unused, same "sparse/unused-field-is-fine" idiom as `RankSO.RequiredStage == null`). `ISkillEffect.Execute` signature changed from `(Transform origin, float magnitude)` to `(Transform origin, SkillSO definition, float magnitude)` so effects can read them. `targetLayerMask` (always "Monster") and VFX pool capacity/max size stay on the slot components — those really are per-slot-instance, not per-skill-identity. VFX pool registration moved from `OnEnable` (fixed prefab) to inside `Execute()` (`EnsurePool` is idempotent, safe to call every cast) since the prefab now varies with whatever's equipped.
- **Balance change:** `SingleTargetStrikeSkillEffect`'s range default was `8` — larger than the distance from the player to the monster spawn points (~5.8 units, measured via camera orthographic size 8 vs. `SpawnPoint_Bottom_*` positions), so 강타 could hit monsters that had just spawned off-screen, looking like it "fired for no reason." Retuned to `2.5`, matching melee `AttackRange`.
- **Balance change (skill damage now scales with player power):** `AreaDamageSkillEffect`/`SingleTargetStrikeSkillEffect` now deal `(caster's current RuntimeStats.AttackPower + magnitude)` instead of `magnitude` alone (cached via `GetComponentInParent<CharacterStatsProvider>()`, same pattern `SelfBuffSkillEffect` already used) — a flat skill number alone would fall behind auto-attack damage as the player's attack power grows from enhancement/equipment, removing any reason to use skills. `SelfBuffSkillEffect` is unaffected (it's a buff, not damage).

### AT. Equipment Bulk Enhance/Fuse: 전체 강화 / 전체 합성 (implemented)
`Equipment/EquipmentEnhancementService.TryEnhanceAll(slot)` / `Equipment/EquipmentFusionService.TryFuseAll(slot)` — added next to `EquipmentSlotPopupUI`'s existing `CloseButton` (two new buttons to its left). Both sort the slot's owned lines ascending by grade (`EquipmentGradeCatalogSO.IndexOf`) and drive the existing single-step `TryEnhance`/`TryFuse` to exhaustion per line before moving to the next — `TryEnhanceAll` needed `EquipmentEnhancementService` to gain an `EquipmentGradeCatalogSO` constructor dependency it didn't have before (trivial: `GameBootstrapper` already holds that field). `TryFuseAll` re-scans and repeats the whole ascending pass until a full pass makes zero progress, so fusion output that lands on a *higher* grade line (possibly newly created via `ItemDroppedEvent`, which mutates `InventoryService.Items` — a single static snapshot would miss it) cascades upward automatically in the same click. Verified: fusing from the bottom up correctly chains multiple grade tiers in one call (e.g. 언커먼5 stacking up feeds into 레어1 → 레어2 automatically).

### AW. Bug Fixes: Cross-Stat Unlock Refresh, Skill Panel Passive-Tab Leak (implemented)
- **`StatRowUI` unlock overlay didn't clear in real time:** `OnStatEnhanced` only called `Refresh()` when `evt.StatType == _statType` (its own stat) — a row locked behind *another* stat's level (section AN, e.g. `AttackSpeed` requiring `AttackPower` Lv.100) never re-checked `IsUnlocked` when that *other* stat leveled up, so the lock overlay stayed stuck until the row was touched some other way (impossible while its buttons are non-interactable). Fixed with `EnhancementService.HasUnlockRequirement(statType)` (new passthrough) + `StatRowUI.OnStatEnhanced` also refreshing when `evt.StatType == service.GetRequiredStatType(_statType)` (guarded by `HasUnlockRequirement`, since `GetRequiredStatType` returns a meaningless default enum value for rows with no requirement at all).

Fixed by wrapping `SkillSlotBar` + `SkillGrid` in a new `ActiveTabContent` container (full-stretch, zero-offset match to `SkillPanel`'s own rect so existing child anchored-positions needed no adjustment when reparented — same recipe as the pre-existing `PassiveTabContent`) and pointing `panels[0]` at that container instead of `SkillSlotBar` directly.

### AY. Rank System: Manual War-Battle Promotion (implemented — supersedes section U's automatic "clear the required stage → auto-promote" behavior)
Clearing `RankSO.RequiredStage` no longer promotes automatically. `RankService` now tracks eligibility only:
- `RankService.SeedHighestCleared(chapter, stageNumber)` (replaces the old `CatchUpFromHighestStage`, called from the same `GameBootstrapper.Start()` spot) and its `HighestStageClearedEvent` subscription both just cache `_highestClearedIndex` — no side effects, no promotion.
- `GetNextRank()` always returns `RankCatalogSO.GetNext(current)` — **exactly one step**, never more, regardless of how far stage progress has outrun the catalog. `IsNextRankAvailable()` is true only when that one next rank's `RequiredStage` is satisfied *and* it has a `BossPrefab` assigned (content gate). `PromoteToNext()` advances exactly one step and publishes `RankChangedEvent(isRestore:false)` (unchanged consumer: `RankUpPopupUI`). **This is deliberate and load-bearing:** a player who stage-skips far ahead while still low-ranked must still fight and win every intermediate rank's promotion battle one at a time — there is no code path that lets `HighestCleared` satisfy more than the immediate next rank in one shot.
- `UI.RankUpAvailableTextUI` — a clickable gold text directly under `StageInfoText` on the main HUD, shown only while `IsNextRankAvailable()`. **Gotcha hit and fixed while building this:** the script component originally lived on the *same* GameObject it called `SetActive(false)` on to hide itself — which also fires that GameObject's own `OnDisable()`, unsubscribing the very event handlers needed to detect "conditions changed, should reappear," permanently stranding it hidden. Fixed by moving the script to an always-active parent and putting the toggled Text+Button on a child (`Content`) — the same `popupRoot`-as-child shape every other popup in this project already uses; this is a general trap for *any* future component whose own visibility toggle also needs to keep listening for what should un-toggle it.
- `Rank.RankPromotionBattleController` — line-for-line the same shape as `Dungeon.StoneDungeonSessionController` (`Enter`/`Retry`/`ExitToOriginalStage`, spawns `targetRank.BossPrefab` via `PoolManager`, `CharacterDiedEvent` decides win/loss), reusing `StageController.PauseForOverlay()`/`ResumeAfterOverlay()` so the promotion battle never touches `StageSO`/`StageProgression`/`SaveService` — identical "self-contained overlay" pattern as the gold/stone dungeons, just triggered by rank eligibility instead of a dungeon-entry popup. On boss death, calls `RankService.PromoteToNext()` directly (no event indirection needed — same GameObject knows exactly what it was fighting for) then resumes the paused stage. On player death, publishes `Rank.Events.RankPromotionAttemptFailedEvent`; `UI.RankPromotionFailurePopupUI` (a `StoneDungeonFailurePopupUI` clone, same retry/exit button wiring) shows a "승급 실패" choice — retry revives the player and respawns the boss without ending the session, exit resumes the original stage with rank unchanged.
- `RankSO` gained `BossPrefab` (nullable — no boss assigned means the promotion is content-incomplete and `IsNextRankAvailable` stays false forever, same "empty = not ready" idiom as `Skill_*`'s `VfxPrefab`). `Rank_1_병사`/`Rank_2_십인대장` both currently point at `Monster_Boss.prefab` (no dedicated boss art/patterns yet, same placeholder-reuse convention as everywhere else in this project).
- Verified end-to-end in Play Mode: promotion button appears only when eligible, boss fight via real combat correctly triggers `PromoteToNext`, `RankUpPopupUI` fires, next rank's button correctly stays hidden until *its own* requirement is separately satisfied (confirmed the no-skip guarantee), and both failure sub-paths (retry, exit) behave correctly.

### AZ. Skill Gacha & Skill Dungeon (implemented)
`Assets/02. Script/Gacha/` + `Assets/02. Script/Dungeon/` + `Assets/02. Script/Skill/` — adds a "스킬 뽑기"/"스킬 던전" pair that mirrors the existing Soldier 뽑기/강화석 던전 pair, but grants a free skill level-up instead of a new item/unit, since Skill has no "unowned" concept (section AH: every skill already sits in `SkillCatalogSO`, level 0 = not yet learned).
- `Gacha.SkillScrollService` (`IManager`/`IService`) — a new currency ("스킬 주문서"), line-for-line the same shape as `SoldierTicketService`/`CurrencyService` (`AddScrolls`/`TrySpendScrolls`, publishes `Gacha.Events.SkillScrollChangedEvent`). Nothing granted it before this section; 스킬 던전 (below) is its only source.
- `Gacha.SkillGachaPoolEntry`/`SkillGachaTableSO`/`SkillGachaRoller` — same weighted-pool shape as `GachaPoolEntry`/`GachaTableSO`/`GachaRoller` (병사), just pointing at `Skill.SkillSO` instead of `Soldier.SoldierSO`. Deliberately duplicated rather than shared, same "parallel service per domain" convention as section AM.

### BG. Equipment Possession Effect: Owned-Regardless-of-Equip Stat Bonus (implemented)
`Assets/02. Script/Equipment/EquipmentPossessionConfigSO.cs` + `EquipmentPossessionService.cs` + `Assets/02. Script/Character/PossessionStatApplier.cs` + `EquipmentPossessionStatReceiver.cs` — a second, independent passive-bonus system alongside section S's "equip-to-get-stats" (`EquipmentStatConfigSO`/`EquipmentStatService`), which only counts the 5 currently-*equipped* items. This one grants a stat bonus from merely *owning* a line, regardless of equip state, summed across every owned line:
- `EquipmentPossessionConfigSO` reuses `EquipmentStatConfigSO.SlotStatEntry` for the slot→stat mapping (무기→공격력, 장갑→공격속도, 갑옷→체력, 투구→크리티컬데미지, 신발→이동속도), same as the equip-effect config. Per-grade scaling is deliberately **not** `SlotStatEntry.PerGradeIndex` (that field is present but unused here) — the user specified growth in terms of the 6 **main-grade categories** (커먼/언커먼/레어/슈퍼레어/에픽/레전더리), not the 30 individual sub-rungs, so `mainGradeMultipliers` (`[1, 5, 10, 20, 50, 100]`) + `subGradesPerMainGrade` (`5`) implement a step function via `GetMainGradeTier(gradeIndex) = gradeIndex / subGradesPerMainGrade` — flat within a main grade's 5 sub-rungs, jumping only at the boundary. This is a deliberate, scoped exception to section J's "grade has no main-grade field, purely index-driven" rule — it doesn't touch `EquipmentGradeSO` itself, just this one config's own derived grouping.
- Enhancement-level scaling also diverges by main-grade tier rather than using a single global rate: `PossessionEnhancementTier { MainGradeTierThreshold, PercentPerLevel, MaxLevel }` — `GetEnhancementTier(mainGradeTier)` picks the entry with the largest `MainGradeTierThreshold <= mainGradeTier`. Tuned values: tiers 0–3 (커먼~슈퍼레어) get `+1%`/강화 레벨 capped at 강화 100; tiers 4–5 (에픽~레전더리) get `+10%`/강화 레벨 capped at 강화 20. This intentionally does **not** reuse `EquipmentEnhancementConfigSO.StatBonusPerLevel` (the equip-effect system's single flat rate) — `EquipmentPossessionService`'s constructor dropped that dependency entirely once this landed.
- `EquipmentPossessionService` (`IManager`/`IService`) — subscribes `Inventory.Events.InventoryChangedEvent`; `RecomputeAndPublish()` iterates **`InventoryService.Items`** (all owned lines, not `EquippedGearService`), and for each line sums `entry.BaseValue × GetMainGradeMultiplier(gradeIndex) × (1 + tier.PercentPerLevel × min(line.EnhancementLevel, tier.MaxLevel))` per stat type across every line touching that stat — same "publish only what changed vs. last time" shape as `EquipmentStatService`. Owning multiple *copies* of the same line (`OwnedEquipment.Count`) does **not** multiply the bonus (each distinct line counts once); owning multiple *distinct* lines of the same slot (different grades) sums all of them (user's explicit choice: "보유 중인 라인 전체를 합산").
- `Character.PossessionStatApplier` — a table deliberately **separate** from the pre-existing `Character.RuntimeStatApplier`, because this feature's semantics for AttackPower/MaxHealth are "% of the character's own base stat" (unlike Enhancement/`RuntimeStatApplier`'s flat-additive convention for those two stats); AttackSpeed/MoveSpeed are base-relative in both tables so the logic matches; CriticalDamage stays flat-additive-percentage-points, matching Enhancement's own established convention for that stat (section AC).
- `Character.EquipmentPossessionStatReceiver` (Player only) — subscribes `Equipment.Events.EquipmentPossessionStatsChangedEvent`, same "track previously-applied cumulative total, apply only the delta" shape as `EquipmentStatReceiver`.
- `EquipmentDetailPopupUI` — the existing 착용 옵션 미리보기 아래에 a `[보유 효과]` section was added to the same `optionsText` block (no new scene UI needed — the existing text box had spare room), listing each stat this specific line contributes as a percentage via `EquipmentPossessionService.CalculatePreview(definition, enhancementLevel)` (mirrors `EquipmentStatService.CalculatePreview`'s shape).
- No dedicated save state — like section S, this is entirely derived from `InventoryService`'s own persisted owned-lines state; `GameBootstrapper.Start()` calls `_equipmentPossessionService?.RecomputeAndPublish()` once after `RestoreInventory()`, same spot/reason as `EquipmentStatService`'s equivalent call.
- Content: `EquipmentPossessionConfig.asset` — Common1 baseline (무기 1%/장갑 0.05%/갑옷 1%/투구 0.1%/신발 0.05%), `PerGradeIndex = 0` for all 5 entries (superseded by `mainGradeMultipliers`, left at 0 as a harmless unused placeholder rather than removed, since the field is shared with `EquipmentStatConfigSO`).
- Verified in Play Mode via reflection: owning 1 Common1 weapon line applied exactly `baseAttack × 1%`; a 2nd copy of the same line added nothing further; a 2nd *distinct* weapon line (different grade) summed on top correctly; enhancing a line scaled the bonus per the tiered formula; grade multipliers matched `1/5/10/20/50/100%` exactly at 커먼1/언커먼1/레어1/슈퍼레어1/에픽1/레전더리1 and stayed flat across sub-rungs within the same main grade; SuperRare capped its enhancement contribution at 강화 100 (20%→40%), Epic capped at 강화 20 (50%→150%).

### BO. Character Physical Separation: No-Overlap Foundation for Player/Soldier/Monster (implemented — prerequisite for the planned 7-unit-type system below)
`Assets/02. Script/Character/CharacterSeparation.cs` (신규) — per user request, this is phase 0 of a much larger planned feature (7 monster unit types — Infantry/Archer/Cavalry/Knight/Spearman/MountedArcher/Siege — each with unique combat mechanics like cavalry charge+knockback and shield-formation damage passthrough, later to be applied to player soldiers too, discussed and scoped in this session but **not yet implemented** — only this prerequisite landed). Every mechanic discussed for that future system (charge collisions, knockback, a shield physically blocking what's behind it) depends on characters actually occupying distinct space instead of freely overlapping, which was the very first blocker found.
- **Why characters currently overlap despite already having colliders:** `Character.CharacterMover.Tick` moves every character via direct `transform.position = Vector3.MoveTowards(...)` — confirmed by reading the class fresh this session — completely bypassing Unity's 2D physics engine. Every character (`Player`, `Soldier`/`Soldier_Ranged`, all `Monster*` tiers) already has a `CircleCollider2D` *and* a `Rigidbody2D`, but every `Rigidbody2D` found was `Kinematic` (confirmed via `execute_code` inspection of the actual prefabs, not assumed) — Kinematic bodies are never pushed by physics collision response no matter how their colliders overlap, so the existing colliders/rigidbodies were only ever load-bearing for `Physics2D.OverlapCircleAll`-based *detection* (targeting scans, hit detection) elsewhere in this project, never for physical collision response.
- **Deliberately did not migrate movement onto Rigidbody2D/Dynamic bodies** to get "free" physics-based collision response — that would require rewriting `CharacterMover` and every system that reads/writes `CharacterMover.Target`/`transform.position` directly (`EnemyTracker`, `MonsterTargetSelector`, `RallyMoveReceiver`, `SoldierBehaviorController`'s kiting, `PlayerManualMover`, offline/online — dozens of already-working call sites) around Rigidbody2D's `FixedUpdate`-timed physics step instead of this project's `GameTicker`/`ITickable` `Update`-timed step, a much larger and riskier rewrite for a project with no physics-driven movement anywhere today. Instead, `CharacterSeparation` is a **fully independent, additive `ITickable`** — it doesn't touch `CharacterMover` at all, doesn't know about targets/AI, and just nudges `transform.position` by a small correction each tick if it's overlapping another `CharacterSeparation`-bearing character, layered on top of whatever `CharacterMover` (or anything else) already did to the position that frame.
- `CharacterSeparation.BodyRadius` (public) reads `CircleCollider2D.radius × transform.lossyScale.x` once in `OnEnable` (re-read on every pool reuse, matching the established "recompute on every `OnEnable`, pooling-safe" idiom from `Soldier.SoldierStatReceiver`/`Character.StageMonsterScaler`) — reuses the collider each prefab already has instead of introducing a second, potentially-inconsistent "body size" number, and automatically picks up `Monster_Elite`/`Monster_Boss`'s 1.2×/1.5× visual scale (section X) without any special-casing.
- No layer filtering at all — `Physics2D.OverlapCircleAll(position, bodyRadius × 2)` queries every layer, and any hit is treated as "another character to separate from" purely by checking `TryGetComponent<CharacterSeparation>()`, regardless of which side it's on (Player/Soldier share the `Player` layer, Monster tiers use `Monster`) — matches the explicit ask ("병사와 플레이어, 적들에게" — soldiers, player, and enemies all mutually block each other) without needing per-prefab layer mask configuration that could be misconfigured.
- Attached to `Player` (scene GameObject) and all 7 character prefabs — `Monster`/`Monster_Elite`/`Monster_Boss`/`Monster_GoldDungeon`/`WarBoss`/`Boss_TrainingDummy`/`Soldier`/`Soldier_Ranged` — via `manage_prefabs(modify_contents, components_to_add)`. `Boss_TrainingDummy` included even though section BF removed its `CharacterMover`/targeting (it never moves) — it should still physically block others from walking through it, and `CharacterSeparation` has no dependency on `CharacterMover` so this works with zero extra wiring.
- **Gotcha hit while verifying (Edit Mode only, not a runtime bug):** testing two overlapping test colliders via `execute_code` initially produced nonsensical diagonal push directions instead of the expected pure-axis push. Root cause: Unity's 2D physics broadphase only syncs a `Collider2D`'s world position with its `Transform` during an actual physics step (`FixedUpdate`, which runs continuously in Play Mode) — in Edit Mode, setting `transform.position` directly does *not* update what `Physics2D.OverlapCircleAll` sees until something forces a sync. Calling `Physics2D.SyncTransforms()` immediately after positioning the test objects fixed it (clean, symmetric push along the expected axis, overlap distance measurably increasing). This only affects *this session's Edit-Mode test harness* — real gameplay already runs a physics step every frame regardless, so `CharacterSeparation` needed no code change for this.
- Verified via `execute_code`: two `CircleCollider2D`(radius 0.5) test objects placed 0.5 units apart (0.5 unit overlap, since combined radius = 1.0) each moved along the correct axis away from the other after one `Tick(0.1f)`, and center-to-center distance increased from `0.5` to `0.92` in a single tick — confirms the overlap-resolution math is correct. Full in-game verification (many characters converging, visually not overlapping, no jitter/instability at scale) still needs a real Play Mode session — not done this session for the usual Editor-focus/low-memory Play Mode hang risk reason.
- **Explicitly out of scope for this step, flagged for the next phases already discussed with the user:** the 7 unit types themselves (`UnitClass` enum, `RangedKiter`, `CavalryCharge`+knockback, `DamageReduction` stat on `Health`, shield-formation damage passthrough for Spearman, circling-kite movement for MountedArcher, `SplashAttackBehavior` for Siege), and the AI-generated sprite set for each. None of that is implemented yet.

### BQ. Unit Type Phase 2: Cavalry Charge with Speed-Dependent Handling + Generic Knockback (implemented)
`Assets/02. Script/Combat/CavalryCharge.cs`/`Character/KnockbackReceiver.cs`(둘 다 신규) — the third planned unit type. Unlike Archer/MountedArcher (section BP, pure repositioning on top of the existing `RangedAttackBehavior`), Cavalry needed genuinely new impact/damage logic, refined twice this session as the user added detail: first the basic "retreat → straight charge → knockback" shape, then explicitly "steering should still be possible mid-charge if the target dodges, but handling should degrade the faster you're going."
- **State machine** (`Positioning` ↔ `Charging`, replaces `MonsterTargetSelector` entirely, same "one movement-driving component per monster" convention as section BP): in `Positioning`, reuses `KiteRetreatCalculator`(section BP) to back away until `chargeStartDistance`(5) is reached, then locks in the threat's *current* position as the initial charge direction and switches to `Charging`. During `Charging`, `CharacterMover` is bypassed entirely (`_mover.Target = null`) — the component drives `transform.position` directly every tick for precise control over acceleration and steering, something `CharacterMover`'s simple `MoveTowards` couldn't express.
- **Acceleration:** `_chargeSpeed` grows by `chargeAcceleration`(4/s) every tick, capped at `maxChargeSpeed`(9), starting from `chargeStartSpeed`(3).
- **Speed-dependent steering (this session's refinement):** every tick, the ideal direction to the threat's *live* (possibly moved) position is computed, and `_chargeDirection` is rotated toward it via `Vector3.RotateTowards` — but the maximum rotation allowed this tick is `turnRateDegreesPerSecond = max(minTurnRateDegreesPerSecond(20), baseTurnRateDegreesPerSecond(180) − turnRatePenaltyPerSpeed(25) × (currentSpeed − chargeStartSpeed))`. At the charge's starting speed this is a full 180°/s (nearly instant lock-on); by `maxChargeSpeed` it's down to 30°/s — a real, measurable "harder to handle at high speed" feel, never dropping below the 20°/s floor (never *fully* uncontrollable).
- **Impact:** each `Charging` tick also runs `Physics2D.OverlapCircleAll(position, bodyRadius + hitCheckReach, allyLayerMask)` (`bodyRadius` read from `CharacterSeparation.BodyRadius`, section BO — same body-size source as the no-overlap system, no second number introduced) — every live `Health` caught is dealt `Stats.AttackPower + (currentSpeed − chargeStartSpeed) × bonusDamagePerSpeed` via a **direct `Health.TakeDamage` call**, bypassing the normal `Attacker`/`IAttackBehavior` cadence entirely (same reasoning as `War.Boss.WarBossPatternRunner`'s AoE, section AG: this is a special one-off impact, not a periodic attack). A hit ends the charge immediately (back to `Positioning`); no hit within `maxChargeDuration`(3s) also ends it (overrun case, prevents an infinite off-screen chase). Regular melee (`Attacker`+`MeleeAttackBehavior`, kept on this prefab unlike Archer/MountedArcher) still functions independently the whole time, for the case where something is adjacent without an active charge.
- **`Character.KnockbackReceiver`** (new, generic — attached to `Player`, `Soldier`, `Soldier_Ranged`, and `Monster_Cavalry` itself for symmetry/future-proofing, *not* the other monster tiers yet since nothing currently targets them with an effect like this) — `ApplyKnockback(direction, distance, duration)` disables the target's own movement-driving components (`componentsToSuspend`, copied field-for-field from each prefab's existing `RallyMoveReceiver` config — `[SoldierBehaviorController, EnemyTracker]` for Soldiers, `[EnemyTracker]` for Player, `[CavalryCharge]` for Cavalry itself) plus `CharacterMover` itself, then moves `transform.position` directly at `distance/duration` units/sec for `duration` seconds — deliberately **not** using `CharacterMover`'s own `Stats.MoveSpeed` (a knockback should feel like a fixed external impact, not scale with how fast the *victim* normally walks). Same "revert cleanly when done, don't leave suspended forever" shape as `RallyMoveReceiver`/`RangedKiter`.
- Content: `MonsterStats_Cavalry.asset`(HP 45/ATK 9/Range 2.5/Speed 2.2/Interval 1) and `Monster_Cavalry.prefab` (duplicated from `Monster.prefab`, `MonsterTargetSelector` → `CavalryCharge`, `MeleeAttackBehavior`/`Attacker` kept as-is). Same "mechanism now, stage spawn tables later" scope as section BP.
- **Gotcha hit while verifying (Edit Mode test-harness debris, not a code bug):** a `Health.TakeDamage` call inside a reflection-driven test threw a `NullReferenceException` on `_statsProvider` that took several iterations to root-cause. The actual cause: **12 orphaned `GameObject`s from earlier failed test attempts in this same Editor session** (including some pre-dating this session's own work entirely) were still sitting in the scene near the test coordinates, several with a `Health` component whose `_statsProvider` had never been reflection-populated (because an earlier attempt threw *before* reaching its own cleanup call). ### BS. Unit Type Phase 4: Spearman + Shield-Bearer Formation (implemented)
`Assets/02. Script/Character/ShieldGuard.cs`(신규) + `Health.cs`(수정) + `Assets/02. Script/Combat/FormationFollower.cs`(신규) — the fifth planned unit type, and the first to introduce a genuine two-unit relationship (a Shield-Bearer that soaks hits, and a Spearman that hides behind it) rather than a single self-contained monster.
- **`Character.ShieldGuard`** (new, attached to `Monster_ShieldBearer.prefab` only) — a second, independent HP pool (`maxShieldHealth`, default 25) that `Health.TakeDamage` checks for and delegates to first. `AbsorbDamage(amount)` absorbs up to its remaining shield HP and returns the unabsorbed overflow; the moment the shield's HP hits 0 *on this call*, any overflow is also pushed straight into a registered `SetProtectedUnit(Health)` via that unit's own `TakeDamage` — this is the literal implementation of the user's "방패를 부수면 보병에게 데미지를 입히고 창병에게까지 데미지를 입힐 수 있겠지?" request: the shield-bearer's own body takes the overflow through the normal `Health.TakeDamage` return path (see below), and the registered Spearman behind it takes the *same* overflow amount through this second, explicit call. No damage-source filtering exists (melee, ranged, charge impact — anything routed through `Health.TakeDamage` is absorbed identically), matching the user's framing that a shield blocks "기마병의 돌진이나 궁병의 활" indiscriminately.
- **`Character.Health.TakeDamage`** gained a `_shieldGuard` field (`GetComponent<ShieldGuard>()` in `Awake`, `null` for every character type except Shield-Bearer — same "optional sibling component, absent everywhere else" shape `CavalryCharge`/`KnockbackReceiver` already established). Ordering is now: `DamageReduction` flat mitigation (section BR) first, then `ShieldGuard` absorption if present and still up, then whatever's left lands on the unit's own health — each stage can fully negate the hit (return early, no event) if it reaches 0.
- **`Combat.FormationFollower`** (new, Spearman's movement driver, replaces `MonsterTargetSelector` entirely) — `SetLeader(Transform)` assigns which Shield-Bearer to hide behind (currently must be called externally; no automatic pairing/formation-spawn system exists yet, matching the user's own framing that formation *spawning* ("병법") is future work — this phase only builds the follow-behavior itself). Every retarget, if a leader is assigned: finds the nearest threat *from the leader's position* (not the spearman's own), then sets its follow-anchor to `leaderPosition + normalize(leaderPosition − threatPosition) × followDistance(1.5)` — i.e., directly behind the leader, opposite the threat, so the leader's body stays between the spearman and whatever it's fighting. If no leader is assigned (or one was never set), falls back to approaching the threat directly like a plain monster, so a Spearman spawned alone isn't inert.
- **Range math (deliberate, not incidental):** `MonsterStats_Spearman.asset`'s `AttackRange = 4` was chosen as `ShieldBearer's AttackRange(2.5) + followDistance(1.5)` — exactly far enough that, standing at the follow anchor, the spear still reaches past the shield-bearer to the same threat the shield-bearer itself is fighting. The Spearman's own `Attacker`/`MeleeAttackBehavior` needed no changes for this — it already independently scans its own `AttackRange` every attack interval, same as any other melee unit; `FormationFollower` only decides *where the Spearman stands*, never who it attacks.
- Content: `MonsterStats_ShieldBearer.asset`(HP 40/ATK 8/Range 2.5/Speed 1.0/Interval 1/DamageReduction 0) and `MonsterStats_Spearman.asset`(HP 35/ATK 10/Range 4/Speed 1.3/Interval 1.1/DamageReduction 0) — placeholder pacing numbers, same convention as every other stat asset. `Monster_ShieldBearer.prefab` (duplicated from `Monster.prefab`, kept the normal `MonsterTargetSelector`+`Attacker`+`MeleeAttackBehavior` Infantry composition unchanged, only added `ShieldGuard`) and `Monster_Spearman.prefab` (duplicated from `Monster.prefab`, `MonsterTargetSelector` → `FormationFollower`, `allyLayerMask` wired to the `Player` layer bit `256` matching every other monster movement driver). ### BT. Unit Type Phase 5: Siege Splash Attack (implemented — completes the 7-unit-type roadmap from section BO)
