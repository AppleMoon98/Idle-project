### GA. Fix: Breakthrough/Repeat Toggle Corrupted Spawner/Tracker State When Used While a Dungeon Overlay Was Active
`Assets/02. Script/Stage/StageProgression.cs` + `Assets/02. Script/UI/StageModeToggleUI.cs`/`StageRepeatPickerPopupUI.cs` — 실사용 중 "던전 입장 중에 돌파/반복 버튼을 조작하면 로직이 꼬인다"는 제보로 조사한 결과, 실제 버그였다.
- **원인:** `StageProgression._isSuppressed`(section BJ/DY 계열 — `StageController.PauseForOverlay`가 켜고 `ResumeAfterOverlay`가 끄는, "오버레이 활성 중엔 `OnStageCleared`/`OnCharacterDied`를 완전히 무시한다"는 기존 안전장치)가 `JumpTo`/`JumpToHighestCleared`/`JumpToBreakthroughFrontier`(각각 반복 스테이지 선택, 랭크 승급 시 자동 반복 전환, 반복→돌파 복귀가 호출하는 세 창구) 세 곳에는 전혀 체크되지 않고 있었다 — `OnStageCleared`/`OnCharacterDied`만 이 플래그를 확인하고, 돌파/반복 UI가 부르는 이 세 메서드는 체크 없이 곧바로 `_controller.LoadStage(...)`를 실행했다. 던전 안(오버레이가 스포너/트래커를 이미 일시정지·은닉해둔 상태)에서 돌파/반복을 조작하면, 던전이 존재하는 걸 전혀 모르는 `LoadStage`가 그 자리에서 실행돼 새 스포너/트래커를 만들고 몬스터를 스폰한다 — 던전을 나갈 때(`ResumeAfterOverlay`)는 여전히 원래(일시정지해뒀던) 스테이지를 복원하려 들어, 두 스테이지 상태가 서로 어긋나며 꼬인다.
- **수정(이중 방어):** (1) `StageProgression`의 세 메서드 전부 맨 앞에 `_isSuppressed` 체크를 추가했다(`OnStageCleared`/`OnCharacterDied`와 동일한 가드) — 이게 실질적인 근본 수정이며, 앞으로 이 메서드들을 부르는 어떤 새 호출부가 생겨도 자동으로 보호된다. `JumpTo`는 실패 시 `false`를 반환한다. (2) `StageModeToggleUI.OnToggleClicked`/`StageRepeatPickerPopupUI.Open()`도 `StageController.IsOverlayActive`를 미리 확인해 `ToastMessageRequestedEvent("던전 입장 중에는 스테이지 모드를 변경할 수 없습니다.")`를 발행하고 아무 것도 하지 않는다 — (1)만으로도 상태 꼬임은 막히지만, UI 레이어에서 먼저 막아야 사용자에게 "왜 안 되는지" 이유가 보인다(section EH의 "개별 합성 재료 부족" 토스트, 지난 세션의 던전 중복 입장 토스트와 같은 UX 관례).
- Play Mode에서 골드 던전 진입 중 `StageRepeatPickerPopupUI.Open()`이 토스트만 띄우고 안 열리는 것, `StageController.JumpCurrentToBreakthroughFrontier`/`JumpCurrentToHighestCleared`/`JumpCurrentToStage`를 UI를 우회해 직접 호출해도(`JumpCurrentToStage`는 `false` 반환) 전부 무시됨을 확인했다.

### GB. Camera Zoom: Slider Drawer/Toggle Button Replaced by Pinch Gesture (supersedes section BN/DX's slider+drawer UI — both deleted outright)
`Assets/02. Script/UI/CameraPinchZoomUI.cs`(신규) + 삭제: `CameraZoomSliderUI.cs`/`CameraZoomDrawerUI.cs` + `Assets/02. Script/Services/CameraFollowService.cs`/`Core/GameBootstrapper.cs`/`Rank/Boss/PromotionBossController.cs`(참조처 갱신) — 화면 왼쪽에서 토글 버튼(`ZoomToggleButton`)으로 여닫던 세로 슬라이더 드로어(`CameraZoomControl`)를 완전히 제거하고, 두 손가락 핀치 제스처(+PC 테스트용 마우스 휠, 아래)로 카메라 시야(`orthographicSize`)를 직접 조절하도록 바꿨다.
- **`UI.CameraPinchZoomUI`**(신규, `Main Camera`에 직접 부착 - `[RequireComponent(typeof(Camera))]`) — 매 틱 `Touchscreen.current.touches`에서 동시에 눌려있는 터치 2개를 찾아 그 사이 거리(픽셀)의 프레임 간 변화량으로 `orthographicSize`를 조절한다. 손가락을 벌리면(거리 증가) 확대(`orthographicSize` 감소), 오므리면(거리 감소) 축소. 민감도를 고정 배율로 두지 않고 `sizeRange / Screen.height`로 매번 계산해, 해상도와 무관하게 "화면 세로 길이만큼 벌리는 핀치 = wide~narrow 전체 범위"가 되도록 정규화했다. 클램프+정규화 저장 로직은 `ApplyOrthographicSizeDelta(float)`로 뽑아뒀다 — 핀치(`TickPinch`)와 마우스 휠(`TickMouseScroll`) 둘 다 이 하나의 메서드로 수렴한다.
- **마우스 휠 보조 입력(`TickMouseScroll`)** — 이 프로젝트는 모바일이 타겟이지만 PC 환경에서도 테스트하는 경우가 있어, `Mouse.current.scroll.y`(위로 굴리면 양수)를 읽어 휠 위로 굴리면 확대, 아래로 굴리면 축소(핀치와 방향 일치)한다. 터치스크린이 없는 에디터/PC 빌드에서는 `Touchscreen.current`가 `null`이라 핀치 경로는 그냥 조용히 스킵되고, 이 마우스 경로만 동작한다.
- **원시값 크기가 아니라 방향(부호)만 읽어 노치당 고정 스텝(`mouseScrollStepSize`, 기본 1.5)을 적용한다.** 최초 구현은 `-scrollY × mouseScrollSensitivity`(기본 0.02, 레거시 Windows 휠 단위인 ±120 근방을 가정)로 원시값에 비례시켰는데, 실사용 중 "휠을 굴려도 줌이 안 움직이는 것 같다"는 제보로 실측해보니 이 개발 환경의 새 Input System에서는 노치 하나당 원시값이 겨우 `±1` 근방만 들어왔다 — 그 결과 실제 변화량이 `0.02`(narrow~wide 전체 범위 18 중 0.1%)에 그쳐 사실상 안 움직이는 것처럼 보였다. 휠 원시값 스케일은 기기/드라이버마다 표준화돼 있지 않아 다음에 또 다른 스케일을 만날 수 있으므로, 그 크기 자체를 아예 무시하고 `Mathf.Sign(scrollY)`로 방향만 취해 매 노치 감지마다 항상 같은 크기(1.5)만큼 움직이도록 바꿨다 — 휠은 핀치처럼 연속적인 제스처가 아니라 이산적인 "노치" 입력이라는 점에서도 이 방식이 더 맞는 모델이다.
- **`wideOrthographicSize`/`narrowOrthographicSize`(기본 24/6)는 예전 슬라이더와 완전히 같은 역할을 그대로 이어받는다** — `Services.CameraFollowService`(카메라 추적 시작 임계값이자 플레이어 이동 제한 경계, section BN)와 `Rank.Boss.PromotionBossController`(승급전 보스 페이즈2 강제 최광각, section FJ)가 참조하는 대상을 `CameraZoomSliderUI` → `CameraPinchZoomUI`로 그대로 갈아끼웠다 — 두 값의 의미/기본값이 동일해 참조처 코드 로직 자체는 손댈 필요가 없었다(타입/필드명 치환뿐).
- **PlayerPrefs 키(`CameraZoomSliderValue`)를 그대로 재사용한다** — 저장 형식(0~1 정규화 값, wide~narrow 보간 비율)이 동일해 기존에 저장된 사용자 줌 선호도가 마이그레이션 없이 그대로 이어진다.
- **삭제된 것과 함께 사라진 UI:** `Canvas/CameraZoomControl`(세로 슬라이더+±라벨), `Canvas/ZoomToggleButton`, `Canvas/SettingsPopup`의 `ZoomRow`(설정 팝업 안의 보조 슬라이더 - 핀치 제스처로 완전히 전환하면서 슬라이더형 대체 입력 자체가 의미 없어져 함께 제거) 전부 씬에서 삭제했다. `SettingsPopup`은 section EG에서 이미 옵션 목록을 스크롤 가능하게 바꿔뒀던 덕분에, 행 하나가 빠져도 `PopupPanel` 크기를 따로 줄일 필요가 없었다.
- `HealthBarUI`/`DamageNumber`/`DamageNumberConfigSO`의 줌 보정 로직(orthographicSize 비율로 자기 자신의 localScale을 보정해 화면상 크기를 일정하게 유지) 자체는 전혀 손대지 않았다 - 이들은 `Camera.main.orthographicSize`를 직접 읽을 뿐 `CameraZoomSliderUI` 타입에 대한 코드 의존이 없었고(주석에서만 언급), 핀치든 슬라이더든 결국 같은 `orthographicSize`를 바꾸는 것이라 자동으로 계속 맞물린다.
- Play Mode에서 `ApplyPinchDelta`를 리플렉션으로 직접 호출해 검증했다: 화면 세로 길이만큼 손가락을 벌리면 `orthographicSize`가 정확히 narrow(6)까지, 절반만큼 벌리면 정확히 `sizeRange`의 절반(9)만큼 감소함을 확인했고, 클램프 경계(6~24) 밖으로 못 나가는 것도 확인했다. `CameraFollowService.GetWorldBoundsHalfExtent()`가 새 컴포넌트로부터 정상적으로 `WideOrthographicSize`를 읽어오는 것(비영·값 일치)과 PlayerPrefs 저장도 함께 확인했다. 마우스 휠 경로는 `InputSystem.QueueStateEvent`로 `MouseState.scroll = (0, 1)`(이 환경에서 실측된 노치당 원시값)을 주입해 `orthographicSize`가 노치마다 정확히 1.5씩(narrowOrthographicSize=6에서 클램프됨) 움직임을 확인했다.

### GC. Top HUD Buttons Gain Sprite-Swap Press Feedback + Pressed-State Label Offset
`Assets/02. Script/UI/ButtonPressedTextOffsetUI.cs`(신규) — `MenuButton`/`StageModeToggle`/`PlayerControlModeToggle`(우상단 고정 HUD 버튼 3개) 전부 `Button.Transition = SpriteSwap`으로 바꿔 누르면 `SmallBlueSquareButton_Pressed` 스프라이트로 전환되고 떼면 원래(`SmallBlueSquareButton_Regular`)로 돌아오도록 했고, 배경색은 어두운 반투명 틴트(`0.15, 0.15, 0.18, 0.9`)에서 흰색(무틴트)으로 바꿔 새 버튼 스프라이트 원색이 그대로 드러나게 했다. 이어서 눌려 있는 동안 라벨 텍스트도 아래로 살짝 밀려 눌린 느낌을 주도록 `UI.ButtonPressedTextOffsetUI`를 추가했다.
- **`UI.ButtonPressedTextOffsetUI`**(신규, `IPointerDownHandler`/`IPointerUpHandler`/`IPointerEnterHandler`/`IPointerExitHandler`) — `Button`(Selectable)이 이미 같은 인터페이스들로 스프라이트 전환 상태 기계를 돌리고 있는 것과 완전히 독립적으로, 같은 GameObject에 얹혀 같은 포인터 이벤트를 받아 자식 라벨 `RectTransform`의 Bottom/Top 오프셋만 조정한다 — 한 GameObject에 이벤트 인터페이스를 구현하는 컴포넌트가 여러 개 있어도 Unity가 전부 호출해주므로 `Button` 자체를 건드리거나 상속할 필요가 없었다.
- **정상 상태 오프셋을 별도 필드로 중복 저장하지 않는다** — `Awake()`가 그 시점의 `text.offsetMin`/`offsetMax`(현재 Bottom=18/Top=0, section 앞부분에서 설정한 값)를 그대로 캐싱해 "정상 상태"로 삼는다. `pressedBottom`(0)/`pressedTop`(16)만 인스펙터 값으로 받아, 눌린 순간(`_isPointerDown && _isPointerOver`) 두 필드만 그 값으로 바꾸고 아니면 캐싱해둔 정상값으로 되돌린다.
- **눌림 판정은 "포인터가 눌려 있고, 동시에 버튼 위에 있을 때"만** — `OnPointerDown`/`OnPointerUp`으로 누름 여부를, `OnPointerEnter`/`OnPointerExit`로 버튼 위에 있는지를 각각 추적해 `Refresh()`에서 AND 조합한다. 버튼을 누른 채 밖으로 드래그하면 즉시 정상 상태로 돌아오고(Unity의 기본 `Selectable` 스프라이트 전환이 포인터가 벗어나면 Normal/Highlighted로 돌아오는 것과 동일한 방향), 버튼 밖에서 떼도 정상 상태가 유지된다 — Play Mode에서 `OnPointerDown`→`OnPointerExit`(밖으로 드래그, 즉시 정상 복귀 확인)→`OnPointerUp`(밖에서 뗌, 정상 상태 유지 확인) 순서로 직접 검증했다.
- **`UI.ButtonColorThemeSwitcherUI`**(신규) — `StageModeToggle`(돌파/반복)과 `PlayerControlModeToggle`(자동/수동) 두 버튼만(`MenuButton`은 대상 아님) 반복/수동처럼 "주의를 끌어야 하는" 상태일 때 배경을 파랑(`SmallBlueSquareButton_*`)에서 빨강(`SmallRedSquareButton_*`) 테마로 통째로 바꾼다. `Button.Transition = SpriteSwap`은 한 시점에 평상시/눌림 스프라이트 한 쌍만 쓸 수 있으므로, 상태가 바뀔 때마다 `Image.sprite`(평상시)와 `Button.spriteState.pressedSprite`(눌림)를 두 세트 중 하나로 동시에 갈아끼우는 `SetAlert(bool)` 하나로 구현했다 — 이 컴포넌트 자체는 "어떤 상태일 때 빨간지"를 전혀 모르는 범용 색 테마 스위처이고, 그 판단은 `StageModeToggleUI`/`PlayerControlModeToggleUI`가 자신의 `Refresh()`에서 내려 넘겨준다(`themeSwitcher?.SetAlert(mode == ...)`).
- `StageModeToggleUI.Refresh()`는 "승급" 라벨 오버라이드보다 먼저 실제 모드(돌파/반복)를 계산해 `SetAlert`를 호출하도록 순서를 바꿨다 — 랭크 승급이 가능해져 라벨이 "승급"으로 잠깐 바뀌어도, 그 밑에 깔린 실제 진행 모드(반복 중이었다면 빨강)와 색이 어긋나지 않는다.
- Play Mode에서 `PlayerControlModeService.Toggle()`/`Stage.StageModeService.Toggle()`을 직접 호출해 왕복 검증했다: 자동→수동/돌파→반복 전환 시 `Image.sprite`와 `Button.spriteState.pressedSprite`가 각각 `SmallRedSquareButton_Regular_0`/`_Pressed_0`로, 되돌리면 다시 `SmallBlueSquareButton_*`로 정확히 전환됨을 확인했다.

### GD. Fix: Manual Mode Player Drifts Upward on Stage Start (Stale CharacterMover.Target Survives Position Reset)
`Assets/02. Script/Character/PlayerManualMover.cs` — 수동 모드로 스테이지를 시작하면 플레이어가 화면 위쪽으로 저절로 끌려가는 버그를 실사용 중 제보받아 조사했다.
- **원인:** `Character.CharacterMover.Tick()`은 `EnemyTracker`의 활성 여부와 무관하게, `Target`이 non-null이기만 하면 계속 그쪽으로 이동한다 — `EnemyTracker`를 끄는 것은 "새 Target을 더 이상 고르지 않는다"는 뜻일 뿐, 이미 설정된 `Target`을 지우지는 않는다. `Character.StagePositionResetter`는 스테이지 전환 시 플레이어의 *위치*만 시작 지점으로 되돌릴 뿐 `CharacterMover.Target`은 전혀 손대지 않는다. 그런데 몬스터는 항상 화면 위쪽 스폰 지점에서 다시 태어나므로(`Stage.MonsterSpawner`), Auto 모드였을 때 `EnemyTracker`가 마지막으로 가리켜뒀던 몬스터 Transform(풀링되어 재사용되는 오브젝트라 파괴되지 않고 계속 살아있다)이 새 스테이지의 위쪽 스폰 지점에 다시 나타나면, Manual 모드로 전환된 뒤에도(`EnemyTracker`가 꺼져 있어 스스로 재보정되지 않으므로) `CharacterMover`가 그 잔여 `Target`을 향해 계속 위로 이동한다.

### GL. Save Load Resilience: Corrupted PlayerPrefs No Longer Crashes Bootstrap (GitHub 이슈 #7)

Script/Rank/RankPromotionBattleController.cs` — 6개 오버레이 세션 컨트롤러 전부 `Enter()`/`Retry()`가 `_isActive`(+`_isFighting`)를 스폰 성공 여부 확인 **전에** 먼저 켜는 공통 결함을 갖고 있었다(실제 GitHub 이슈로 제보됨). `SpawnBoss()`/`SpawnMonsters()`/`SpawnZones()`는 `PoolManager`를 못 구하면(`DungeonSpawnUtility.TryGetPool` 실패) 조용히 `return`해 대상이 `null`/빈 컬렉션으로 남는데, 그 시점엔 이미 상태가 "진행 중"으로 커밋된 뒤였다.
- **영향은 컨트롤러마다 달랐다:** 던전 5개(Gold/Stone/Skill/Boss/SoldierRescue)는 전부 `TimeLimitSeconds` 타이머가 있어 결국 `HandleFailure()`/`EndSession(false)`로 자동 탈출은 됐다 — 영구 소프트락은 아니지만, 그 시간 내내 빈 전투 화면에 갇히고 `PauseForOverlay`/`SetSoldiersActive(false)`/`ResetCombatantsForRetry` 같은 부수효과가 실패한 시도에도 그대로 적용된 채 방치됐다. **`RankPromotionBattleController`는 제한시간 자체가 없어서(section AY, 의도적 설계)** `_bossInstance`가 `null`인 채 `CharacterDiedEvent`를 영원히 기다리는 **진짜 무한 대기(영구 소프트락)**가 됐다 — 이 컨트롤러가 이슈의 핵심 사례.
- **수정 패턴(6개 파일에 동일하게 적용, 이 프로젝트의 "던전류 컨트롤러는 베이스 클래스 없이 나란히 중복 구현" 기존 관례를 그대로 따라 새 공유 베이스는 만들지 않음):** `SpawnX()`를 `bool TrySpawnX(out GameObject instance)`(단일 대상, Rank/Stone/Skill/Boss)나 `bool TrySpawnX()`(다중 대상, 성공 시 컬렉션이 비어있지 않음 — Gold의 `_aliveMonsters`/SoldierRescue의 `_activeZones`)로 바꿔, "준비 → 생성 → 커밋" 순서로 뒤집었다. `Enter()`/`Retry()`는 스폰을 **먼저** 시도해 성공했을 때만 `_isActive`/`_isFighting`을 켜고 `stageController.PauseForOverlay()`/`SetSoldiersActive(false)`/`ResetCombatantsForRetry()` 등 부수효과를 실행한다 — 실패하면 이런 부수효과 자체가 한 번도 안 일어났으므로 롤백할 상태가 없다(`Retry()`의 실패는 이미 떠 있던 "토벌 실패" 화면 상태를 그대로 유지 — 추가 롤백 없이 다시 재도전/나가기 가능). 기존 `StartAttempt()`/`SpawnBoss()` 이름은 각각 `BeginFighting()`(스폰 이후의 순수 북키핑만)/`TrySpawnBoss()`로 갈렸다. 실패 시 공통 토스트("전투 대상을 생성하지 못했습니다. 잠시 후 다시 시도해주세요.")를 새로 추가했다(이슈의 "사용자 오류 안내 제공" 완료 조건).
- `RegressionChecks.cs`에 6개 검사를 추가했다 — 이슈의 재현법("PoolManager 없이 임시 ServiceLocator 구성")을 새 ServiceLocator를 따로 만드는 대신 `WithNullServices(Action)`(신규 헬퍼, 리플렉션으로 `GameBootstrapper.Services` 자동 프로퍼티의 private 세터를 호출해 실행 동안만 `null`로 바꿨다가 항상 원래 값으로 복원)로 재현했다 — 새 ServiceLocator를 조립하는 것보다 훨씬 적은 코드로 동일한 "PoolManager를 못 구함" 상태를 만든다. `AssertTrySpawnBossReturnsFalse<T>()`/`AssertTrySpawnCollectionReturnsFalse<T>(methodName, fieldName)` 두 제네릭 헬퍼가 리플렉션으로 각 컨트롤러의 `TrySpawnX`를 직접 호출해 `false`(+ 대상 없음/컬렉션 빈 상태)를 반환하는지 확인한다 — `config`/프리팹 등 실제 콘텐츠 애셋을 하나도 준비하지 않아도 되는 이유는, `TrySpawnX`가 `GameBootstrapper.Services == null` 체크를 `config`/프리팹을 만지기도 전에 가장 먼저 하기 때문이다(생성자 순서 자체가 이미 안전).
  - **함정(발견 후 수정):** `Dungeon.GoldDungeonSessionController._aliveMonsters`는 `HashSet<GameObject>`인데, `List<T>`와 달리 `HashSet<T>`는 비제네릭 `System.Collections.ICollection`을 구현하지 않아 `(ICollection)field.GetValue(...)` 캐스팅이 `InvalidCastException`을 던졌다 — 컬렉션 구체 타입에 의존하지 않도록 `collection.GetType().GetProperty("Count").GetValue(collection)`로 `Count`를 리플렉션으로 직접 읽는 방식으로 고쳤다(`HashSet<T>`/`List<T>` 둘 다 동일하게 동작).
- 회귀 검사 21/21 통과. Play Mode에서 정상 경로(실제 `PoolManager` 존재)도 함께 확인했다 — `GoldDungeonSessionController.Enter(1)`과 `RankPromotionBattleController.Enter(랭크)` 둘 다 여전히 정상적으로 `IsActive=true`가 되고 스폰/정리가 문제없이 동작함을 실제 호출로 검증(리팩터링이 정상 경로를 깨지 않았는지 확인).
- **이번엔 하지 않은 것:** `DungeonSpawnUtility` 자체는 이미 `TryGetPool(out PoolManager)`로 방어적이라 손대지 않았다. 완료 조건 중 "부분 생성 객체 풀 반환/구독 해제"는 이번 수정으로 애초에 부분 생성 자체가 발생하지 않게 되어(성공 아니면 아예 시작을 안 함) 별도 로직이 필요 없어졌다.

### GN. Currency Services Reject Non-Positive Amounts, Clamp Negative Restored Balances (GitHub 이슈 #8)
`Assets/02. Script/Loot/CurrencyService.cs` + `Equipment/EnhancementStoneService.cs` + `Gacha/{SoldierTicketService,SkillScrollService,EquipmentGachaTicketService}.cs` + `Dungeon/BossTokenService.cs` — 재화 6종(골드/강화석/병사 소환권/스킬 주문서/무기 뽑기권/보스 토벌 증표) 서비스 전부가 "재화 도메인별 병렬 서비스"(section AM 등에서 확립된 관례)로 완전히 동일한 형태인데, 그 형태 자체에 `TrySpend*(음수)`가 성공하며 잔액을 오히려 늘리는 버그가 공통으로 있었다(실제 GitHub 이슈로 제보됨).
- **원인:** `TrySpend*(amount)`가 `amount > _current`만 검사했다 — `amount`가 음수면 이 조건은 (`_current`가 음수가 아닌 한) 항상 거짓이라 그대로 통과해버리고, `_current -= amount`가 음수를 빼는 셈이라 사실상 덧셈이 된다. `Add*(amount)`도 부호 검증이 전혀 없어 음수를 넘기면 조용히 잔액을 깎을 수 있었고, 생성자의 `initialX`(세이브 복원값)도 검증 없이 그대로 대입돼 손상된 세이브가 음수 잔액을 만들 수 있었다(이슈 #7과 같은 "손상된 저장값을 안전하게 처리해야 한다"는 결이지만, 여기선 저장값 자체가 아니라 그걸 신뢰하는 소비/지급 API가 문제).
- **수정(6개 파일에 동일 패턴, 새 공유 베이스 없이 각자 적용 — 이 프로젝트의 "병렬 서비스는 나란히 중복" 기존 관례 유지):** `TrySpend*`는 `amount <= 0 || amount > _current`일 때 `false`(0 소비도 무의미한 요청으로 취급해 거부 — "0 소비 정책 일관성" 완료 조건). `Add*`는 `amount <= 0`이면 조용히 no-op — `Character.Health.TakeDamage`/`Heal`이 이미 쓰고 있던 "amount <= 0이면 그냥 리턴" 관례를 그대로 재사용했다(새 패턴을 만들지 않음). 생성자는 `initialX > 0 ? initialX : 0`(또는 `CurrencyService`는 `BigNumber` 비교 연산자로 `initialGold >= BigNumber.Zero ? initialGold : BigNumber.Zero`)로 음수 초기값을 0으로 클램프. `CurrencyService.CanAfford`도 같은 이유로 `amount > 0`을 함께 요구하도록 고쳤다(음수 질의에 오해를 부르는 `true`를 반환하지 않음) — 이슈가 명시적으로 지목한 목록엔 없었지만 `TrySpendGold`와 짝을 이루는 조회 메서드라 함께 처리했다.
- `RegressionChecks.cs`에 6개 검사(재화별 1개, 이슈의 재현 절차(초기 잔액 10 → `TrySpend*(-5)`) 그대로 재현)를 추가했다 — 각각 음수 소비 거부+잔액 불변, 0 소비 거부, 음수 지급 no-op, 음수 초기값의 0 클램프까지 한 번에 확인한다. 리플렉션 없이 실제 public API를 직접 호출한다(서비스가 `MonoBehaviour`가 아니라 `new CurrencyService(events, initial)`처럼 바로 생성 가능해서, 이슈 #20의 `MonoBehaviour` 기반 컨트롤러 검사보다 훨씬 단순했다). 27/27 통과. Play Mode에서 실제 등록된 `CurrencyService`로도 재확인 — `TrySpendGold(-5)`는 `false`+잔액 불변, 이어서 `TrySpendGold(50)`(정상 소비)은 그대로 `true`+정상 차감돼 정상 경로가 안 깨졌음을 확인했다.
- **이번엔 하지 않은 것:** "SO 비용에 런타임 검증 추가"/"잘못된 SO 비용 발견 시 오류 제공"은 이번 수정 범위 밖이다 — 이슈의 재현 절차 자체는 런타임 API(`TrySpend*`/`Add*`)만 겨냥하고 있고, SO 콘텐츠(강화/스킬/가챠 비용 등) 검증은 이 6개 서비스보다 훨씬 넓은 범위(비용을 정의하는 모든 SO 타입)를 훑어야 하는 별도 작업이라 분리했다.

### GO. Catalog Identity: StableId Replaces Array Index in Save Data (GitHub 이슈 #19)
`Equipment/{EquipmentSO,EquipmentCatalogSO}.cs` + `Soldier/{SoldierSO,SoldierCatalogSO}.cs` + `Skill/{SkillSO,SkillCatalogSO}.cs` + `Behavior/{BehaviorProfileSO,BehaviorProfileCatalogSO}.cs` + `Inventory/{InventoryService,EquippedGearService}.cs` + `Soldier/SoldierRosterService.cs` + `Skill/{SkillService,SkillLoadoutService}.cs` + `Editor/StableIdBackfill.cs`(신규) — 세이브 데이터가 `EquipmentSO`/`SoldierSO`/`SkillSO`/`BehaviorProfileSO`를 카탈로그 배열 인덱스로만 식별하던 것을, 절대 안 바뀌는 GUID(`StableId`)로 바꿨다(실제 GitHub 이슈로 제보됨). section FM에서 기마궁수를 카탈로그 중간에서 삭제했을 때 정확히 이 문제(인덱스가 밀려 저장된 세이브가 엉뚱한 항목을 가리킴)로 수작업 리플렉션 마이그레이션이 필요했던 사례가, 이번에 4개 카탈로그 전체에 걸쳐 시스템적으로 해소됐다.
- **4개 SO 타입에 `stableId`(`[SerializeField] string`) + `StableId` 게터 추가**, **4개 카탈로그에 `FindByStableId(string)`**(기존 `FindBySlotAndGrade` 등과 같은 선형 탐색 패턴, 빈/불일치 문자열은 null) 추가 — 기존 `IndexOf`/`GetAt`는 그대로 남겨뒀다(이 4개 카탈로그의 `IndexOf`/`GetAt`를 세이브 코드 밖에서 쓰는 곳이 없음을 grep으로 확인했고, `StageCatalogSO`처럼 인덱스 자체가 의미 있는(순차 진행) 다른 카탈로그는 애초에 범위 밖).
- **`Editor/StableIdBackfill.cs`**(신규, `[MenuItem]`) — 프로젝트의 기존 자산(장비 150·병사 48·스킬 9·행동 프로필 등, 총 203개) 전체에 `SerializedObject`로 `stableId`가 비어있는 것만 새 GUID를 발급한다(멱등 — 몇 번을 돌려도 이미 값이 있는 자산은 절대 덮어쓰지 않음). 이 도구를 실행하지 않으면 모든 항목의 `StableId`가 비어있어 세이브 자체가 전부 실패하므로, 코드 배포와 함께 반드시 한 번 실행해야 한다.
- **6개 서비스의 스냅샷 구조체(`OwnedEquipmentSnapshot`/`EquippedSnapshotEntry`/`OwnedSoldierSnapshot`/`SkillLevelSnapshot`/`SkillCountSnapshot`/`SkillLoadoutSnapshotEntry`)**: `int CatalogIndex` → `string StableId`로 교체(`SoldierRosterService.OwnedSoldierSnapshot`은 `BehaviorProfileIndex`도 `BehaviorProfileStableId`로 함께 교체). `ExportSnapshot`은 `catalog.IndexOf(definition)` 대신 `definition.StableId`를 직접 읽고, `RestoreSnapshot`은 `catalog.GetAt(index)` 대신 `catalog.FindByStableId(id)`를 쓴다.
- **마이그레이션 정책(구버전 세이브는 리셋) — 사용자에게 직접 확인 후 결정:** 완전한 하위 호환 마이그레이션(구버전 int 포맷을 감지해 StableId로 변환 후 재저장) 대신, 훨씬 적은 작업량의 "새 포맷 도입 + 구버전 스냅샷은 리셋"을 선택했다. **별도의 스키마 버전 필드 없이 저절로 동작한다** — 구버전 JSON(`{"CatalogIndex":5,...}`)을 새 구조체(`StableId` 필드)로 `JsonUtility.FromJson`하면 필드명이 안 맞아 `StableId`가 그냥 빈 문자열로 남고, 6개 서비스가 이미 갖고 있던 "definition을 못 찾으면 skip" 방어 코드(`RestoreSnapshot`들)가 그 항목을 조용히 건너뛴다 — 그 결과가 곧 "리셋"이다. 새로 짠 코드는 하나도 없고, 필드 타입을 바꾼 것 자체가 자체 마이그레이션 역할을 한다.
  - **Play Mode에서 실제로 확인된 파급:** 이 세션에서 라이브 검증 중, 로컬 개발 세이브의 `Save.SkillLevelsJson`/`Save.SoldierRosterJson`(둘 다 구포맷으로 저장돼 있었음)을 실제 `RestoreSnapshot`으로 복원해보니 `ExportSnapshot()` 결과가 빈 배열로 나와, 스킬 레벨/병사 로스터가 의도한 대로 조용히 리셋됨을 확인했다 — 설계대로지만 실제 로컬 세이브에 적용된 실제 결과다. `Save.InventoryJson`은 이 세션 중 이미 새 포맷으로 재직렬화돼 있어 영향받지 않았다.

### GS. Save Load Resilience 보완: Gold 오버플로 예외 격리 + 나머지 정수 필드 범위 클램프 (GitHub 이슈 #7 완료 조건 4번 마저 충족)
`Core/BigNumber.cs` + `Save/SaveService.cs` — section GL(이슈 #7 1차 수정)이 `LastActiveUnixTime` 형식 오류와 9개 JSON 블롭 손상만 격리했던 것을 재점검한 결과, 완료 조건 4번("음수·오버플로·누락 값에 안전한 기본값과 범위 검사")이 Gold 필드에서 여전히 뚫려 있는 것을 실제로 재현해 확인했다.
- **원인:** `BigNumber.TryParse`가 `catch (FormatException)`만 잡고 있었는데, `Parse()`가 지수 파트에 쓰는 `long.Parse`는 값이 `long` 범위를 넘으면 `FormatException`이 아니라 별개 계열인 `OverflowException`을 던진다 — Unity Editor에서 `Core.BigNumber.TryParse("1E99999999999999999999", out _)`를 직접 실행해 `OverflowException`이 그대로 새는 것을 확인했다(section GL의 원래 재현 절차와 정확히 같은 클래스의 버그가 `SaveService.LoadGold()`를 거쳐 `Load()` 전체를 다시 중단시킨다). `BigNumber.TryParse`에 `catch (OverflowException)`을 추가해 `Zero`로 폴백하도록 고쳤다.
- **나머지 정수 필드에는 애초에 범위 검사 자체가 없었다:** `ParseLastActiveUnixTimeOrZero`(section GL)만 음수/오버플로를 걸렀을 뿐, `Load()`의 나머지 약 15개 `PlayerPrefs.GetInt` 호출(Gold 레거시 int 폴백, EnhancementStones, Chapter/StageNumber, 6종 플레이어 강화 레벨, RankIndex, SoldierTicketCount, 6종 병사 강화 레벨, SkillScrollCount, EquipmentGachaTicketCount, BossTokenCount)은 레지스트리/plist를 직접 편집해 음수를 넣는 것을 막지 못했다. `SaveService.ClampNonNegative(int)`(0 미만 → 0)와 `ClampAtLeastOne(int)`(1 미만 → 1, `Chapter`/`StageNumber` 전용 — 이 둘은 "기록 없음"이 아니라 카탈로그 인덱스 계산이 깨지는 잘못된 상태이므로 최소값이 0이 아니라 1이어야 한다)를 새로 만들어 `Load()`의 해당 호출 전부와 `LoadGold()`의 레거시 int 폴백에 적용했다.
- `RegressionChecks.cs`에 검사 2개 추가(`BigNumber_TryParse_OverflowExponentFallsBackToZeroWithoutThrowing`, `SaveService_ClampHelpers_NegativeAndBelowMinimumFallBackToSafeDefault`, 51/51 통과) — 후자는 리플렉션으로 `ClampNonNegative`/`ClampAtLeastOne`을 직접 호출해 음수/`int.MinValue`/경계값(0, 1)/정상값을 전부 검증한다.
- Play Mode에서 이슈 재현 절차 그대로 실제 PlayerPrefs를 손상시켜 재확인했다: `Save.Gold.Big`을 `"1E99999999999999999999"`로 손상시킨 뒤 실제 `SaveService.Load()`를 호출해 예외 없이 `Gold = 0E0`으로 복구됨을 확인했고, `Save.Chapter=-7`/`Save.EnhancementStones=-999`로 손상시킨 뒤에도 각각 `Chapter=1`(최소값 클램프)/`EnhancementStones=0`(0 클램프)으로 안전하게 복구됨을 확인했다(모든 테스트는 완료 직후 원래 PlayerPrefs 값으로 복원).

### GU. Gacha Result Reveal: Re-Enable Now Restores Already-Decided Slots Instantly (fixes a real bug found while re-verifying GitHub Issue #10's completion conditions)
`UI/GachaResultRevealController.cs` + `Editor/RegressionChecks.cs` — section GP(이슈 #10 1차 수정)가 "패널 비활성화 시 스폰해둔 슬롯을 전부 풀에 반납"하는 것까지는 정확히 구현했지만, 완료 조건 3번("팝업 닫기·재열기·탭 왕복 후 `_pending`, 버튼 표시, 스크롤 상태가 일관됨")을 재점검하는 과정에서 반납 이후 재활성화 시점의 복원 로직 자체가 아예 없다는 걸 실제로 재현해 확인했다.
- **원인:** `OnDisable()`은 `_spawned`를 비우고 전부 풀로 반납하지만, `_pending`/`_nextIndex`(리빌 진행 상태)는 전혀 건드리지 않는다. `OnEnable()`은 반대로 `_pool` 확보와 ticker 재등록만 하고 `_pending`/`_nextIndex`를 참고해 화면을 다시 채우는 로직이 없었다 — 그 결과 두 가지 실제 버그가 있었다: (1) 리빌 애니메이션이 끝나기 전(예: 10개 중 3개만 보여준 시점)에 탭을 벗어났다 돌아오면, 이미 보여줬던 앞쪽 3개는 다시 나타나지 않고 `Tick()`이 남은 뒤쪽 7개만 이어서 스폰해 총 7개만 보이는 상태가 된다. (2) 리빌이 완전히 끝난 뒤(10/10) 탭을 벗어났다 돌아오면 `_nextIndex >= _pending.Count`라 `Tick()`이 아무 것도 안 하므로 화면이 통째로 빈 채로 남는다 — 내부 상태(`_pending`/`_nextIndex`)는 "다 끝났다"고 말하는데 실제 화면에는 아무 슬롯도 없는 불일치.
- **수정:** `OnEnable()`이 `RestoreAlreadyRevealedSlots()`(신규)를 마지막에 호출한다 — `_pending != null && _nextIndex > 0`이면 인덱스 `0..(_nextIndex-1)`을 애니메이션 없이 즉시 다시 스폰한 뒤 `ScrollToBottom()`한다. 진행 중이든(위 시나리오 1) 완전히 끝났든(시나리오 2) `_nextIndex`가 "이미 결정된 개수"를 그대로 말해주므로 이 로직 하나로 두 시나리오가 함께 해결된다 — `_nextIndex` 자체는 건드리지 않으므로 아직 안 끝난 리빌은 `Tick()`이 정상적으로 이어서 마무리한다. `SpawnNext()`의 스폰 로직을 `SpawnAt(int index)`(신규, `_nextIndex`를 증가시키지 않음)로 뽑아 `SpawnNext`(다음 한 칸, 인덱스 증가)와 `RestoreAlreadyRevealedSlots`(이미 결정된 구간 전체, 인덱스 불변) 둘이 공유한다.

- **함정(작성 중 실제로 겪음) — Edit Mode에서는 `Health.Awake()`가 자동으로 안 불린다:** `Health`에는 `[ExecuteAlways]`가 없어, 이 메뉴 항목 실행 자체가 Edit Mode(Play Mode 아님)인 상태에서는 `GameObject.SetActive(true)`가 `Awake()`를 유발하지 않는다 — 실제 씬(Play Mode)이라면 `PoolManager.Get()`의 `SetActive(true)` → `NotifySpawned()` → `Health.OnSpawned()`(`Revive()` 호출) 순서가 문제없이 통과하지만, Edit Mode에서는 `Awake()`가 아예 안 불려 `_statsProvider`가 `null`인 채로 `Revive()`가 곧장 `NullReferenceException`을 던진다. `pool.Get()`이 반환된 뒤 클론에 `Awake()`를 대신 호출해주는 방식으로는 이미 늦다 — 크래시가 `pool.Get()` **내부**(`NotifySpawned`)에서 먼저 일어나기 때문이다. 해결: `pool.Get()`을 처음 호출하기 전에, `EnsurePool`이 prewarm해둔 인스턴스(아직 비활성, `ObjectPool<T>`의 private `_pool` 스택에 대기 중)를 리플렉션으로 순회하며 각 클론의 `Health.Awake()`를 미리 실행해둔다 — `UI.GachaResultRevealController` 검사(이슈 #10)가 이미 겪은 것과 정확히 같은 함정이자 해법이다. Play Mode에서 같은 검사를 재실행해, 리플렉션으로 미리 호출한 뒤 Unity가 자동으로 다시 호출하는 "이중 Awake"가 되더라도(내부 로직이 매번 같은 값을 재계산할 뿐이라) 문제없이 통과함을 별도로 확인했다.

### GZ. Regression Checks Now CI-Invocable With a Real Exit Code + GitHub Actions Workflow Scaffold (GitHub 이슈 #14)
`Editor/RegressionChecks.cs` + `.github/workflows/regression-checks.yml`(신규) — `RegressionChecks`가 `[MenuItem]` 기반이라 NUnit(Unity Test Runner)이 이 클래스를 전혀 스캔하지 못해, `-runTests`로 EditMode/PlayMode를 돌리면 둘 다 "0건 발견, 결과 Passed"로 집계된다는 게 실제 GitHub 이슈로 제보됐다 — CI가 이 "0건 성공"을 진짜 성공으로 오인하면 회귀 검사를 한 건도 안 돌리고도 초록불이 뜨는 거짓 양성이다. 프로젝트 자체가 asmdef 없이 전부 암묵적 `Assembly-CSharp`인 구조(RegressionChecks 클래스 문서에 이미 명시)라, 이슈가 스스로도 제안한 대로 asmdef/NUnit 전환(중기 과제)은 보류하고 단기 조치만 적용했다.
