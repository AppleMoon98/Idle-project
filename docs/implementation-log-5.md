### EC. CategoryTabBar 버튼 높이 통일 + BottomMenuUI 선택 탭 색상 강조 (opt-in)
`Assets/02. Script/UI/BottomMenuUI.cs` — 두 가지를 함께 손봤다: (1) section EB에서 새로 만든 `CategoryTabBar`의 버튼 높이가 `TierTabBar`(골드뽑기/티켓뽑기/픽업뽑기)와 달랐던 것, (2) 가챠 탭을 눌러도 지금 어느 탭이 선택돼 있는지 색으로 구분이 안 되던 것.
- **높이 불일치 원인:** `CategoryTabBar`의 `HorizontalLayoutGroup.childForceExpandHeight = true`가 버튼에 걸어둔 `LayoutElement.preferredHeight(100)`를 무시하고 컨테이너 전체 높이(150)로 강제 확장시키고 있었다. `childForceExpandHeight = false` + `childAlignment = MiddleLeft`로 바꿔 `TierTabBar`와 동일하게 100으로 맞췄다. **함정:** `execute_code`로 `RectTransform.rect`를 이 변경 직후 곧바로 읽으면 여전히 옛 값(150)이 나온다 — section DT가 이미 남긴 것과 같은 함정으로, `Canvas.ForceUpdateCanvases()`를 먼저 호출해 레이아웃 리빌드를 강제해야 실제 반영된 값을 읽을 수 있다.
- **`BottomMenuUI.highlightSelectedTab`**(신규, 기본값 `false`) + `selectedTabColor`(신규, 기본 골드 `(1, 0.84, 0)`) — `BottomMenuUI`는 하단 메인 탭, 장비/스킬 서브탭, 가챠 카테고리/티어 탭 등 프로젝트 전역에서 재사용되는 범용 셸(section M)이라, 색상 강조를 기본 동작으로 넣으면 안 건드리려던 다른 모든 탭 바까지 함께 바뀐다 — `selectFirstTabByDefault`/`allowToggleClose`(section AM)와 같은 "opt-in 필드, 기본값은 기존 동작 유지" 관례를 그대로 따랐다.
- `RefreshTabHighlights()` — 켜져 있으면 `panels[i].activeSelf`를 기준으로 그 탭 버튼의 `targetGraphic.color`를 `selectedTabColor`(선택됨)/캐싱해둔 원래 색(`_normalTabColors[i]`, `Awake()`에서 1회 캐싱, 선택 안 됨)으로 되돌린다. `OnTabClicked`가 패널을 토글한 직후(열기/닫기 두 경로 모두) 호출하고, `Awake()`가 `selectFirstTabByDefault`로 초기 패널을 연 직후에도 한 번 호출해 시작 상태부터 강조가 반영되게 했다.
- 가챠 팝업의 `CategoryTabBar`(1개, 무기/장갑/갑옷/투구/신발/병사/스킬)와 7개 `TierTabBar`(카테고리별 골드/티켓/픽업) 전부에 `highlightSelectedTab=1`을 켰다 — 다른 `BottomMenuUI` 사용처(하단 메인 탭, 장비/스킬 서브탭 등)는 필드 기본값이 그대로 유지돼 전혀 영향받지 않는다.

### ED. EquipmentSlotPopup: 닫기 버튼 → 정렬 버튼(보유 우선 + 등급 오름/내림차순 토글, 앱 재시작에도 유지)
`Assets/02. Script/UI/EquipmentSlotPopupUI.cs` — 장비 슬롯 팝업의 목록이 항상 등급 오름차순(커먼→레전더리) 고정이었던 것을, 보유 여부를 1순위로 항상 위에 올리고 그 안에서만 등급 오름/내림차순을 토글할 수 있게 했다. 닫기 버튼은 별도 기능이 없어도 이미 `EquippedSlotBarUI.OnDisable()`(장비 탭을 다시 누르면 자동으로 `popup.Close()` 호출, section M)이 닫기를 담당하고 있어 그 자리를 정렬 버튼으로 교체해도 닫는 방법 자체는 사라지지 않는다.
- **정렬 규칙:** `Refresh()`가 `equipmentCatalog.Items`를 `(Owned == null ? 1 : 0)`으로 먼저 `OrderBy`하고(보유 라인이 항상 위), 그 안에서만 `_sortDescending`에 따라 `gradeCatalog.IndexOf(Grade)`를 오름차순/내림차순으로 `ThenBy`/`ThenByDescending`한다 — 토글은 등급 방향만 바꿀 뿐 "보유 우선"이라는 1순위 자체는 절대 안 바뀐다.
- **PlayerPrefs로 직접 영속화(순수 클라이언트 선호도라 `SaveData`/`SaveService` 왕복 없이, `CameraShakeToggleUI`/`ConfirmationPopupUI`와 같은 관례):** `_sortDescending`은 `Awake()`가 `PlayerPrefs.GetInt("EquipmentSlotPopup.SortDescending", 0)`으로 초기값을 읽고, `ToggleSort()`가 뒤집을 때마다 `PlayerPrefs.SetInt`+`Save()`로 즉시 기록한다. `Open()`/`Close()` 어디에서도 리셋하지 않으므로 팝업을 몇 번을 닫았다 열어도, 앱을 완전히 재시작해도 마지막으로 고른 방향이 그대로 유지된다.
- `sortButton`/`sortButtonLabel`(신규 필드, 기존 `closeButton` 필드를 대체) — `ToggleSort()`가 방향을 뒤집고 라벨 텍스트를 `"정렬 ▲"`/`"정렬 ▼"`로 갱신한 뒤 열려있으면 즉시 `Refresh()`한다.
- 씬: 팝업 우상단의 기존 `CloseButton`(빨간 배경, "닫기") GameObject를 그대로 재활용해 `SortButton`으로 개명하고, 배경색을 다른 버튼들과 같은 중립 회색(`0.3, 0.3, 0.3`)으로, 라벨을 `"정렬 ▲"`(폰트 30, 기존 36에서 살짝 축소 — 화살표 포함 텍스트가 좀 더 길어서)로 바꿨다. **함정(씬 저장 시 노이즈, 기존 메모리 노트의 반대 방향 사례):** Play Mode에서 여러 팝업을 열어본 뒤 `manage_scene save`를 호출하면, 비활성 레이아웃 그룹 자식들이 "0으로 찍히는" 기존에 알려진 방향이 아니라 **반대로 실제 계산된(0이 아닌) 좌표값으로 채워지는** 노이즈가 났다(이번엔 대량의 무관한 스테퍼/팝업 RectTransform 앵커가 바뀜) — `git checkout`으로 되돌린 뒤 이 4개 지점(GameObject 이름, Image 색상, Label 텍스트/폰트크기, `EquipmentSlotPopupUI`의 필드 참조)만 텍스트 에디터로 직접 수정하고, `manage_scene load`로 Unity가 그 수정된 파일을 다시 읽어들이게 해서 노이즈 없이 반영했다.

### EE. Confirmation Popup: Enhance/EnhanceAll/Fuse/FuseAll Gated Behind "정말로 진행하시겠습니까?" + Per-Action "다시 보지 않기"
`Assets/02. Script/UI/ConfirmationPopupUI.cs`(신규) + `EquipmentSlotPopupUI.cs`/`EquipmentRowUI.cs`/`EquipmentEnhancementPopupUI.cs` — 전체 강화/전체 합성(`EquipmentSlotPopupUI`)과 개별 강화/합성(행 단위, `EquipmentRowUI`→`EquipmentEnhancementPopupUI`) 네 액션 모두, 실제 서비스 호출 직전에 메시지+체크박스+취소/확인 두 버튼의 범용 확인 팝업을 거치게 했다.
- **`UI.ConfirmationPopupUI`**(신규, 범용/재사용 컴포넌트) — `RequestConfirm(string actionKey, string message, Action onConfirm)` 하나가 공개 API 전부다. `actionKey`별로 독립된 "다시 보지 않기" 여부를 `PlayerPrefs`(`ConfirmationPopup_DontShow_{actionKey}`)에 저장한다 — 이미 켜져 있으면 팝업 없이 `onConfirm`을 즉시 실행하고, 아니면 팝업을 띄워 확인 버튼을 눌러야(체크박스가 켜진 채였다면 그 순간 `PlayerPrefs`에 기록) `onConfirm`이 실행된다. 취소 버튼은 그냥 닫기만 한다(`onConfirm` 호출 안 함). 순수 클라이언트 선호도라 서비스/이벤트 왕복 없이 직접 `PlayerPrefs`를 읽고 쓰는 `CameraShakeToggleUI`(section BA)/`SoundVolumeSliderUI`와 같은 관례를 그대로 따랐다 — 앱을 재시작해도 유지된다(장비 슬롯 팝업 정렬 방향(section ED)이 세션 단위만 유지하는 것과 대비되는 지점 — "다시 보지 않기"는 원래부터 영구 저장이 자연스러운 종류의 설정이라 별도 요청 없이도 PlayerPrefs를 택했다).
- **네 호출부 전부 같은 패턴(팝업 참조를 못 구하면 확인 없이 즉시 실행, 방어적 폴백):**
  - `EquipmentSlotPopupUI.EnhanceAll()`/`FuseAll()` — 각각 `actionKey="EnhanceAll"`/`"FuseAll"`, 메시지 `"전체 강화/합성을 진행합니다. 정말로 진행하시겠습니까?"`.
  - `EquipmentRowUI`의 `fuseButton`이 새로 얻은 `onFuseRequested`(신규 선택적 콜백, 기존 `onEnhanceRequested`와 정확히 같은 모양 — 없으면 예전처럼 `EquipmentFusionService.TryFuse`를 즉시 호출) → `EquipmentSlotPopupUI.RequestFuseConfirm`이 `actionKey="Fuse"`로 확인을 받은 뒤 `TryFuse`.

`Assets/02. Script/Combat/CavalryCharge.cs` — 돌진이 명중하기 직전에 한 번 멈칫하고 처음 속도부터 재돌진하는 문제가 보고돼 확인했다. 사용자가 "거리 비례 돌진 시간을 넣었는데 계산이 잘못된 것 같다"고 정확히 짚었다 — `BeginCharge` 시점 스냅샷 거리로 미리 계산해두던 총 돌진 제한 시간(`_currentChargeDuration`, section BQ) 자체가 원인이었다.
- **원인:** `BeginCharge`는 그 순간 위협까지의 직선 거리를 `CalculateTimeToCoverDistance`(가속 구간 + 등속 구간 운동방정식, 수학적으로는 정확했다)에 넣어 "이 거리를 주파하는 데 걸리는 시간 + chargeOverrunDuration"을 돌진 전체의 제한 시간으로 미리 확정해뒀다. 문제는 위협(특히 플레이어)이 돌진 도중에도 계속 움직인다는 것 — `TickCharging`의 조향 로직이 매 틱 위협의 살아있는 위치로 방향을 보정하므로 실제 이동 경로는 스냅샷 시점의 직선 거리보다 길어질 수 있는데, 제한 시간은 그 스냅샷 거리 기준으로 이미 고정돼 있었다. 그 결과 실제로 따라잡아 명중하기도 전에 제한 시간이 먼저 끝나 `EndCharge()`가 호출되고, `Positioning`으로 돌아갔다가(대개 여전히 `chargeStartDistance` 밖이라) 곧바로 `BeginCharge`가 다시 호출돼 `chargeStartSpeed`부터 재가속하는 흐름이 "박치기 직전에 한 번 움찔 멈추고 재돌진"하는 것으로 보였다.
- **수정:** 돌진 종료 조건을 "얼마나 이동했는가"가 아니라 "실제로 명중했는가"로 바꿨다. `_hitElapsedMark`(신규 필드)가 이번 돌진에서 첫 명중이 발생한 순간의 `_chargeElapsed` 값을 기록하고(`CheckChargeHit`에서 `_hasHitThisCharge`가 처음 `true`로 바뀌는 순간에만 기록), `ShouldEndCharge()`(신규, `TickCharging`이 매 틱 호출)는 아직 한 번도 못 맞혔으면 `maxChargeDuration`(안전망 — 위협이 끝내 안 맞고 계속 피하는 극단적 경우에만 발동)까지는 무조건 계속 돌진하고, 이미 맞혔으면 그 순간부터 `chargeOverrunDuration`만큼만 더 달리고 끝낸다. 위협이 아무리 이동해도 실제로 따라잡을 때까지는 조기 종료되지 않는다. `CalculateTimeToCoverDistance`/`_currentChargeDuration`/`minChargeDuration`(이제 전부 불필요)는 제거했다 — 각 프리팹(`Monster_Cavalry`/`_Elite`/`_Boss`/`_Rescue`)에 남아있는 `minChargeDuration`의 직렬화 값은 클래스에 필드가 없으므로 다음 저장 때 조용히 무시된다(section CC와 동일한 무해한 정리).
- Play Mode에서 리플렉션으로 `ShouldEndCharge()`를 직접 호출해 5가지 경계 시나리오(미명중 상태에서 안전망 시간 전/후, 명중 직후, overrun 경과 전/후, `maxChargeDuration` 근처에서 명중해도 overrun 윈도우는 그대로 보장되는 경우)를 검증해 전부 기대값과 일치함을 확인했다.

### ET. StageProgression: Deferred LoadStage Prevents Same-Frame Kills From Being Orphaned Mid Stage-Transition
`Assets/02. Script/Stage/StageProgression.cs` — 스테이지 클리어/사망 후퇴 순간 같은 프레임에 몰린 다른 처치 이벤트가 조용히 유실될 수 있는 재진입 버그를 발견해 고쳤다("적 수가 모자라서 클리어가 안 된다"는 실사용 제보를 조사하던 중, 정확히 그 증상은 아니지만 인접한 진짜 버그로 발견됨).
- **원인:** 마지막 처치 하나가 `Stage.StageProgressTracker.OnCharacterDied` → `StageClearedEvent` 발행 → `StageProgression.OnStageCleared` → `StageController.LoadStage`까지 전부 **같은 `CharacterDiedEvent.Publish` 호출 스택 안에서 동기적으로** 실행됐다. `LoadStage`가 부르는 `EndCurrentStage()`는 현재 `StageProgressTracker`를 그 자리에서 즉시 `Dispose()`(EventBus 구독 해제)한다. `Core.EventBus.Publish`는 매 호출마다 그 순간의 구독자 목록을 스냅샷 뜨는 구조라(section DV), 같은 프레임·같은 호출 체인 안에서 **다른 몬스터의 사망 이벤트가 그 직후에 또 발행되면**(예: 광역 스킬이 여러 마리를 한 foreach에서 연달아 처치, 또는 같은 프레임에 여러 공격자의 쿨다운이 동시에 끝나는 경우) 그 사망은 이미 사라진 옛 트래커도, 아직 구독 전인 새 트래커도 받지 못해 아무 곳에도 집계되지 않고 사라진다. 플레이어 사망으로 인한 스테이지 후퇴(`OnCharacterDied`)도 같은 구조로 `LoadStage`를 동기 호출하고 있어 동일한 문제를 안고 있었다.
- **수정:** `StageProgression`이 `ITickable`을 구현해 `Core.TickerRegistration`에 스스로 등록/해제하도록 하고, `OnStageCleared`/`OnCharacterDied` 두 곳 모두 `_controller.LoadStage(...)`를 그 자리에서 바로 부르는 대신 `_pendingLoadStage`에 목표 스테이지만 적어둔다. 실제 `LoadStage` 호출은 `Tick()`에서 다음 프레임에 수행한다 — 그러면 같은 프레임에 몰린 나머지 사망 이벤트가 트래커 교체 전에 전부 원래 트래커에 정상 도달한 뒤에야 `Dispose`/재구독이 일어난다. `JumpTo`/`JumpToHighestCleared`/`JumpToBreakthroughFrontier`는 UI에서 직접 호출되어(EventBus 재진입이 아님) 그대로 즉시 `LoadStage`한다 — 지연시키면 그만큼 조작감이 나빠질 뿐 재진입 위험이 없는 경로이기 때문.
- **주의 — 이 수정이 설명하는 것과 설명하지 못하는 것:** 이 레이스는 스테이지 전환이 실제로 발생하는 그 순간에만 발동하고, 전환이 일어나면 즉시 완전히 새로운 `StageProgressTracker`(요구 마릿수도 처음부터 재계산)가 생기므로, "같은 스테이지 시도에서 계속 몇 마리가 부족하다"처럼 지속되는 상태를 만들지는 않는다 — 딱 그 전환 경계의 사망 하나(또는 몇 개)가 어딘가로 증발하는 형태다. 애초에 이 수정을 촉발한 "1-13에서 2마리 부족" 제보는 트래커의 요구/등록 마릿수 자체가 항상 정확히 일치함을 별도로 검증해(스테이지 로드 직후, 던전 중단 후 재개 등 여러 시나리오로 재현 시도) 이 재진입 버그와는 무관한 것으로 판단됐다(화면 밖으로 카이팅한 유닛을 못 찾은 것으로 추정) — 이번 수정은 그 조사 과정에서 별도로 발견된, 실재하는 재진입 버그를 선제적으로 막은 것이다.
- Play Mode에서 `Time.timeScale=0`으로 얼려둔 채 20마리 웨이브를 전부 처치해 마지막 처치가 `StageClearedEvent`를 동기 발행하는 순간, `StageController._tracker`가 **같은 호출 안에서는 교체되지 않고 그대로 유지**되는 것을 리플렉션으로 확인했다. 이어서 실제 프레임을 한 틱 흘려보내자 트래커가 다음 스테이지용 새 인스턴스로 정상 교체되고 새 웨이브가 올바른 마릿수로 스폰되는 것도 확인했다.

  - **부대(SoldierDeploymentService.SquadCount) 개념은 스폰 위치와 완전히 분리됐다** — 부대는 여전히 배치 UI(section DF~DJ)/전술 선택(section DL, `SquadTacticService`)/부대 이동속도 동기화(`SquadMovementSyncService`)의 단위지만, 물리적으로 어디에 서서 스폰되는지는 이제 부대 소속과 무관하게 오직 사거리로만 정해진다. 방패벽 전술의 리더/팔로워 페어링(`SquadShieldWallCoordinator`)도 스폰 위치가 아니라 컴포넌트 존재(`ShieldGuard`/`FormationFollower`) + 배치 그리드 상 행 관계(`GetProtectorSlotIndex`, section EY)로만 이뤄지므로 영향받지 않는다.
- **`Soldier.SoldierSpawnSlot`**은 더 이상 스폰 위치를 스스로 계산하지 않는다(`SquadSpawnLayout`/`SquadSpawnRowMode`/`SquadSpawnRowService` 완전 삭제) — `slotIndex` 하나만 갖고, 계산된 좌표를 담아 돌려줄 스크래치 앵커 `Transform`(`ResolvePositionAnchor(Vector3 position)`, 지연 생성 후 매번 재배치)만 소유한다. `Soldier.SoldierSpawnUtility.TrySpawnAssigned`도 위치를 스스로 구하지 않고 호출부가 미리 계산한 `Vector3 position`을 그대로 받는다.
- **`Soldier.SoldierRespawner`**가 배치 계산의 실제 진입점이다 — `ComputePlacements(SoldierSpawnSlot[] slots)`(공개, `CameraFollowService` 경계 조회 + `SoldierGridPlacement.ComputePlacements` 위임)를 스폰/리셋 호출마다 한 번씩 계산해 전체 슬롯의 좌표 맵을 얻고, `TrySpawnSlot(slot, position)`으로 그 맵에서 조회한 좌표에 스폰한다. `ResetPositions(slots)`(현재 살아있는 병사만 재배치)/`ResetForNewStage(slots)`(체력 리바이브 + 빈 슬롯 재배치) 둘 다 이 패턴을 따른다. `Soldier.SoldierSpawner`는 초기 전체 스폰(`TrySpawn`)과 개별 슬롯 재편성(`RefreshSlot`) 시점에 매번 `ComputePlacements`를 새로 호출한다 — 슬롯 하나의 배정 변경도 전체 사거리 정렬 순서를 바꿀 수 있어(예: 사거리가 가장 짧은 유닛이 새로 배치되면 그 뒤 모든 유닛의 행이 한 칸씩 밀림), "슬롯 하나만 보고 자기 위치를 안다"는 방식 자체가 성립하지 않는다. 다만 이미 스폰돼 살아있는 다른 병사들의 위치는 재편성만으로는 옮기지 않는다(교전 중 순간이동은 부자연스러움) — 실제로 전원이 다시 정렬되는 시점은 `ResetPositions`/`ResetForNewStage`가 호출되는 스테이지 전환/던전 진입 같은 명시적 리셋 지점뿐이다.
- **`Stage.StageController`**는 4방향 스폰 지점 배열(`topSpawnPoints`/`bottomSpawnPoints`/`leftSpawnPoints`/`rightSpawnPoints`)과 `tacticUnitSpacing`/`tacticRowSpacing` 필드를 전부 제거했다. 대신 `CameraFollowService`를 `Start()`에서 조회해 `MonsterSpawner` 생성자에 전달한다. `GetLeftSpawnPoint`/`GetRightSpawnPoint`/`GetTopSpawnPoint`(`Transform` 반환, 배열 순환 인덱싱)는 `GetLeftEdgePosition`/`GetRightEdgePosition`/`GetTopEdgePosition`(`Vector3?` 반환, `SpawnGridLayout`의 화면 가장자리 계산 위임)으로 교체됐다 — `Soldier.SquadRaidCoordinator`(부대 단위 좌우/후방 습격 전술, 스테이지 시작 후 일정 시간 뒤 화면 가장자리에 병사를 재배치하는 별도 시스템)가 이 API의 유일한 외부 소비자라, 그쪽 호출부(`ExecuteRaid`)도 `Vector3?`/`Quaternion.identity` 기반으로 함께 갱신했다 — 습격 전술 자체의 판정/타이밍 로직(`_isPending`/`_remaining`/`GetDelay` 등)은 이번 변경과 무관하게 그대로다.
- **씬 정리:** `StageController` 밑의 4방향 스폰 지점 GameObject(`SpawnPoint_Top_Left`/`_Top_Right`/`_Bottom_Left`/`_Bottom_Right`/`_Left_1~3`/`_Right_1~3`, 10개)와 `SoldierSpawner` 밑의 옛 정적 스폰 지점(`SoldierSpawnPoint_1~72`, `SoldierSpawnPoint_Front_1~60`, 총 132개)을 전부 삭제했다 — 둘 다 더 이상 어떤 코드도 참조하지 않는다. `SoldierSpawner.slots` 배열은 72개(스폰 지점 개수에 종속되던 예전 한계)에서 `SoldierDeploymentService.SquadCount × SlotsPerSquad`(120) 전체로 확장했다 — 그리드가 물리적 지점 개수에 더 이상 얽매이지 않으므로, 배치 UI가 여는 슬롯(현재 랭크 콘텐츠 기준 최대 40, section DJ)을 넘어서도 향후 랭크 콘텐츠가 늘어나면 코드 변경 없이 전부 스폰 가능하다.
