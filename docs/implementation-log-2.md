CLAUDE.md의 "### X. Monster Targeting..."에서 "### AO. Third Rank"까지의 상세 구현 기록입니다. 섹션 번호는 CLAUDE.md 전체 기준(3. Architecture & Technical Rules 하위)과 이어집니다.

### X. Monster Targeting Simplified to Nearest-Ally, Real Attack Range, Visual Tiering (implemented — supersedes the `MonsterTargetSelector` description in section F)
`Assets/02. Script/Combat/MonsterTargetSelector.cs` — replaced the old claim-priority chain (player-if-currently-targeted, else claiming soldier, else player fallback) with a plain nearest-target scan:
- `ChooseTarget()` runs `Physics2D.OverlapCircleAll(position, detectionRange, allyLayerMask)` and returns the nearest live `Health`, falling back to `PlayerTransform` if nothing is in range — the same nearest-wins idiom `EnemyTracker` already used for the opposite faction.
- `allyLayerMask` points at the `Player` layer; `Soldier`/`Soldier_Ranged` prefabs sit on that layer (not `Default`) so one scan naturally covers both the Player and any Soldier.
- `Combat.PlayerTargetTracker`/`Combat.PlayerTargetMarker` and `Soldier.SoldierTargetRegistry.TryGetClaimant` were deleted along with the old priority chain. `SoldierTargetRegistry.IsClaimedByOther`/`SetClaim` remain — still used by `SoldierEnemyFilter` for soldier-vs-soldier target spreading, an unrelated concern.
- Monster's own attack uses the same `Attacker` + `MeleeAttackBehavior` composition Player/Soldier use, targeting the `Player` layer. `MonsterTargetSelector.Retarget()` also sets `CharacterMover.StoppingDistance = Stats.AttackRange` (mirroring `EnemyTracker`), so monsters stop at range instead of walking onto the target's position. All three monster tiers' `CharacterStatsSO.AttackRange` is `2.5` (matching melee `Soldier`).
- `Monster_Elite.prefab`/`Monster_Boss.prefab` get a purely visual `transform.localScale` bump (1.2x / 1.5x) so they read as tougher at a glance. `AttackRange` lives on `CharacterStatsSO`, entirely independent of transform scale, so this doesn't touch combat reach. Each prefab's `HealthBar` child is counter-scaled (`1/scale`) so the bar itself stays a consistent on-screen size instead of growing with the body.

### Y. Rank Gating: Startup Promotion Replay & Locked Soldier Tab (implemented — supersedes part of section U)
- `RankService.SeedRank(rankIndex)` sets the in-memory rank silently (no event) from the save; called in `GameBootstrapper.Awake()` right after `SaveService.Load()`, strictly before offline progress runs. **Gotcha this avoids:** `OfflineProgressService.CalculateAndApply()` runs *before* `RestoreLevel` in `Start()`, and if simulated offline progress advances the record, `RankService.OnHighestStageCleared` would re-derive every rank from scratch as if newly earned (`isRestore: false`) — replaying the rank-up popup on every launch for ranks already reached long ago. `SeedRank` avoids this by pre-seeding the rank before offline progress ever runs.
- `UI.SoldierPanelGateUI` (on the `SoldierPanel` bottom-tab panel) — while the current rank is below a configured `requiredRank`, shows a locked message instead of the roster/deployment lists. The message is built from `requiredRank.RequiredStage` (`"{chapter}-{stageNumber} 스테이지 클리어 후 오픈됩니다."`), so it tracks the real requirement with no code change if the rank/stage is retuned. Subscribes `RankChangedEvent` so reaching the rank while the tab is open unlocks it immediately.

### Z. Soldier Deployment Fixes (implemented — the "& Equipment" half of this section's original title described Soldier.SoldierEquippedGearService, deleted in full along with the rest of the soldier-only equipment system; see the final section of implementation-log-4.md)

### AA. Gacha Popup: Categories, Tiers & Multi-Pull (implemented)
`Assets/02. Script/Gacha/` + `Assets/02. Script/UI/` — a full-screen modal gacha screen, replacing the inline pull button that used to live in the soldier roster panel:
- The bottom tab bar's fifth slot ("뽑기") is wired directly to `UI.GachaPopupUI.Open()` rather than through `BottomMenuUI`'s normal panel array, since this popup needs to cover the tab bar itself.
- Two-level tab structure, built by nesting the generic `BottomMenuUI` shell twice: an outer category row (무기 뽑기 / 병사 뽑기) and, per category, an inner tier row (일반 / 고급 / 유료). Adding a category or tier is just one more button+panel entry in an inspector array. Only "일반" is wired to a working table on either side; 고급/유료 are placeholder-only ("준비 중").
- `EquipmentGachaPoolEntry`/`EquipmentGachaTableSO`/`EquipmentGachaService` mirror the pre-existing `GachaPoolEntry`/`GachaTableSO`/`GachaService` (soldier gacha) structure, but spend gold instead of soldier tickets and grant the result by republishing `Loot.Events.ItemDroppedEvent` (the same path `EquipmentFusionService` reuses) rather than touching `InventoryService` directly.
- Both services expose `Pull(tierIndex, count)`: loops up to `count` times, stopping the moment currency runs out (partial success), and publishes one aggregated `SoldierPulledEvent`/`EquipmentPulledEvent` (`IReadOnlyList<T>`) rather than one event per pull. `SoldierPulledPopupUI`/`EquipmentPulledPopupUI` group the batch by item name and show per-item counts.
- **Gotcha:** Canvas draw order is sibling-index based (later siblings draw on top) — a result popup added to the hierarchy *before* the popup that triggers it will render behind that popup. Keep result-notification popups as later Canvas siblings than whatever opens them.

### AB. UI Layout & Discoverability Fixes (implemented)
- Equipment row's biggest tap target (the item name) opened a read-only detail popup with no equip action; the real equip trigger was the row's own background `Button`, mostly covered by its `HorizontalLayoutGroup` children. Added an explicit "장착" button (same pattern as fuse/enhance), disabled and reading "장착됨" once that line is currently worn.
- **List popups need scroll containers or content silently overflows/vanishes.** Any scrollable list in this project follows one standard structure: `RowContainer(ScrollRect) → Viewport(RectMask2D) → Content(VerticalLayoutGroup + ContentSizeFitter)`. A `sizeDelta` that isn't set relative to its parent can silently collapse a container to zero height with rows still logically present but invisible.

### AC. Enhancement System Expansion: New Stats & Critical Hits (implemented)
`Assets/02. Script/Enhancement/` + `Assets/02. Script/Character/` + `Assets/02. Script/Combat/Attacker.cs`:
- `EnhancementStatType` gained `AttackSpeed`, `MoveSpeed`, `CriticalChance`, `CriticalDamage`. `CharacterStatsSO`/`RuntimeStats` gained matching `CriticalChance` (default `0`) and `CriticalDamageMultiplier` (default `0.5` — a critical hit deals `AttackPower * (1 + CriticalDamageMultiplier)`).
- `Combat.Attacker` rolls `Random.value < Stats.CriticalChance` on every attack and scales damage accordingly before calling `IAttackBehavior.Execute`. Applies to Player, Soldier, and Monster alike, but monsters never crit in practice since their base `CriticalChance` is `0`.
- `Character.RuntimeStatApplier` takes the owning character's *base* `CharacterStatsSO` alongside its `RuntimeStats`, because `AttackSpeed`/`MoveSpeed` are "N% of the character's own base value per level" rather than a flat delta — `CriticalChance`/`CriticalDamage` stay flat additive (percentage-point) since they have no meaningful "base" to scale from.
- `EnhancementConfigSO.CostIncreasePerLevel` (linear, `int`) was replaced with `CostMultiplier` (compound, `float`) — next cost is `BaseCost * CostMultiplier ^ level`, computed in `double` and saturated at `int.MaxValue` rather than cast straight to `int` (a naive `int` cast overflows/wraps negative around level 47 at a 1.5x multiplier, which makes `CurrencyService.TrySpendGold` read the negative cost as "affordable" — enhancement becomes free and net gold-positive). `MaxLevel = 2000` on every stat (previously 50) so the compound curve stays affordable across a large level range, since monster HP scaling (section X) grows *linearly* with stage index. `AttackPower`/`MaxHealth`'s cost curve was later moved off compound entirely onto a tiered-linear one — see section AL for current tuned values across all six stats.
- `AttackSpeed`/`MoveSpeed`: 1%/level, capped at level 20 (±20% off base). `CriticalChance`: 0.1%/level to level 500. `CriticalDamage`: 0.5%/level to level 300 (the crit bonus fraction, not total multiplier).
- `UI.StatDisplayNames.FormatValue(statType, value)` — formats the four percentage-based stats as `"N%"` in `StatRowUI` instead of a raw decimal.
- `Save.SaveData`/`SaveService` has one level field per new stat, following the same per-stat-field pattern as `AttackPowerLevel`/`MaxHealthLevel`.

### AD. Offline Progress: Difficulty-Accurate & Repeat-Only (implemented — supersedes section P)
`Assets/02. Script/Offline/OfflineProgressService.cs`:
- The offline combat simulation computes monster health via `_difficultyConfig.GetMultiplier(_catalog.IndexOf(stage))`, folded in exactly like `StageMonsterScaler` does for real combat. **Gotcha this avoids:** using each monster's flat `CharacterStatsSO.MaxHealth` directly (ignoring the per-stage-index multiplier real combat applies) makes the simulation effectively always fight stage-1-strength monsters — a long offline window could then blow through stages the player could never actually clear live.
- The simulation is repeat-only: it simulates the player's *highest-cleared* stage on repeat for the entire time budget and never advances the record or resume position past it, always resuming there afterward regardless of whatever death-regressed position (`StageProgression`, section Q) was current when the player left. `HighestStageClearedEvent` is never published from here, since the record never changes.
- `Offline.Events.OfflineProgressCalculatedEvent.TimesCleared` counts repeat-clears of the one stage, not newly-conquered stages.

### AE. War Objective Progress & Pre-Climax Warmup Warning (implemented)
`Assets/02. Script/War/` + `Assets/02. Script/UI/` — a readable progress signal for the four War objectives (`WarObjectiveType` = `Annihilation`/`StructureCapture`/`BossDefeat`/`CargoProtection`) and a 3-second warning countdown before a climax fight's judgment starts:
- `IWarObjective.Progress01` (0~1) — `AnnihilationObjective`/`BossDefeatObjective` return `IsCompleted` as 0/1 (no continuous progress); `CargoProtectionObjective` returns `elapsed / protectDuration`; `StructureCaptureObjective` averages `WarStructure.Control` across `requiredStructures`.
- `WarBattleController` doesn't activate the objective the instant a climax stage loads. It starts a `climaxWarmupDuration` (default 3s) countdown, publishing `War.Events.WarClimaxWarmupStartedEvent(objectiveType, chapter, duration)`; once it hits zero, activates the objective and publishes `WarClimaxStateChangedEvent(true, ...)`. `warZoneRoot` (structures/cargo) activates immediately so the battlefield is visible during the countdown, but `ResetForNewAttempt()` — and therefore judgment — only runs once warmup ends, so any progress ticked during the countdown is wiped before real judgment starts.
- `War.Events.WarClimaxStateChangedEvent(IsClimax, ObjectiveType, Chapter)` fires when the fight starts (after warmup) and when climax is left. `War.Events.WarObjectiveProgressChangedEvent(Progress01)` fires only while the objective is active, whenever `Progress01` changes.
- `UI.WarBattleHudUI` subscribes both events; shows an objective banner always, a progress gauge only for `StructureCapture`/`CargoProtection` (`Annihilation` already has `StageInfoUI`'s remaining-monster count as an equivalent signal, `BossDefeat` has the boss's own `HealthBarUI`). `StageInfoUI` itself also subscribes `WarClimaxWarmupStartedEvent`/`WarClimaxStateChangedEvent` and suppresses its "남은 몬스터: X/Y" line whenever the active climax objective isn't `Annihilation` — that count isn't the real clear condition for the other objective types and would otherwise mislead the player.
- `UI.WarClimaxWarningUI` subscribes `WarClimaxWarmupStartedEvent` (show banner + countdown) and `WarClimaxStateChangedEvent` (hide unconditionally — covers both "fight started" and "player left climax mid-warmup" with one rule).
- **Testing gotcha (do not repeat):** publishing a synthetic `Stage.Events.StageClearedEvent`/`StageChangedEvent`/`CharacterDiedEvent` directly on the live `EventBus` during a Play Mode session is indistinguishable to `StageProgression`/`SaveService` from a real clear/death — `StageProgression` blindly advances its own tracked index on any `StageClearedEvent` without checking payload against what's actually loaded, and `SaveService` writes every `StageChangedEvent` straight to `PlayerPrefs`. Prefer reflection-invoking the private method that owns the judgment logic directly (bypassing the EventBus) when verifying detection logic during Play Mode.

### AF. Player Manual Control Toggle (implemented)
`Assets/02. Script/Character/` + `Assets/02. Script/UI/` — lets the player switch between auto-chase movement and direct tap-to-move. General-purpose and independent of War or any other system — always available.
- `Character.PlayerControlMode` enum `{ Auto, Manual }`; `Character.Events.PlayerControlModeChangedEvent`; `Character.PlayerControlModeService` (`IManager`/`IService`) holds the current mode, `Toggle()`/`SetMode()` publish on change.
- `Character.PlayerManualMover` (Player-only, `ITickable`) — on `Manual`, disables the Player's own `EnemyTracker` to take over `CharacterMover.Target` (same "disable the sibling tracker, drive `CharacterMover` directly" pattern `Soldier.SoldierBehaviorController` uses for ranged kiting/off-screen return, section W). On a tap that isn't over UI, converts screen position to world point and points `CharacterMover.Target` at a scratch, unparented Transform there — unparented for the same reason `SoldierBehaviorController._returnAnchor` must be (a child anchor's world position would recede as the character approaches it). On `Auto`, re-enables `EnemyTracker`. `Attacker` (auto-attack) is untouched by mode either way.
- `UI.PlayerControlModeToggleUI` — persistent top-right "자동"/"수동" button, positioned at Canvas sibling index 3 (ahead of every `*Popup`) so popups always draw on top of it.

### AG. War Boss Unique Patterns (implemented)
`Assets/02. Script/War/Boss/` — telegraphed AoE attacks for the War-climax boss on top of the normal `Monster_Boss` composition, without touching `Monster_Boss` itself:
- `War.Boss.WarBossPatternSO` (data) — one pattern: `TelegraphDuration`, `Radius`, `Damage`. Pattern variety is pure data, not a C# type per pattern.
- `War.Boss.WarBossPatternRunner` (`ITickable`, `IPoolable`) — cycles its `patterns` array on `intervalBetweenPatterns`; each cast snapshots the nearest ally's (Player/Soldier layer) position, shows a `WarBossTelegraphIndicator` there, and after `TelegraphDuration` applies `Damage` via `Physics2D.OverlapCircleAll` + `Health.TakeDamage` to whatever's still in `Radius`. All judgment/timing is owned here, never by the indicator (same `Attacker`/`WeaponSwing` split as melee).
- `War.Boss.WarBossTelegraphIndicator` (`IPoolable`, pure visual) — a world-space `SpriteRenderer` whose circular sprite is generated once in code (no art asset), cached `static` and shared across every instance.
- `WarBoss.prefab` — a duplicate of `Monster_Boss.prefab` plus `WarBossPatternRunner` — composition reuse, no inheritance.

### AH. Skill System (implemented — supersedes the "SkillPanel is a scriptless placeholder" note in section M)
`Assets/02. Script/Skill/` — three fixed auto-cast skills the player levels up with gold + enhancement stones; deliberately does not know "Player" exists any more than Enhancement does:
- `SkillSO` — data asset: `DisplayName`, `Icon`/`IconTint`, `Cooldown`, `MaxLevel`, a gold/stone cost curve (`GoldCostBase`/`GoldCostIncreasePerLevel`, `StoneCostBase`/`StoneCostIncreasePerLevel` — linear, same shape as `EquipmentEnhancementConfigSO`), and `GetMagnitude(level)` = `EffectValueBase + EffectValuePerLevel * level`.
- `SkillCatalogSO` — flat `SkillSO[]`, same `IndexOf`/`GetAt` shape as every other catalog; lets `SaveService` identify a skill by index instead of an asset reference.
- `ISkillEffect.Execute(origin, magnitude)` mirrors `Combat.IAttackBehavior`'s strategy pattern — `SkillSlot` never knows what a skill does, only when to call it. Three implementations under `Skill/Effects/`: `AreaDamageSkillEffect` (`Physics2D.OverlapCircleAll` around the caster), `SingleTargetStrikeSkillEffect` (nearest live target in range), `SelfBuffSkillEffect` (temporary `AttackPower` bonus on the caster's own `CharacterStatsProvider`; re-casting reverts the previous bonus first instead of stacking).
- `SkillSlot` (`MonoBehaviour`, `ITickable`) reads the current level from `SkillService` fresh on every cast (never caches it, so a mid-cooldown level-up takes effect on the very next cast). **Gotcha:** `Tick` must read the level *before* touching `_elapsed`/cooldown and return immediately if `level <= 0` — otherwise an un-leveled (not-yet-learned) skill still auto-casts at its flat `EffectValueBase` on a fixed cooldown regardless of player power, indistinguishable from a real hit sitting among otherwise-scaling auto-attack numbers.
- `SkillService` (`IManager`/`IService`) — `TryLevelUp(definition)` requires both `Loot.CurrencyService.TrySpendGold` and `Equipment.EnhancementStoneService.TrySpendStones` to succeed (no partial spend if either is short). Keeps only level state, never touches `RuntimeStats`/damage (same "service owns state, component applies effect" split as `EnhancementService`/`StatEnhancementReceiver`). Takes only `EventBus` as a constructor dependency and looks up the two currency services via `GameBootstrapper.Services` at `TryLevelUp` time instead, since `SkillService` must exist *before* `SaveService` (a circular-dependency workaround).
- Save: `SkillService.SkillLevelSnapshot[]` (catalog index + level) serialized as one JSON blob (`SaveData.SkillLevelsJson`). **Gotcha:** a save-blob struct/class used with `JsonUtility` must be marked `[Serializable]` — without it, `JsonUtility` silently produces an empty array on save with no error anywhere; the level-up itself still works in-memory (gold/stones spent, level increments) but resets to 0 on next load.
- UI: `UI.SkillSlotBarUI` + `UI.SkillDetailPopupUI` — icon-bar-then-popup shape like `Equipment.EquippedSlotBarUI`/`EquipmentSlotPopupUI`, simpler since a skill slot has no "which owned copy is equipped" concept.
- The original fixed 3-slot loadout was superseded by the 6-slot equip system in section AQ.

### AI. Content Editor: In-Editor Art & Catalog Tool (implemented, Editor-only)
`Assets/02. Script/Editor/` — a `Tools/Idle Project/Content Editor` window consolidating placeholder-art assignment and catalog-SO hand-editing into one place. Pure Editor tooling: the `Editor/` folder name excludes it from player builds.
- `ContentEditorWindow` — two tabs: **World Sprites** and **Catalog Editor**.
- **World Sprites tab** — a fixed list of `ArtAssignmentTarget`s, each hiding *how* a sprite gets read/written for that kind of target: `PrefabSpriteTarget` (prefab assets, via `PrefabUtility.LoadPrefabContents`/`SaveAsPrefabAsset`), `SceneSpriteTarget` (the `Player` GameObject, which lives in the scene rather than as a prefab asset), `ScriptableObjectIconTarget` (SO `icon` fields, via `SerializedObject`). Equipment/Stage catalogs are excluded — too many for a flat list (handled by Catalog Editor) or generated by script (not meant for hand editing).
- **Catalog Editor tab** (`CatalogEditorPanel` + `CatalogRegistration`) — generic editor for any "one SO holding a flat array of item SOs" catalog in the project. `CatalogRegistration` is just `{ DisplayName, CatalogAssetPath, ArrayFieldName, ItemType }` — adding a catalog to the tool is one entry, no new code. Every field on a selected item's SO renders via `SerializedObject` + `EditorGUILayout.PropertyField` (iterating `SerializedObject.GetIterator()`, skipping `m_Script`), so new fields on any catalog's item type show up automatically.
- **Gotcha:** `SerializedProperty.DeleteArrayElementAtIndex` on an array of object references only *nulls out* the slot on the first call if the reference wasn't already null — it takes a second call to actually shrink the array. Skipping this leaves a `null` gap in the array instead of removing the slot.

### AK. Damage Numbers (implemented)
`Assets/02. Script/Combat/` — floating combat text shown at the moment damage lands:
- `Character.Health.TakeDamage(float amount, bool isCritical = false)` publishes `Character.Events.DamageAppliedEvent(target, amount, isCritical)` alongside its existing `CharacterHealthChangedEvent`/death handling.
- `Combat.IAttackBehavior.Execute` requires `bool isCritical` (not optional, since the interface is Combat-internal). `Combat.Attacker` (which rolls the crit chance) passes it through to `MeleeAttackBehavior` (straight to `TakeDamage`) and `RangedAttackBehavior` → `Projectile.Launch(target, damage, isCritical)`, which stores it and applies it on arrival.

- `Combat.DamageNumberSpawner` (plain C# class, constructed in `GameBootstrapper.Awake()`) subscribes `DamageAppliedEvent` and spawns/`Show()`s a `DamageNumber` via `PoolManager`. Doesn't distinguish attacker faction — fires for any `Health.TakeDamage` in either direction, since `Health` itself is faction-agnostic.

### AL. Tiered-Linear Enhancement Cost for AttackPower/MaxHealth (implemented — supersedes part of section AC)
`Assets/02. Script/Enhancement/` — `AttackPower`/`MaxHealth` moved off the compound cost curve onto a step-wise linear one, so the *increase-per-level* grows in discrete jumps instead of compounding every level:
- `Enhancement.CostIncrementTier` (`[Serializable]`, not a SO — same "plain data row" shape as `Stage.MonsterSpawnEntry`) — `LevelThreshold`/`Increment`: from `LevelThreshold` onward, each enhance costs `Increment` more than the previous one.
- `EnhancementConfigSO.CostIncrementTiers` (`CostIncrementTier[]`) — empty array = unchanged legacy compound behavior (`BaseCost * CostMultiplier^level`), same "empty/null as a signal" idiom as `RankSO.RequiredStage == null`.
- `EnhancementService.GetNextCost` branches on whether `CostIncrementTiers` is non-empty: `CalculateTieredCost` sums, per tier, `Increment × (levels of that tier at or below the current level)`; `CalculateCompoundCost` is the original formula. Tiered totals stay far inside `int` range even at `MaxLevel = 2000`, so unlike the compound path it needs no `double`/saturate handling.
- Current tuned values: `AttackPower`/`MaxHealth` — `costIncrementTiers = [{0, +10}, {100, +100}, {1000, +1000}]`, `BaseCost = 10`. `AttackSpeed`/`MoveSpeed` — `BaseCost = 1000`, `MaxLevel = 100`, `CostMultiplier = 1.1`. `CriticalChance`/`CriticalDamage` — `BaseCost = 100`, `CostMultiplier = 1.3`.

### AM. Soldier Stat Enhancement Tab (implemented)
`Assets/02. Script/SoldierEnhancement/` + `Assets/02. Script/Soldier/SoldierStatReceiver.cs` + `Assets/02. Script/UI/` — a second, parallel enhancement track that raises the same 6 stats for **every currently-deployed soldier globally**, gold-funded like the player's own Enhancement:
- `SoldierEnhancement.SoldierEnhancementService` — a line-for-line parallel of `Enhancement.EnhancementService`, publishing `SoldierEnhancement.Events.SoldierStatEnhancedEvent` instead. Deliberately duplicated rather than shared, same "parallel service per domain" convention as `EnhancementStoneService`↔`CurrencyService`. Reuses `Enhancement.EnhancementConfigSO`/`CostIncrementTier` as-is.
- **Why this needed a different application strategy than the Player's:** Player's `Character.StatEnhancementReceiver` subscribes once and additively applies each level's delta on top of whatever `RuntimeStats` already holds, which works because the Player is never pooled/destroyed. Soldiers are continuously spawned/despawned/respawned via `PoolManager`/`SoldierRespawner`, and `CharacterStatsProvider.Stats` is a `RuntimeStats` instance cached once per component and **not reset by pooling** — naively reusing the Player's additive-only pattern would either compound the bonus every respawn or leave soldiers with inconsistent stats depending on which enhancement events they happened to be alive to catch.
- `Character.RuntimeStats.ResetTo(CharacterStatsSO source)` — the constructor's field-copy logic extracted so a pooled instance's stats can be rewound to base without allocating a new object.
- `Soldier.SoldierStatReceiver` (on `Soldier.prefab`/`Soldier_Ranged.prefab`) — on every `OnEnable` (fires on every pool `Get()`), calls `Stats.ResetTo(BaseStats)` then loops `SoldierEnhancementService.StatTypes`, applying the full cumulative bonus via `Character.RuntimeStatApplier.Apply`, then `Health.Revive()`. Same "recompute fully from BaseStats every spawn, never accumulate across pool reuse" shape as `Character.StageMonsterScaler.ApplyScale`. While alive, also subscribes `SoldierStatEnhancedEvent` and applies just that single level's delta for live in-combat updates.
- `GameBootstrapper` constructs `SoldierEnhancementService` and calls its 6 `RestoreLevel(...)` calls in `Awake()` (not `Start()`, where the Player's equivalent calls live) — safe because `SoldierStatReceiver` *pulls* the current level on its own `OnEnable` rather than relying on catching a replayed event.
- UI: `UI.SoldierStatPanelUI`/`UI.SoldierStatRowUI` are parallel duplicates of `UI.StatPanelUI`/`UI.StatRowUI`. `Canvas/PanelRoot/StatPanel` has a `SubTabBar` (`BottomMenuUI`, 플레이어/병사 buttons) toggling between `RowContainer` and `SoldierRowContainer`.
- **`BottomMenuUI` gained two opt-in fields** (default off, so every other instance is unaffected): `selectFirstTabByDefault` (auto-opens `panels[0]` in `Awake()`) and `allowToggleClose` (when `false`, clicking the already-active tab is a no-op instead of closing it) — needed because the main bottom nav should start closed-until-tapped, but this sub-tab bar should open 플레이어's rows immediately and not blank on re-tap.
- Tuned values (per-stat, mirroring section AL's player-side numbers at double cost / half value-per-level): `AttackPower`/`MaxHealth` — tiered `[{0,+20},{100,+200},{1000,+2000}]`, `ValuePerLevel` 1/5. `AttackSpeed`/`MoveSpeed` — `BaseCost = 2000`, `ValuePerLevel = 0.005`. `CriticalChance`/`CriticalDamage` — `BaseCost = 200`, `ValuePerLevel` 0.0005/0.0025.

### AN. Player Stat Row Unlock Requirements (implemented)
`Assets/02. Script/Enhancement/` + `Assets/02. Script/UI/StatRowUI.cs` — lets a stat row stay locked behind another stat's level, data-driven the same way `RankSO.RequiredStage` gates rank content:
- `EnhancementConfigSO.HasUnlockRequirement`/`RequiredStatType`/`RequiredLevel`. `HasUnlockRequirement = false` (default) means always-unlocked, so this needed no changes to any config other than the ones being gated (including the parallel `SoldierEnhancement` configs, section AM, left at default).
- `EnhancementService.IsUnlocked(statType)` — `!config.HasUnlockRequirement || GetLevel(config.RequiredStatType) >= config.RequiredLevel`. `GetRequiredStatType`/`GetRequiredLevel` passthroughs let `StatRowUI` build the lock message without holding its own config reference.
- `StatRowUI`'s `Refresh()` sets `multiplierButtons[*].interactable = IsUnlocked` and toggles a `lockOverlay` with text `"{RequiredStatType 한글명} Lv.{RequiredLevel} 필요"`. `StatRow.prefab`'s `LockOverlay` child uses `LayoutElement.ignoreLayout = true` to sit stretched over the whole row despite the root's `VerticalLayoutGroup` — the standard trick for an overlay child inside a layout-grouped parent — and blocks clicks via `Image.raycastTarget` + draw order (last sibling), with `interactable = false` on the buttons as a second line of defense.
- **`OnStatEnhanced` must also refresh on the *required* stat's level-up, not just its own** — a row locked behind another stat's level otherwise never re-checks `IsUnlocked` when that other stat levels up, since its own buttons are non-interactable and nothing else would trigger a refresh (fixed in section AW).
- Content: `Enhancement_AttackSpeed`/`Enhancement_MoveSpeed` require `AttackPower`/`MaxHealth` Lv.100 respectively; `CriticalChance`/`CriticalDamage` require `AttackPower` Lv.140.
