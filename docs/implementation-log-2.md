# 구현 히스토리 2부 (섹션 X~AO)

CLAUDE.md의 "### X. Monster Targeting..."에서 "### AO. Third Rank"까지의 상세 구현 기록입니다. 섹션 번호는 CLAUDE.md 전체 기준(3. Architecture & Technical Rules 하위)과 이어집니다.

### X. Monster Targeting Simplified to Nearest-Ally, Real Attack Range, Visual Tiering (implemented — supersedes the `MonsterTargetSelector` description in section F)
`Assets/02. Script/Combat/MonsterTargetSelector.cs` — replaced the old claim-priority chain (player-if-currently-targeted, else claiming soldier, else player fallback) with a plain nearest-target scan:
- `ChooseTarget()` runs `Physics2D.OverlapCircleAll(position, detectionRange, allyLayerMask)` and returns the nearest live `Health`, falling back to `PlayerTransform` if nothing is in range — the same nearest-wins idiom `EnemyTracker` already used for the opposite faction.
- `allyLayerMask` points at the `Player` layer; `Soldier`/`Soldier_Ranged` prefabs were moved onto that layer (previously `Default`) so one scan naturally covers both the Player and any Soldier.
- `Combat.PlayerTargetTracker`/`Combat.PlayerTargetMarker` and `Soldier.SoldierTargetRegistry.TryGetClaimant` lost their only consumer (the removed priority chain) and were deleted. `SoldierTargetRegistry.IsClaimedByOther`/`SetClaim` remain — still used by `SoldierEnemyFilter` for soldier-vs-soldier target spreading, an unrelated concern.
- Monster's own attack switched from `ContactAttacker` (pure physics-trigger, no range concept at all) to the same `Attacker` + `MeleeAttackBehavior` composition Player/Soldier use, targeting the `Player` layer. `MonsterTargetSelector.Retarget()` now also sets `CharacterMover.StoppingDistance = Stats.AttackRange` (mirroring `EnemyTracker`), so monsters stop at range instead of walking fully onto the target's position — `StoppingDistance` previously defaulted to `0`, which is why monsters used to visually stack exactly on top of whatever they were attacking. All three monster tiers' `CharacterStatsSO.AttackRange` set to `2.5` (matching melee `Soldier`) — previously `0` and silently unused since `ContactAttacker` never read it.
- `Monster_Elite.prefab`/`Monster_Boss.prefab` also get a purely visual `transform.localScale` bump (1.2x / 1.5x) so they read as tougher at a glance. `AttackRange` lives on `CharacterStatsSO`, entirely independent of transform scale, so this doesn't touch combat reach. Each prefab's `HealthBar` child is counter-scaled (`1/scale`) so the bar itself stays a consistent on-screen size instead of growing with the body.

### Y. Rank Gating Fixes: Startup Promotion Replay & Locked Soldier Tab (implemented — supersedes part of section U)
- **Gotcha fixed:** `RankService` used to sit at its constructor-default rank (index 0) until `GameBootstrapper.Start()` called `RestoreLevel`. But `OfflineProgressService.CalculateAndApply()` runs *before* that in `Start()`, and if simulated offline progress advanced the record, `RankService.OnHighestStageCleared` re-derived every rank from scratch as if newly earned (`isRestore: false`) — replaying the rank-up popup on every single launch for ranks the player had already reached long ago. Fixed with `RankService.SeedRank(rankIndex)`, which sets the in-memory rank silently (no event) from the save; called in `GameBootstrapper.Awake()` right after `SaveService.Load()`, strictly before offline progress ever runs.
- `UI.SoldierPanelGateUI` (on the `SoldierPanel` bottom-tab panel) — while the current rank is below a configured `requiredRank`, shows a locked message instead of the roster/deployment lists (which used to render as unexplained empty containers). The message is built from `requiredRank.RequiredStage` (`"{chapter}-{stageNumber} 스테이지 클리어 후 오픈됩니다."`), so it tracks whatever the real requirement is with no code change if the rank/stage is retuned. Subscribes `RankChangedEvent` so reaching the rank while the tab is already open unlocks it immediately.

### Z. Soldier Deployment & Equipment Fixes (implemented)
- `Soldier.SoldierDeploymentService.TryAssign` — a soldier can now occupy at most one deployment slot at a time. Assigning an instance that's already deployed elsewhere auto-vacates the old slot first; the deployment picker popup (`SoldierDeploymentPickerPopupUI`) also excludes units already deployed to a *different* slot from the pick list. Previously nothing enforced this, so a single soldier instance could be assigned to every slot at once (no real exclusivity).
- `SoldierEquippedGearService.Equip` now actually **consumes** 1 unit from `SoldierEquipmentInventoryService`'s stock instead of just pointing at the stack (the model it originally copied from the player's own `Inventory.EquippedGearService`, which works there because the player has exactly one wearer). With many soldiers able to want the same line, the old non-consuming model let every soldier "equip" the same single copy at once. `Equip` now fails if stock is empty, is a no-op if the unit already has that exact line equipped, and returns a swapped-out item's copy to stock. A new `Unequip` (previously nonexistent — equipping was one-way) also returns the copy to stock. The old "count hits zero → auto-unequip everyone on that line" safety net (originally needed because equipping never touched count) was removed, since it now misfires on the *expected* case of equipping the last copy.

### AA. Gacha Popup: Categories, Tiers & Multi-Pull (implemented)
`Assets/02. Script/Gacha/` + `Assets/02. Script/UI/` — a full-screen modal gacha screen, replacing the inline pull button that used to live in the soldier roster panel:
- The bottom tab bar's fifth slot (previously "유물"/`RelicPanel`, an unimplemented placeholder) was repurposed into "뽑기", wired directly to `UI.GachaPopupUI.Open()` rather than through `BottomMenuUI`'s normal panel array — this popup needs to cover the tab bar itself, which the other four tabs don't.
- Two-level tab structure, built by nesting the existing generic `BottomMenuUI` shell twice: an outer category row (무기 뽑기 / 병사 뽑기) and, per category, an inner tier row (일반 / 고급 / 유료). Adding either a new category or a new tier is just one more button+panel entry in an inspector array — no new tab-switching code. Only the "일반" tier is wired to a working table on either side; 고급/유료 are placeholder-only ("준비 중") since neither a probability table nor a currency source exists for them yet.
- `EquipmentGachaPoolEntry`/`EquipmentGachaTableSO`/`EquipmentGachaService` mirror the pre-existing `GachaPoolEntry`/`GachaTableSO`/`GachaService` (soldier gacha) structure exactly, but spend gold instead of soldier tickets and grant the result by republishing `Loot.Events.ItemDroppedEvent` (the same acquisition path `EquipmentFusionService` already reuses) rather than touching `InventoryService` directly.
- Both services expose `Pull(tierIndex, count)`: loops up to `count` times, stopping the moment currency runs out (partial success — a "300개 뽑기" with only enough currency for 50 still nets 50, not zero), and publishes one aggregated `SoldierPulledEvent`/`EquipmentPulledEvent` (now carrying `IReadOnlyList<T>` instead of a single item) rather than one event per pull. A single "1개 뽑기" is just `count = 1` through the same path. `SoldierPulledPopupUI`/`EquipmentPulledPopupUI` group the batch by item name and show per-item counts.
- **Gotcha fixed:** `SoldierPulledPopup` predates `GachaPopup` in the Canvas hierarchy, so its result notification rendered *behind* the still-open gacha popup (later siblings draw on top). Moved to the last sibling.

### AB. UI Layout & Discoverability Fixes (implemented)
- **Equipment row had no discoverable way to equip.** The row's biggest, most natural tap target (the item name) opens a read-only stat detail popup with no equip action, and the actual equip trigger was the row's own background `Button` sitting *behind* the name/fuse/enhance children — which, via `HorizontalLayoutGroup`, tile the row's entire width, leaving only a ~20px sliver of uncovered padding clickable. Added an explicit "장착" button (same pattern as the existing fuse/enhance buttons), disabled and reading "장착됨" once that line is the one currently worn.
- **Player was missing a head HP bar.** Monster/Soldier prefabs already nest `HealthBar.prefab`; Player didn't. Added the same instance at the same local offset.
- **`EquippedSlotBarUI` slots showed nothing when empty.** Each slot only ever displayed the equipped item's name (or `"-"`), so an empty slot gave no clue which gear type it represented. Added a permanent slot-type label (무기/장갑/갑옷/투구/신발) above the existing item-name label — purely static scene content, no code change, since the slot type never changes at runtime.
- **List popups with no scroll overflowed their frame.** `EquipmentSlotPopupUI`'s row container, `SoldierDeploymentPickerPopupUI`'s row container, and `StatPanel`'s row list all either rendered past their popup/panel bounds (no `RectMask2D`) or had `sizeDelta` values that canceled out to a literal zero-height container against their parent's own size (so rows existed but nothing was visible). All three were rebuilt into the same `RowContainer(ScrollRect) → Viewport(RectMask2D) → Content(VerticalLayoutGroup + ContentSizeFitter)` structure, which is now the standard pattern for any scrollable list in this project.

### AC. Enhancement System Expansion: New Stats & Critical Hits (implemented)
`Assets/02. Script/Enhancement/` + `Assets/02. Script/Character/` + `Assets/02. Script/Combat/Attacker.cs`:
- `EnhancementStatType` gained `AttackSpeed`, `MoveSpeed`, `CriticalChance`, `CriticalDamage` (supersedes the two-value enum shown in section L). `CharacterStatsSO`/`RuntimeStats` gained matching `CriticalChance` (default `0`) and `CriticalDamageMultiplier` (default `0.5` — a critical hit deals `AttackPower * (1 + CriticalDamageMultiplier)`, so the default is "crits deal 150%").
- `Combat.Attacker` rolls `Random.value < Stats.CriticalChance` on every attack and scales damage accordingly before calling `IAttackBehavior.Execute`. This applies to whatever shares the component — Player, Soldier, and Monster alike — but monsters never crit in practice since their base `CriticalChance` is `0`.
- `Character.RuntimeStatApplier` now takes the owning character's *base* `CharacterStatsSO` alongside its `RuntimeStats`, because `AttackSpeed`/`MoveSpeed` are designed as "N% of the character's own base value per level" rather than a flat delta (e.g. `stats.MoveSpeed += baseStats.MoveSpeed * delta`) — `CriticalChance`/`CriticalDamage` stay flat additive (percentage-point) since they have no meaningful "base" to scale from. Both `StatEnhancementReceiver` and `EquipmentStatReceiver` (which share this mapping table) pass `CharacterStatsProvider.BaseStats` into the call now.
- `EnhancementConfigSO.CostIncreasePerLevel` (linear, `int`) was replaced with `CostMultiplier` (compound, `float`) — next cost is `BaseCost * CostMultiplier ^ level`, computed in `double` and saturated at `int.MaxValue` rather than cast straight to `int`. **Gotcha this fixed:** the naive `int` cast overflowed (wrapped negative) around level 47 at a 1.5x multiplier, and `CurrencyService.TrySpendGold` then read the negative cost as "affordable," making enhancement free (and net gold-*positive*, since spending a negative amount is adding). Current tuned values: `AttackPower`/`MaxHealth`/`AttackSpeed`/`MoveSpeed` at 1.05x–1.1x (`AttackPower`/`MaxHealth` 1.05x, `AttackSpeed`/`MoveSpeed` 1.1x), `CriticalChance`/`CriticalDamage` at 2.1x, all with `MaxLevel = 2000` (previously 50) — chosen so the compound curve stays affordable across a meaningfully large number of levels instead of most of the level range being purely decorative, since monster HP scaling (section X derived from section R) grows *linearly* with stage index while a much steeper compound rate does not correspond to that at all.
- `AttackSpeed`/`MoveSpeed`: 1%/level, capped at level 20 (±20% off base). `CriticalChance`: 0.1%/level to level 500. `CriticalDamage`: 0.5%/level to level 300 (i.e. the crit bonus fraction, not total multiplier — see above).
- `UI.StatDisplayNames.FormatValue(statType, value)` — new formatting helper so the four percentage-based stats render as `"N%"` in `StatRowUI` instead of a raw decimal (`0.01` read as meaningless before this).
- `Save.SaveData`/`SaveService` gained one level field per new stat, following the exact same per-stat-field pattern as `AttackPowerLevel`/`MaxHealthLevel` (no generic collection — six named int fields, consistent with existing style rather than a new serialization scheme).

### AD. Offline Progress: Difficulty-Accurate & Repeat-Only (implemented — supersedes section P)
`Assets/02. Script/Offline/OfflineProgressService.cs`:
- **Gotcha fixed:** the offline combat simulation computed monster health from each monster's flat `CharacterStatsSO.MaxHealth`, completely ignoring `StageDifficultyConfigSO`'s per-stage-index multiplier that real combat applies via `StageMonsterScaler` (up to ~49x by the final stage). The simulation was effectively always fighting stage-1-strength monsters, so a long-enough offline window could blow through most of the 320-stage catalog in one sitting — including stages the player could never actually clear live. Fixed by computing `_difficultyConfig.GetMultiplier(_catalog.IndexOf(stage))` and folding it into the simulated monster's health exactly like `StageMonsterScaler` does.
- Even with health scaling fixed, the simulation still advanced into new, unproven stages every time it "cleared" one. Redesigned to be repeat-only: it now simulates the player's *highest-cleared* stage on repeat for the entire time budget and never advances the record or resume position past it, always resuming there afterward regardless of whatever death-regressed position (see `StageProgression`, section Q) was current when the player left. `HighestStageClearedEvent` is no longer published from here at all, since the record never changes.
- `Offline.Events.OfflineProgressCalculatedEvent.StagesCleared` renamed to `TimesCleared`, reflecting that it now counts repeat-clears of one stage rather than newly-conquered stages.

### AE. War Objective Progress & Pre-Climax Warmup Warning (implemented)
`Assets/02. Script/War/` + `Assets/02. Script/UI/` — adds a readable progress signal to the four War objectives (section context: `WarObjectiveType` = `Annihilation`/`StructureCapture`/`BossDefeat`/`CargoProtection`) and a 3-second warning countdown before a climax fight's judgment actually starts:
- `IWarObjective.Progress01` (0~1) — `AnnihilationObjective`/`BossDefeatObjective` just return `IsCompleted` as 0/1 (no continuous progress exists); `CargoProtectionObjective` returns `elapsed / protectDuration`; `StructureCaptureObjective` averages `WarStructure.Control` across `requiredStructures`.
- `WarBattleController` no longer activates the objective the instant a climax stage (`StageNumber == climaxStageNumber`) loads. It now starts a `climaxWarmupDuration` (default 3s) countdown, publishing `War.Events.WarClimaxWarmupStartedEvent(objectiveType, chapter, duration)` instead. `Tick()` counts the warmup down and, once it hits zero, runs the previous immediate-activation logic (`ActivateObjective`, `_isActive = true`, publish `WarClimaxStateChangedEvent(true, ...)`). `warZoneRoot` (structures/cargo) still activates immediately so the battlefield is visible during the countdown, but `ResetForNewAttempt()` — and therefore judgment — only runs once warmup ends, so any `WarStructure` progress ticked during the countdown is wiped before real judgment starts. Leaving climax (or re-entering) mid-warmup resets `_isWarmingUp` cleanly.
- `War.Events.WarClimaxStateChangedEvent(IsClimax, ObjectiveType, Chapter)` — fires when the real fight starts (`IsClimax=true`, after warmup) and when climax is left (`IsClimax=false`). `War.Events.WarObjectiveProgressChangedEvent(Progress01)` — fires from `Tick()` only while the objective is actually active, whenever `Progress01` changes.
- `UI.WarBattleHudUI` — subscribes `WarClimaxStateChangedEvent`/`WarObjectiveProgressChangedEvent`; shows an objective banner always, and a progress gauge only for `StructureCapture`/`CargoProtection` (`Annihilation` already has `StageInfoUI`'s remaining-monster count as an equivalent signal, `BossDefeat` has the boss's own `HealthBarUI` — see gotcha below for why that pairing needed a follow-up fix).
- `UI.WarClimaxWarningUI` — subscribes `WarClimaxWarmupStartedEvent` (show banner + a locally-ticking countdown number) and `WarClimaxStateChangedEvent` (hide unconditionally, regardless of `IsClimax` — covers both "real fight just started" and "player left climax mid-warmup" with one rule).
- `UI.WarObjectiveBannerText` — static `WarObjectiveType → 한글 배너 문구` helper shared by `WarBattleHudUI`/`WarClimaxWarningUI` so the two don't duplicate the switch (same motivation as `StatDisplayNames`/`RuntimeStatApplier`).
- **Gotcha fixed:** `StageInfoUI` showed "남은 몬스터: X/Y" unconditionally on every stage, including climax stages running a non-`Annihilation` objective — where remaining monster count isn't the real clear condition and just confuses the player (e.g. during `StructureCapture`, monsters can keep spawning/dying with zero relation to whether the structure is captured). Fixed by having `StageInfoUI` additionally subscribe `WarClimaxWarmupStartedEvent`/`WarClimaxStateChangedEvent` and suppress that line whenever the active climax objective isn't `Annihilation`.
- **Testing gotcha (do not repeat):** publishing a synthetic `Stage.Events.StageClearedEvent`/`StageChangedEvent`/`CharacterDiedEvent` directly on the live `EventBus` during a Play Mode session — e.g. to verify an objective's completion path — is indistinguishable to `StageProgression`/`SaveService` from a real clear/death. `StageProgression` blindly advances its own tracked index on any `StageClearedEvent` (it doesn't check the event's payload against what's actually loaded), and `SaveService` writes every `StageChangedEvent` straight to `PlayerPrefs`. A synthetic event during testing genuinely advanced real save progress by one stage in this project's dev save. Prefer reflection-invoking the private method that owns the judgment logic directly (bypassing the EventBus) when verifying "did X correctly detect Y" during Play Mode.

### AF. Player Manual Control Toggle (implemented)
`Assets/02. Script/Character/` + `Assets/02. Script/UI/` — lets the player freely switch between the existing auto-chase movement and direct tap-to-move. Deliberately general-purpose and independent of War or any other system (not gated by climax state) — the toggle is always available.
- `Character.PlayerControlMode` enum `{ Auto, Manual }`; `Character.Events.PlayerControlModeChangedEvent`; `Character.PlayerControlModeService` (`IManager`/`IService`, registered in `GameBootstrapper`) holds the current mode, `Toggle()`/`SetMode()` publish the event on change.
- `Character.PlayerManualMover` (Player-only, `ITickable`) — on `Manual`, disables the Player's own `EnemyTracker` component to take over `CharacterMover.Target` (the exact same "disable the sibling tracker, drive `CharacterMover` directly" pattern `Soldier.SoldierBehaviorController` already uses for ranged kiting/off-screen return — see section W). On a new Input System pointer press that isn't over UI (`EventSystem.IsPointerOverGameObject()`), converts the tap's screen position to a world point (`Camera.ScreenToWorldPoint`) and points `CharacterMover.Target` at a scratch, unparented Transform placed there (`StoppingDistance = 0`) — unparented for the same reason `SoldierBehaviorController._returnAnchor` must be (section W: a child anchor's world position would recede as the character approaches it). On `Auto`, re-enables `EnemyTracker`. `Attacker` (auto-attack) is untouched by mode either way — only movement changes.
- `UI.PlayerControlModeToggleUI` — a persistent top-right button showing "자동"/"수동", positioned at Canvas sibling index 3 (ahead of every `*Popup` object) so any popup always draws on top of it rather than the toggle floating above open popups.

### AG. War Boss Unique Patterns (implemented)
`Assets/02. Script/War/Boss/` — gives the War-climax boss (currently chapter 3's `BossDefeat` objective) telegraphed AoE attacks on top of the normal `Monster_Boss` composition, without touching `Monster_Boss` itself — every other chapter's `s=40` finale boss is unaffected.
- `War.Boss.WarBossPatternSO` (data) — one pattern: `TelegraphDuration`, `Radius`, `Damage`. Pattern variety is pure data, not a C# type per pattern — `WarBossPattern_GroundSlam` (radius 2.5, damage 25, 1.5s telegraph) and `WarBossPattern_WideShockwave` (radius 4.5, damage 15, 2s telegraph) under `Assets/03. SO/War/`.
- `War.Boss.WarBossPatternRunner` (`ITickable`, `IPoolable`) — cycles its `patterns` array on `intervalBetweenPatterns`; each cast snapshots the nearest ally's (Player/Soldier layer) position at that instant, shows a `WarBossTelegraphIndicator` there, and after `TelegraphDuration` applies `Damage` via `Physics2D.OverlapCircleAll` + `Health.TakeDamage` to whatever is still standing in `Radius`. ### AH. Skill System (implemented — supersedes the "SkillPanel is a scriptless placeholder" note in section M)
`Assets/02. Script/Skill/` — three fixed auto-cast skills the player levels up with gold + enhancement stones; deliberately does not know "Player" exists any more than Enhancement does:
- `SkillSO` — data asset: `DisplayName`, `Icon`/`IconTint` (all three skills currently reuse `WeaponSprite.png` tinted differently — same placeholder-reuse pattern as Player/Soldier/Cargo, no dedicated skill art yet), `Cooldown`, `MaxLevel`, a gold/stone cost curve (`GoldCostBase`/`GoldCostIncreasePerLevel`, `StoneCostBase`/`StoneCostIncreasePerLevel` — linear, same shape as `EquipmentEnhancementConfigSO`), and `GetMagnitude(level)` = `EffectValueBase + EffectValuePerLevel * level`.
- `SkillCatalogSO` — flat `SkillSO[]`, same `IndexOf`/`GetAt` shape as every other catalog in this project; lets `SaveService` identify a skill by index instead of an asset reference.
- `ISkillEffect.Execute(origin, magnitude)` — mirrors `Combat.IAttackBehavior`'s strategy pattern: `SkillSlot` never knows what a skill actually does, only when to call it. Three implementations under `Skill/Effects/`: `AreaDamageSkillEffect` (`Physics2D.OverlapCircleAll` around the caster, damages every live `Health` hit), `SingleTargetStrikeSkillEffect` (nearest live target in range), `SelfBuffSkillEffect` (temporary `AttackPower` bonus on the caster's own `CharacterStatsProvider`; re-casting reverts the previous bonus first instead of stacking, so repeated casts can't compound).
- `SkillSlot` (`MonoBehaviour`, `ITickable`) — one fixed slot. Caches `GetComponent<ISkillEffect>()` in `Awake`, accumulates `deltaTime`, and calls `Execute` every `SkillSO.Cooldown`, reading the current level from `SkillService` fresh on every cast (never caches it, so a mid-cooldown level-up takes effect on the very next cast). Player has 3 child GameObjects for this (`Skill_Whirlwind`/`Skill_BattleCry`/`Skill_PowerStrike`), each just a `SkillSlot` + one effect component + its own `SkillSO` reference — composition, not inheritance, same as every other domain here. **Level-0 gate (fixed):** `Tick` originally called `Execute` regardless of level, so an un-leveled (level-0, "not yet learned") skill still auto-cast at its flat `EffectValueBase` on a fixed cooldown, independent of the player's actual power — reported as monsters "occasionally taking exactly 30 damage" (강타's `EffectValueBase`) for no visible reason, since it's a flat skill hit sitting among otherwise-scaling auto-attack numbers. `Tick` now reads the level *before* touching `_elapsed`/cooldown and returns immediately if `level <= 0`, so an un-leveled skill neither casts nor accumulates cooldown progress — it starts counting down fresh from the moment it's first leveled to 1.
- `SkillService` (`IManager`/`IService`) — `TryLevelUp(definition)` requires both `Loot.CurrencyService.TrySpendGold` and `Equipment.EnhancementStoneService.TrySpendStones` to succeed (fails harmlessly with no partial spend if either is short), then publishes `SkillLeveledUpEvent`. Keeps only level state and never touches `RuntimeStats`/damage itself — same "service owns state, component applies effect" split as `EnhancementService`/`StatEnhancementReceiver`. Takes only `EventBus` as a constructor dependency (not `CurrencyService`/`EnhancementStoneService`) and looks those up via `GameBootstrapper.Services` at `TryLevelUp` time instead: both currencies are constructed *after* `SaveService.Load()` in `GameBootstrapper.Awake()` (so they can seed from the save), but `SkillService` itself must exist *before* `SaveService` (which takes it as a save/restore dependency) — requiring the currencies as constructor params would be a circular dependency.
- Save: `SkillService.SkillLevelSnapshot[]` (catalog index + level, same shape as `InventoryService.OwnedEquipmentSnapshot`) serialized as one JSON blob (`SaveData.SkillLevelsJson`), same pattern as the Inventory/equipped snapshot in section O. **Gotcha fixed:** `SkillLevelSnapshot` was originally missing `[Serializable]`, so `JsonUtility` silently produced an empty array on save — the level-up itself still worked (gold/stones were spent, the in-memory level went up), but the level silently reset to 0 on the next load, with no error anywhere. `JsonUtility` fails this particular case silently rather than throwing; worth checking for on any future save-blob struct.
- UI: `UI.SkillSlotBarUI` + `UI.SkillDetailPopupUI` (`Assets/02. Script/UI/`) are the real controllers that replaced the old scriptless "준비 중" `SkillPanel` mentioned in section M — same icon-bar-then-popup shape as `Equipment.EquippedSlotBarUI`/`EquipmentSlotPopupUI`, but simpler since a skill slot has no "which owned copy is equipped" concept, just one level per skill. `SkillSlotBarUI` shows `Lv.N` per slot and opens `SkillDetailPopupUI` on tap; the popup shows the current magnitude and the next level's gold/stone cost (or "MAX") and wires its 레벨업 button straight to `SkillService.TryLevelUp`.
- Not yet done: no Rank gate (Soldier gates at 십인 대장 via `requiredRank`, section U/Y; Skill has no such check and is active from game start), no cast VFX/SFX (melee at least has `WeaponSwing`; skills apply damage/buff with no visual tell). The loadout is no longer fixed — see section AQ for the 6-slot equip system that superseded this.

### AI. Content Editor: In-Editor Art & Catalog Tool (implemented, Editor-only)
`Assets/02. Script/Editor/` — a `Tools/Idle Project/Content Editor` window (opened via `[MenuItem]`) that consolidates two previously-manual jobs (assigning placeholder art, hand-editing catalog SO fields in the Inspector one asset at a time) into one place. Pure Editor tooling: no runtime code depends on anything here, and the `Editor/` folder name alone excludes it from player builds (no separate asmdef needed since the project has none).
- `ContentEditorWindow` (`EditorWindow`) — two tabs via `GUILayout.Toolbar`: **World Sprites** and **Catalog Editor**.
- **World Sprites tab** — a fixed list of `ArtAssignmentTarget`s, each a small polymorphic wrapper hiding *how* a sprite gets read/written for that particular kind of target (drag in a new `Sprite`, hit 적용, it writes straight to the real asset):
  - `PrefabSpriteTarget` — prefab assets (`Monster`/`Monster_Elite`/`Monster_Boss`/`Monster_GoldDungeon`/`WarBoss`/`Soldier`/`Soldier_Ranged`/`Cargo`/`Projectile`). Uses `PrefabUtility.LoadPrefabContents` + `SaveAsPrefabAsset` so it edits the prefab *asset* without needing Prefab Mode open.
  - `SceneSpriteTarget` — the `Player` GameObject, which (unlike the above) lives directly in the scene rather than as a prefab asset. Finds it by name in whatever scene is currently open, edits its `SpriteRenderer`, and marks the scene dirty; does nothing (safely) if that scene isn't open.
  - `ScriptableObjectIconTarget` — SO `icon` fields (`Skill_WhirlwindSlash`/`Skill_BattleCry`/`Skill_PowerStrike`, `Soldier_Melee`/`Soldier_Ranged`), via `SerializedObject`.
  - Equipment (150 assets) is deliberately **not** in this tab — too many for a flat manual list, handled by the Catalog Editor's searchable list instead. Stage (320 assets) is excluded entirely — that content is generated by a one-off script (section V), not meant for one-by-one hand editing. Animator Controller assignment isn't supported yet since no prefab in the project uses `Animator` at all (everything is a static sprite) — deferred until that exists.
- **Catalog Editor tab** (`CatalogEditorPanel` + `CatalogRegistration`) — generic editor for *any* of this project's catalogs (the "one SO holding a flat array of item SOs" shape used everywhere: `EquipmentCatalogSO`, `SoldierCatalogSO`, `SkillCatalogSO`, `RankCatalogSO`, `EquipmentGradeCatalogSO`, `SoldierEquipmentCatalogSO`, `BehaviorProfileCatalogSO`). `CatalogRegistration` is just `{ DisplayName, CatalogAssetPath, ArrayFieldName, ItemType }` — adding a catalog to the tool is one entry in `ContentEditorWindow.BuildCatalogPanel()`, no new code. Pick a catalog → search/click an item → every field on that item's SO renders via `SerializedObject` + `EditorGUILayout.PropertyField` (iterating `SerializedObject.GetIterator()`, skipping `m_Script`) — this is why the tool needs no per-field code at all: whatever fields a catalog's item SO has (string, enum, `Sprite`, nested arrays, object refs, ...) just show up and are editable, including fields added after this tool was built. "+ 새 항목 추가" creates a new SO instance next to the catalog asset and appends it to the catalog's array; "삭제" removes the selected item from the array and deletes its asset, behind an `EditorUtility.DisplayDialog` confirmation since it's not reversible.
- **Gotcha (deleting from an Object-reference array):** `SerializedProperty.DeleteArrayElementAtIndex` on an array of object references only *nulls out* the slot on the first call if the reference wasn't already null — it takes a second call to actually shrink the array. `CatalogEditorPanel.DeleteSelectedItem` checks `arraySize` after the first call and calls it again if the size didn't change; skipping this leaves a `null` gap in the catalog array instead of removing the slot.
- This tool directly motivated adding an `Icon` field to `EquipmentSO`/`SoldierEquipmentSO` (see section J) — both previously had no icon field at all (Equipment showed grade tint only), so there was nothing for the World Sprites tab (or the Catalog Editor's generic `PropertyField` rendering) to assign. Neither field is drawn by any real UI yet — this only gets the data in place.

### AL. Tiered-Linear Enhancement Cost for AttackPower/MaxHealth (implemented — supersedes part of section AC)
`Assets/02. Script/Enhancement/` — `AttackPower`/`MaxHealth` moved off the compound cost curve onto a step-wise linear one, so the *increase-per-level* itself grows in discrete jumps instead of compounding every level:
- `Enhancement.CostIncrementTier` (new, `[Serializable]`, not a SO — same "plain data row" shape as `Stage.MonsterSpawnEntry`) — `LevelThreshold`/`Increment`: from `LevelThreshold` onward, each enhance costs `Increment` more than the previous one.
- `EnhancementConfigSO` gained `CostIncrementTiers` (`CostIncrementTier[]`). **Empty array = unchanged legacy behavior** (`BaseCost * CostMultiplier^level`) — this is why `AttackSpeed`/`MoveSpeed`/`CriticalChance`/`CriticalDamage` needed zero code changes, only value tweaks. Same "empty/null as a signal" idiom as `RankSO.RequiredStage == null` meaning "starting rank."
- `EnhancementService.GetNextCost` branches on whether `CostIncrementTiers` is non-empty: `CalculateTieredCost` sums, per tier, `Increment × (levels of that tier at or below the current level)`; `CalculateCompoundCost` is the untouched original formula. Tiered totals stay far inside `int` range even at `MaxLevel = 2000` (~591,010 at level 1500), so unlike the compound path it needs no `double`/saturate handling.
- Tuned values: `AttackPower`/`MaxHealth` — `costIncrementTiers = [{0, +10}, {100, +100}, {1000, +1000}]` (i.e. 강화당 +10원 until 100강, +100원 until 1000강, +1000원 beyond), `BaseCost` still `10`. `AttackSpeed`/`MoveSpeed` — `BaseCost = 1000`, `MaxLevel = 100` (was `10`/`20`), `CostMultiplier` unchanged (`1.1`). `CriticalChance`/`CriticalDamage` — `BaseCost = 100`, `CostMultiplier = 1.3` (was `10`/`2.1`).
- Verified in Play Mode via `EnhancementService.GetNextCost` at levels 0/99/100/999/1000/1500 for `AttackPower` (10 / 1,000 / 1,010 / 90,910 / 91,010 / 591,010 — matches the tier-boundary math exactly) and level-0/1 spot checks for the other four configs.

### AM. Soldier Stat Enhancement Tab (implemented)
`Assets/02. Script/SoldierEnhancement/` + `Assets/02. Script/Soldier/SoldierStatReceiver.cs` + `Assets/02. Script/UI/` — a second, parallel enhancement track that raises the same 6 stats (`AttackPower`/`MaxHealth`/`AttackSpeed`/`MoveSpeed`/`CriticalChance`/`CriticalDamage`) for **every currently-deployed soldier globally**, gold-funded like the player's own Enhancement:
- `SoldierEnhancement.SoldierEnhancementService` — a line-for-line parallel of `Enhancement.EnhancementService` (same `GetLevel`/`GetMaxLevel`/`GetValuePerLevel`/`GetNextCost`/`RestoreLevel`/`TryEnhance(Multiple)`, same tiered/compound cost branching), publishing `SoldierEnhancement.Events.SoldierStatEnhancedEvent` instead of `Enhancement.Events.StatEnhancedEvent`. Deliberately duplicated rather than shared/abstracted — same "parallel service per domain" convention as `EnhancementStoneService`↔`CurrencyService` and `EquipmentGachaService`↔`GachaService`. Reuses `Enhancement.EnhancementConfigSO`/`CostIncrementTier` as-is (pure data, no reason to fork).
- **Why this needed a different application strategy than the Player's:** Player's `Character.StatEnhancementReceiver` subscribes once and additively applies each level's delta on top of whatever `RuntimeStats` already holds, which works because the Player is never pooled/destroyed. Soldiers are continuously spawned/despawned/respawned via `PoolManager`/`SoldierRespawner`, and `CharacterStatsProvider.Stats` is a `RuntimeStats` instance cached once per component and **not reset by pooling** — so naively reusing the Player's additive-only pattern would either compound the bonus every respawn (if reapplied blindly) or leave individual soldiers with inconsistent stats depending on which enhancement events they happened to be alive to catch (if only reacting to live events).
- `Character.RuntimeStats.ResetTo(CharacterStatsSO source)` (new) — the constructor's field-copy logic extracted into a callable method, so a pooled instance's stats can be rewound to base without allocating a new object.
- `Soldier.SoldierStatReceiver` (new, on `Soldier.prefab`/`Soldier_Ranged.prefab`, requires `CharacterStatsProvider`+`Health`) — on every `OnEnable` (fires on every pool `Get()`, matching `PoolManager`'s `SetActive(true)`), calls `Stats.ResetTo(BaseStats)` then loops `SoldierEnhancementService.StatTypes`, applying `GetValuePerLevel(type) * GetLevel(type)` (the full cumulative bonus, since RuntimeStats was just reset to base) via the shared `Character.RuntimeStatApplier.Apply` table, then `Health.Revive()`. Same "recompute fully from BaseStats every spawn, never accumulate across pool reuse" shape as `Character.StageMonsterScaler.ApplyScale`. While alive, also subscribes `SoldierStatEnhancedEvent` and applies just that single level's delta (not cumulative) for live in-combat updates.
- `GameBootstrapper` constructs `SoldierEnhancementService` and calls its 6 `RestoreLevel(...)` calls in **`Awake()`**, not `Start()` (where the Player's equivalent calls live). This is safe specifically because `SoldierStatReceiver` *pulls* the current level on its own `OnEnable` rather than relying on catching a replayed event — nothing needs to already be subscribed, it only needs `SoldierEnhancementService`'s internal level dictionary seeded before any soldier can possibly spawn, which `GameBootstrapper`'s `-1000` script execution order (section H) already guarantees.
- Save: 6 more flat `int` fields on `SaveData` (`SoldierAttackPowerLevel` etc., same explicit-named-field convention as the player ones — constructor is now 24 positional params, flagged as a known growing-pain but kept consistent rather than switching schemes), `SaveService` subscribes `SoldierStatEnhancedEvent` the same way it subscribes `StatEnhancedEvent`.
- UI: `UI.SoldierStatPanelUI`/`UI.SoldierStatRowUI` are parallel duplicates of `UI.StatPanelUI`/`UI.StatRowUI` (hardcode `SoldierEnhancementService`/`SoldierStatEnhancedEvent` directly, matching those components' existing non-injected style), using a cloned `SoldierStatRow.prefab` (same visual as `StatRow.prefab`, just re-pointed at the new script). `Canvas/PanelRoot/StatPanel` gained a `SubTabBar` (`BottomMenuUI`, 2 buttons: 플레이어/병사) toggling between the pre-existing `RowContainer` (shrunk to make room for the bar) and a new sibling `SoldierRowContainer` — same nested-tab recipe as `GachaPopupUI`'s category/tier tabs.
- **UX fix:** `BottomMenuUI` originally always started with every panel closed and toggled the active tab closed on a second click — fine for the main bottom nav (스탯/장비/스킬/병사/뽑기, deliberately closed-until-tapped) but wrong for this sub-tab bar, where opening 스탯 should show 플레이어's rows immediately and re-tapping 플레이어 shouldn't blank the panel. `BottomMenuUI` gained two opt-in fields — `selectFirstTabByDefault` (auto-opens `panels[0]` in `Awake()`) and `allowToggleClose` (when `false`, clicking the already-active tab is a no-op instead of closing it) — both default to the original behavior (`false`/`true`) so every other `BottomMenuUI` instance (main bottom nav, Gacha's nested tabs) is untouched; only `StatPanel/SubTabBar` sets `selectFirstTabByDefault=true, allowToggleClose=false`.
- Tuned values (per-stat, same `BaseCost`/`MaxLevel` as the player's own config; see section AL for the player-side numbers this mirrors): `AttackPower`/`MaxHealth` — tiered `[{0,+20},{100,+200},{1000,+2000}]` (double the player's increments), `ValuePerLevel` 1/5 (half the player's); `AttackSpeed`/`MoveSpeed` — `BaseCost = 2000` (double, `CostMultiplier` unchanged at `1.1`), `ValuePerLevel = 0.005` (half); `CriticalChance`/`CriticalDamage` — `BaseCost = 200` (double, `CostMultiplier` unchanged at `1.3`), `ValuePerLevel` 0.0005/0.0025 (half).
- Verified in Play Mode: enhancing a stat live updates every currently-alive soldier simultaneously; killing a soldier and waiting for `SoldierRespawner` to bring it back shows the cumulative bonus intact (not reset, not doubled); `SaveService`/`PlayerPrefs` correctly persists the level; real UI button clicks through both the row's multiplier buttons and the new 플레이어/병사 sub-tab toggle work end-to-end.
